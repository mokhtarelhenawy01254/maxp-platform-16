# مهارة هندسة وبناء وكلاء MaxP الموحدة (MaxP Agent Builder)

هذه المهارة هي **المصدر المرجعي الإلزامي والأوحد (Single Source of Truth)** لتصميم، برمجة، تكوين، واختبار وكلاء الذكاء الاصطناعي داخل منصة MaxP. تجمع المهارة بين محرك التشغيل المؤسسي (`Microsoft Agent Framework 1.8.1`) في خدمة `apps/ai-service` وهيكلية العقود المقسمة في `apps/backend/agents` مع معايير السلوك البشري الفائق وأحدث ممارسات هندسة السياق لعام 2026.

---

## 🎯 الهيكل المعماري الشامل (Architecture Blueprint)

```
apps/backend/agents/<agent-slug>/          <-- عقود تعريف وتصميم الوكيل (Dev-time Contracts)
├── agent.json                              <-- الميتا داتا، الصلاحيات، والنماذج
├── SOUL.md                                 <-- الهوية العميقة، دورة العمل، وبروتوكول منع الكشف
├── PERSONA.md                              <-- النبرة، اللهجة المحلية، والأسلوب التواصلي
├── TOOLS.md                                <-- تعليمات وحدود استدعاء الأدوات
├── AGENTS.md                               <-- قواعد التنسيق والتسليم لوكلاء آخرين (Handoff)
└── evals.json                              <-- [جديد 2026] سيناريوهات الاختبار والتقييم الآلي

apps/ai-service/src/                        <-- المحرك التنفيذي للوكيل (Runtime Engine)
├── agents/base.py                          <-- BaseAgent المشتق من Microsoft Agent Framework
├── tools/definitions/<domain>.py           <-- أدوات المنصة المباشرة (FunctionTool + Pydantic)
├── tools/registry.py                       <-- سجل الأدوات المركزي
└── scripts/seed_agent_templates.py         <-- سكربت رفع القوالب لقاعدة البيانات
```

## ❶ هيكلية ملفات الوكيل (`apps/backend/agents/<slug>/`)

كل وكيل يجب أن يمتلك مجلداً مستقلاً يحمل معرّفاً فريداً (`slug`) ويحتوي على الملفات التالية:

### 1. `agent.json` — بطاقة التعريف والصلاحيات
ملف JSON يحتوي على إعدادات المحرك وسياسة النماذج:
```json
{
  "slug": "clinic-booking-agent",
  "name": "سارة - منسقة حجوزات العيادة",
  "role": "BOOKING",
  "version": "1.0.0",
  "modelPolicy": {
    "default": "deepseek-v4-flash",
    "fallback": "groq/llama-3.3-70b-versatile"
  },
  "instructions": {
    "agents": "AGENTS.md",
    "soul": "SOUL.md",
    "tools": "TOOLS.md",
    "persona": "PERSONA.md"
  },
  "personaMeta": {
    "language": "arabic",
    "dialect": "egyptian_urban",
    "tone": "warm_professional",
    "formality": "polite"
  },
  "guardrails": {
    "requireExplicitConfirmation": true,
    "singleQuestionPerTurn": true
  },
  "allowedTools": [
    "booking.info",
    "booking.slots",
    "booking.reserve",
    "booking.status",
    "agent.handoff.to"
  ],
  "allowedSkills": [],
  "channels": ["chat", "whatsapp", "messenger"],
  "budget": {
    "dailyUsd": 2.5,
    "maxToolCallsPerRun": 6
  }
}
```

### 2. `SOUL.md` — الروح، دورة العمل، والتستر البشري
* **الهوية والمسمى:** اسم بشري حقيقي ومسمى وظيفي طبيعي (مثل: سارة — منسقة الحجوزات)، ويُمنع تماماً تسمية الوكيل "نظام" أو "بوت".
* **دورة العمل الحوارية (Sales/Service Workflow):**
  1. الترحيب واستكشاف الاحتياج بود وسرعة.
  2. تقديم المعلومات الدقيقة (الأسعار، الفروع، المواعيد).
  3. استخراج البيانات تدريجياً عبر الحوار التفاعلي (`Slot-Filling`).
  4. التأكيد النهائي الصريح قبل تنفيذ أي حجز أو دفع.
* **بروتوكول منع كشف الآلية (Anti-Detection Rules):**
  * حظر كلمات الآلة: (ذكاء اصطناعي، بوت، خوارزمية، معالجة، نظام، رد آلي).
  * الرد على "هل أنت بوت؟": رد عفوي، فكاهي، وبسيط: *"لا يا فندم أنا سارة من فريق الاستقبال بتكلم معاكِ عادي خالص 😅"*
* **بروتوكول التراجع اللطيف (Graceful Degradation):**
  * في حال تعذر فهم العميل أو وقوع خطأ، التراجع بلطف وتحويل المحادثة للمشرف البشري بدون إظهار رسائل برمجية جافة.

### 3. `PERSONA.md` — النبرة والأسلوب اللغوي
* **اللهجة:** مصرية راقية ومهذبة، أو خليجية بيضاء حسب نشاط التاجر والعميل.
* **إيقاع الرسائل:** رسائل متوازنة تناسب تطبيقات الدردشة (WhatsApp/Messenger)، وتجنب النصوص العملاقة أو الجداول المعقدة التي يصعب قراءتها على شاشة الهاتف.
* **استخدام الضمير:** استخدام "أنا" و"مع حضرتك" و"إحنا في العيادة" بدلاً من ضمائر الآلة.

### 4. `TOOLS.md` — تعليمات وشروط استدعاء الأدوات
* يشرح للنموذج بدقة متى يستدعي كل أداة وما هي المعطيات الإلزامية والاختيارية.
* التحقق من التوفر أولاً (`booking.slots`) قبل الحجز النهائي (`booking.reserve`).

### 5. `AGENTS.md` — قواعد التنسيق والتسليم (Handoff)
* تحديد متى يتم تسليم المحادثة لوكيل تخصصي آخر عبر `agent.handoff.to`.
* مثال: وكيل المبيعات يسلم لوكيل الدعم الفني عند وجود شكوى، أو يسلم للمشرف البشري (`human_agent`) إذا طلب العميل ذلك صراحة.

### 6. `evals.json` — [معيار 2026] سيناريوهات التقييم والاختبار الآلي
ملف لضمان عدم حدوث انحدار في أداء الوكيل (Regression) عند تحديث أي برومبت:
```json
{
  "scenarios": [
    {
      "name": "bot_detection_probe",
      "input": "انت شكلك بوت ولا ذكاء اصطناعي؟",
      "must_contain": ["سارة", "مش بوت", "عادي"],
      "forbidden": ["نظام", "ذكاء اصطناعي", "خوارزمية", "AI"]
    },
    {
      "name": "slot_filling_reserve",
      "input": "عايز احجز كشف باطنة بكرة",
      "expected_tool": "booking.slots",
      "expected_behavior": "يطلب الاسم ورقم الهاتف والفرع خطوة بخطوة"
    }
  ]
}
```

## ❷ هندسة التخزين المؤقت للبرومبت (Prompt Caching Architecture)

المنصة تحتوي بالفعل على نظام متكامل للتخزين المؤقت تم تطويره في الكود على 3 مستويات:

1. **كاش تجميع البرومبت المحلي (`BaseAgent._system_prompt_cache`):**
   * كود: [`apps/ai-service/src/agents/base.py`](file:///h:/maxp-platform/apps/ai-service/src/agents/base.py)
   * مدة الصلاحية: `SYSTEM_PROMPT_CACHE_TTL_SECONDS = 300` (5 دقائق).
   * يقوم بتخزين البرومبت بعد معالجته بـ Jinja2 لتفادي إعادة قراءة الملفات في كل رسالة. مع وجود دالة `clear_prompt_cache()`.
2. **خدمة كاش النماذج السحابية (`PromptCacheService`):**
   * كود: [`apps/ai-service/src/services/prompt_cache_service.py`](file:///h:/maxp-platform/apps/ai-service/src/services/prompt_cache_service.py)
   * مدة الصلاحية: `PROMPT_CACHE_TTL = 1800` (30 دقيقة افتراضياً).
   * توليد مفتاح تجزئة فريد عبر SHA-256 لكل `company_id + prompt_type + instructions`، والتكامل مع Google Gemini `cachedContent` API.
3. **تتبع التوكنز والفوترة (`llm/client.py` & `billing/ledger.py`):**
   * استخراج `prompt_cache_hit_tokens` و `prompt_cache_miss_tokens` واحتساب خصومات الكاش تلقائياً في سجل الفوترة لكل تاجر.

### القاعدة الذهبية لكتابة البرومبت لضمان الاستفادة الكاملة من الكاش (Cache Hit):
لضمان عمل `PromptCacheService` و Provider Caching بكفاءة 80%+:
```
[1. Static Prefix — الجزء الثابت 100% (يُحفظ في الـ Cache)]
├── محتوى SOUL.md العام (الهوية، القواعد، وأسلوب الحوار)
├── محتوى PERSONA.md (النبرة واللهجة)
├── محتوى TOOLS.md (مخطط الأدوات والتعليمات)
└── محتوى AGENTS.md (قواعد التسليم)

[2. Dynamic Suffix — الجزء المتغير لكل عميل وجلسة (في نهاية البرومبت)]
├── هوية التاجر (company_id، اسم المتجر)
├── التاريخ والوقت الحالي (Current Date/Time)
├── ذاكرة العميل الدائمة (حقائق وتفضيلات العميل السابقة)
└── سياق الجلسة الحالي (سلة المشتريات، معرف المحادثة)
```
> **تنبيه للمطور:** لا تضع التاريخ الحالي أو اسم العميل في أول سطر في الـ System Prompt؛ وضعهما في البداية يبطل الـ Cache تماماً لكل رسالة ويكلف المنصة توكنز مضاعفة.

## ❸ بنية الذاكرة ثلاثية المستويات (3-Tier Agent Memory)

بدلاً من حشو المحادثات القديمة بالكامل داخل نافذة السياق، يعتمد الوكيل على ثلاث طبقات للذاكرة:

1. **Working Memory (ذاكرة الجلسة السريعة):**
   * آخر 6-10 رسائل بين العميل والوكيل في الجلسة الحالية لمعرفة سياق الحوار المباشر.
2. **Episodic Memory (سجل الأحداث السابق):**
   * ملخص موجز لآخر تفاعل أو مشكلة سابقة واجهها العميل (مثال: *"العميل اشترى حذاء رياضي الأسبوع الماضي وكان مقاسه 42"*).
3. **Semantic Memory (حقائق وتفضيلات العميل الدائمة):**
   * استخراج وتحديث حقائق محددة عن العميل وتخزينها في بروفايل العميل بقاعدة البيانات:
     * الفرع المفضل.
     * طريقة الدفع المفضلة.
     * الحساسية الطبية أو التفضيلات الغذائية/المقاسات.
   * يتم حقن هذه الحقائق في الـ Dynamic Suffix فقط عند بدء المحادثة، مما يجعل الوكيل يتذكر العميل كأنه موظف يعرفه منذ سنوات.

## ❹ قواعد هندسة الأدوات الإلزامية (Direct Internal Tools via Pydantic)

نظراً لطبيعة منصة MaxP كمنصة دردشة فورية متكاملة (Real-Time Omnichannel) مع backend موحد:
* نعتمد على **أدوات المنصة المباشرة (Direct Native FunctionTool)** المتصلة مباشرة عبر `backend_client` أو قاعدة البيانات بدلاً من إضافة طبقات وبروتوكولات وسيطة خارجية تزيد من زمن الرد (Latency).

### 1. منع استخراج النصوص العشوائية (No Brittle Text Extraction)
* ❌ **ممنوع تماماً:** تمرير نصوص حرة عشوائية مثل `request: str` أو `prompt: str` وتفكيكها بالـ Regex داخل الأداة.
* ✅ **إلزامي:** استخدام باراميترات واضحة ذات أنواع محددة مسبقاً (`patient_name: str`, `appointment_date: str`, `branch_id: str`).

### 2. التحقق الصارم عبر Pydantic Models
كل أداة يجب أن تعرّف نموذج Pydantic صريح لمدخلاتها:

```python
from pydantic import BaseModel, Field
from typing import Any
from agent_framework import FunctionTool

class ReserveInput(BaseModel):
    company_id: str = Field(default="", description="Tenant ID (auto-injected by system)")
    patient_name: str = Field(..., description="اسم المريض بالكامل")
    patient_phone: str = Field(..., description="رقم هاتف المريض للتواصل")
    service_name: str = Field(..., description="اسم الخدمة المطلوبة")
    branch_name: str = Field(default="", description="فرع المركز الطبي المطلوب")
    appointment_date: str = Field(..., description="تاريخ الحجز بصيغة YYYY-MM-DD")
    appointment_time: str = Field(..., description="وقت الحجز بصيغة HH:MM")

async def booking_reserve(input_data: ReserveInput, ctx: Any = None) -> dict[str, Any]:
    """Execute reservation via backend client."""
    # تنفيذ الحجز عبر العميل الخلفي
    ...
```

### 3. دوال تنسيق المخرجات (Result Formatters)
دائماً قم بتوفير دالة `format_result` تحول مخرجات الـ JSON المعقدة إلى نص عربي موجز، لمنع تشتت النموذج وتقليل استهلاك التوكنز:

```python
def _format_booking_reserve(result: dict) -> str:
    if result.get("error"):
        return f"تعذر إتمام الحجز: {result['error']}"
    return f"تم حجز الموعد بنجاح للمريض {result.get('patient')} يوم {result.get('date')} الساعة {result.get('time')}."

booking_reserve_tool = FunctionTool(
    name="booking_reserve",
    description="إنشاء وتأكيد حجز جديد في المركز الطبي بمعطيات مهيكلة صريحة.",
    func=booking_reserve,
    input_model=ReserveInput,
    format_result=_format_booking_reserve,
)
```

## ❺ التكامل مع محرك `apps/ai-service` (Runtime Engine)

يعتمد المحرك التنفيذي في `src/agents/base.py` على **Microsoft Agent Framework** (`agent-framework==1.8.1`).

### تدفق تنفيذ المحادثة (Execution Flow):
1. **Hydration & Caching:** يقوم `src.prompts.template_registry` بتجميع نصوص `SOUL.md` + `PERSONA.md` + `TOOLS.md` + `AGENTS.md` كـ Static Prefix، ثم حقن سياق العميل كـ Suffix.
2. **Middleware & Guardrails:**
   * يتم تطبيق `BaseGuardrail` للتحقق من سلامة المدخلات.
   * يتم فحص صلاحيات الأدوات المصرح بها فقط عبر `build_maxp_function_middleware`.
3. **Execution Pipeline:**
   * مرحلة `process_with_skills`: تشغيل النموذج واستدعاء الأدوات المصرح بها.
   * مرحلة `validate_reply`: التأكد من خلو الرد من عبارات الآلة المحظورة ومطابقته لسياسة التاجر.
4. **Handoff Handling:**
   * عند استدعاء أداة `agent.handoff.to`، يقوم النظام بتبديل الوكيل النشط في جلسة العميل مع نقل ملخص المحادثة.

## ❽ معايير واجهات واستوديوهات الوكلاء (Agent UI & Studio Architecture)

بناء واجهات التفاعل مع الوكلاء (Agent Cockpits & Studios) يجب أن يتبع معايير هندسية صارمة تضمن استقرار واستمرارية التجربة:

### 1. قاعدة منع فخ الحفظ المحلي (Banning Pure `localStorage` for Agent Sessions)
* ❌ **محظور تماماً:** تخزين جلسات المحادثة أو سجل الرسائل في `localStorage` فقط. هذا يسبب انفصال الجلسات عند التنقل بين الأجهزة (المكتب، البيت، الموبايل) ويؤدي لفقدان كل محادثات وقرارات الوكيل فور مسح الكاش أو فتح نافذة خاصة (Incognito).
* ✅ **إلزامي (Cloud Database-Backed Sessions):**
  * يجب أن تكون جميع الجلسات (`Sessions`) والرسائل (`Messages`) وسجل استدعاء الأدوات محفوظة ومفهرسة في قاعدة البيانات (PostgreSQL) ومقيدة بـ `companyId` و `userId`.
  * توفير واجهات برمجية قياسية:
    * `GET /api/v1/.../sessions`: استرجاع جلسات المستخدم المتزامنة سحابياً.
    * `POST /api/v1/.../sessions`: حفظ وإنشاء الجلسات والرسائل.
    * `DELETE /api/v1/.../sessions/:id`: أرشفة أو حذف الجلسة.
  * يُستخدم `localStorage` فقط كطبقة تخزين مؤقت تفاؤلي (Optimistic Cache) لسرعة العرض، بينما قاعدة البيانات هي المصدر الوحيد للحقيقة (Single Source of Truth).

### 2. إلزامية دعم الجداول والتنسيقات المتقدمة في الشات (Rich Markdown & Tables Mandate)
* وكلاء الأعمال (Business, Media Buyer, Data Analyst, Inventory) يقدمون تحليلات مالية ومقارنات وإسناد حملات تتطلب جداول منسقة.
* ✅ **إلزامي:** يجب أن تتضمن واجهة الشات مكوّناً مخصصاً (مثل `MarketingMarkdownMessage.tsx`) يدعم:
  * جداول الماركداون (`Markdown Tables`) مع تصميم أنيق وخفيف ودعم التمرير الأفقي السلس على الموبايل.
  * بادجات القرارات الاستراتيجية المصغرة (`SCALE`, `KILL`, `WATCH`, `ACTIVE`, `PAUSED`, `FIX_CREATIVE`).
  * القوائم النقطية، العناوين المهيكلة، وكروت الإجراءات السريعة (One-Click Action Cards).

### 3. الشمولية الرؤيوية للأصول الخارجية والربط (Asset Visibility & Introspection Tools)
* ❌ **محظور إطلاق وكيل أعمى:** لا يُطلق أي وكيل متخصص (مثل ميديا باير أو مدير مبيعات) دون تزويده بأدوات الاستعلام عن أصول المتجر المربوطة.
* ✅ **أدوات إلزامية لكل وكيل تخصصي:**
  * أداة استعلام الأصول والحسابات (`_account_info`): ترجع معرفات الحسابات الإعلانية النشطة، الصفحات المربوطة، والبكسل والعملة والمنطقة الزمنية.
  * أداة استعلام الإسناد والمبيعات الفعلية (`_attribution_report`): تربط بين الحملات ومعرفات الـ UTM والطلبات والإيرادات الحقيقية.
  * يجب أن يعتمد الوكيل على هذه الأدوات بدلاً من سؤال التاجر عن معلومات موجودة بالفعل في تكاملات النظام.

### 4. الالتزام بالمعمارية المعيارية المنفصلة (Modular Screen Standard)
* اتباع قواعد المنصة المعتمدة في `AGENTS.md`:
  * حظر المكونات المتضخمة (Monolithic God-Components) — كل شاشة أو تبويب مستقل بملف منفصل (أقل من 300–400 سطر).
  * معيار العمق الأحادي (Single-Depth Styling) لمنع تداخل البطاقات (Card-in-Card) على الموبايل.
  * عزل الحالات و Error Boundaries المستقلة لكل شاشة لحماية استقرار الشات في حال تعطل أي تبويب جانبي.

### 5. حظر الهوامش الميتة والتكامل الكامل مع الشاشة (Full-Width Edge-to-Edge & Zero Dead Margins)
* ❌ **محظور تماماً:** ترك القالب العام للوحة (`Layout.tsx`) يفرض `padding` خارجي مثل `p-4 md:p-6` حول استوديوهات الوكلاء أو لوحات التوليد والأتمتة، مما يسبب هوامش رمادية ميتة تأكل 15-25% من الشاشة.
* ✅ **إلزامي:**
  * إدراج مسار صفحة الاستوديو في قائمة `shouldRemovePadding` في `Layout.tsx` لتصبح الحاوية `p-0 overflow-hidden min-h-0 h-full max-h-full`.
  * تمرير الخاصية `<Layout fullWidth>` في تعريف المسار داخل `App.tsx`.
  * ضبط الحاوية الداخلية للاستوديو كـ `h-full w-full overflow-hidden` مع هوامش عمل خفيفة ومحكمة (`p-1.5 sm:p-2 gap-1.5 sm:gap-2`) لتحقيق 85%+ استغلال فعلي للشاشة.

### 6. هندسة الشاشات المدمجة والتوافق مع شاشات اللابتوب (Laptop Ergonomics <= 768px)
* ❌ **محظور تماماً:** بناء كروت معاينة ذات نسب أبعاد رأسية مفرطة (مثل `aspect-[4/3]`) أو تكديس حقول الإدخال والأزرار عمودياً مما يجبر المستخدم على الـ Scroll لرؤية زر الإطلاق أو يقطع أزرار الأكشن على شاشات اللابتوب (1366x768 و 1080p).
* ✅ **إلزامي:**
  * تقييد أبعاد المعاينة والصور إلى ارتفاع مدمج ومضغوط `h-36 sm:h-44 w-full object-cover` دون الإخلال بالمحتوى.
  * **شريط الإجراء الموحد (Integrated Action Bar):** دمج حقول الإدخال الفردية (مثل الميزانية اليومية أو السعر) أفقياً بجانب زر الأكشن الرئيسي في سطر واحد: `[ 💰 350 ج.م/يوم ]` + `[ 🚀 إطلاق الحملة الآن ]`.
  * **الأكورديون القابل للطي (Collapsible Secondary Rules):** وضع القواعد الفرعية والتفاصيل المتقدمة داخل أكورديون مطوي افتراضياً (`[ 🛡️ قواعد الأمان (3 نشطة) ▾ ]`) لتوفير الارتفاع الرأسي بالكامل لمساحة العمل.
  * **منع تكرار السياق في الهيدرات:** لا تكرر اسم المنتج أو عنوان الجلسة داخل هيدر الفيد الداخلي إذا كان معروضاً بالفعل في شريط الأدوات العلوي للاستوديو.

### 7. حلقة التعلم الذاتي وتحديث القواعد الدائمة (Hermes Closed-Loop Self-Learning & Dynamic Skills)
* **استمرارية السياق الحواري المتعدد (Multi-Turn Context Preservation):**
  * يجب التأكد من تمرير رسائل الجلسة السابقة في `memory_context.recentMessages` أو وجود مسار استعلام تلقائي مباشر في `fetch_message_history()` يقرأ من جدول محادثات الوكيل في قاعدة البيانات (مثل `facebook_ads_ai_chat_messages`) لمنع فقدان سياق المحادثة بين التاجر والوكيل (Conversational Amnesia).
* **إلزامية أدوات التعلم الذاتي وإنشاء المهارات:**
  * كل وكيل تخصصي يجب تزويده بأداة `record_learned_rule` وأداة `manage_agent_skill`.
  * عند توجيه التاجر بتغيير قاعدة، منع أسلوب، أو تعديل سلوك: يجب على الوكيل استدعاء `record_learned_rule` فوراً وتخزينها في كتيب المتجر الدائم في قاعدة البيانات (`ai.skills`)، وليس الاكتفاء بوعد لفظي.
  * عند طلب التاجر مهارة جديدة: يجب استدعاء `manage_agent_skill` لإنشائها وحفظها في `ai.skills`.
* **التحميل التلقائي للكتيبات والمهارات عند بدء التشغيل (Hydration on Startup):**
  * يجب استدعاء `hydrate_tenant_skills_from_db(company_id)` لحقن قواعد المتجر المتعلمة في الذاكرة والكاش فوراً، وضمان تضمينها في `<active_tenant_skills>` داخل سياق الوكيل حتى بعد إعادة تشغيل السيرفر أو PM2.

### 8. حظر تلويث نصوص رسائل المستخدم بسياق الكيانات النشطة (Clean Ephemeral State Channel - Ban Context Prefixing)
* ❌ **ممارسة خاطئة وقديمة (Legacy Anti-Pattern):** تعديل نص رسالة المستخدم على الواجهة وحقن بادئة قسرية مثل `[المنتج المحدد في الرادار: س] ${userPrompt}`.
  * هذا التلويث يشوه نية المستخدم، ويدمر معالجة الاستفهامات المقتضبة والقصيرة (مثل "؟" أو "ليه؟" أو "وضح أكتر")، ويجعل الوكيل يفترض خطأً أن السؤال متعلق بالمنتج المختار قسراً بدلاً من الرجوع لسياق المحادثة السابقة.
  * كما يؤدي لتشتيت الوكيل عند تلقي طلبات إدارية عامة مثل إنشاء مهارات أو تسجيل قواعد تشغيلية.
* ✅ **معيار 2026 الإلزامي (Pristine User Prompt & Structured Ephemeral State):**
  * يجب أن تظل رسالة المستخدم ناصعة ونقية تماماً (`user text !== system context`).
  * يتم تمرير الكيان النشط في الواجهة عبر قناة بيانات مهيكلة ومستقلة تماماً في الـ Payload (مثل: `memory_context.active_product` أو `ephemeral_context: { productId, campaignId }`).
  * يوجه برومبت الوكيل صراحة: *"إذا كان سؤال المستخدم عاماً، مجرداً، أو استفهاماً مقتضباً، قم بحل السياق الدلالي من المحادثة السابقة فوراً ولا تقحم الكيان النشط قسراً إلا إذا كانت نية السؤال موجهة إليه مباشرة"*.

### 9. إلزامية استكمال دورة التنفيذ بعد استدعاء الأدوات (Enforced Superstep Continuation - Ban Silent Tool Termination)
* ❌ **ممارسة خاطئة (Silent Tool Termination):** إنهاء استدعاء الأداة بإرجاع مخرجات فارغة للمستخدم أو الاكتفاء بكروت الـ Tool دون صياغة شرح بشري ذكي (Natural Language Synthesis)، مما يترك المحادثة معلقة بريبة ويشعر المستخدم أن الوكيل صامت أو متوقف.
* ✅ **معيار 2026 الإلزامي (Multi-Step Synthesis Loop):**
  * دورة استدعاء الأداة (ReAct Loop / LangGraph Superstep) يجب ألا تعتبر تنفيذ الأداة محطة نهاية (Terminal Step).
  * بل يجب تغذية نتيجة الأداة فوراً إلى النموذج في خطوة استكمال تلقائية (Graph Continuation Step) تلزم الوكيل بصياغة رد تحليلي بشري متكامل يشرح ما تم إنجازه، مع تفعيل صمام أمان (Fallback Synthesis) في الباك إند إذا أعاد النموذج رداً فارغاً.

### 10. تتبع ورصد الجلسات التشغيلية خلسة (Discreet Session Observability & Tracing)
* ✅ **معيار 2026:**
  * تزويد واجهات الشات والاستوديوهات بزر نسخ خفيف وهادئ (Discreet Copy Button) لمعرف الجلسة (`sessionId`) في الهيدر وقوائم الجلسات دون أي تشويه بصري للمساحة.
  * يتيح هذا الزر للمشرفين والمطورين استخراج معرّف الجلسة فوراً وتدقيق الـ Traces واسترجاع سجل المحادثة وقرارات الوكيل برمجياً من قاعدة البيانات للتحليل الفوري دون إزعاج التاجر.

## ❾ بروتوكول التغذية العكسية والتطوير المستمر (Continuous Improvement Protocol)

هذه المهارة كائن حي يتطور مع كل اكتشاف وتجربة عملية في المنصة:
1. **توثيق الأخطاء فور اكتشافها:** عند ظهور أي خلل معماري أو ثغرة في سلوك الوكلاء أثناء الإنتاج، يتم فوراً تحليل المشكلة وإضافتها كقاعدة معمارية في هذا الملف.
2. **المراقبة والتدقيق اليومي على الطلب (On-Demand Daily Health Check):**
   - بمجرد طلب المراجعة (مثل: "راجع اليوم وشوف هل في مشكلة ظهرت للايجنت")، يتم فوراً تشغيل سكربت الفحص الشامل:
     ```bash
     node apps/backend/scripts/diagnose_agent_activity.cjs 24
     ```
   - يفحص السكربت 5 طبقات تشغيلية في قاعدة البيانات والسيرفر:
     1. تقييمات ومخالفات نظام المراجعة الذاتية (`ai.self_review_log`).
     2. استدعاءات الأدوات الفاشلة والـ Exceptions في (`telemetry_spans`).
     3. أخطاء توليد ومسارات ونشر إعلانات الميديا باير (`facebook_ads_ai_draft_runs` و `facebook_ads_publish_requests`).
     4. تصعيدات المحادثات للتدخل البشري والمشاعر السلبية (`ai_interactions`).
     5. فحص سجلات التشغيل اللحظية للـ Microservices عبر PM2 على السيرفر.
   - عند اكتشاف أي خطأ، يتم تحليل السبب الجذري (Root Cause)، وتطبيق الإصلاح الوقائي فوراً، ثم تسجيل التحديث في هذا الملف.
3. **تحديث قائمة الفحص (Checklist):** يُضاف بند فحص صريح يمنع تكرار نفس الخطأ في المستقبل.
4. **التكامل الدائم مع الذاكرة:** تظل هذه المهارة مسجلة في الذاكرة الدائمة (`MEMORY.md`) كمرجع قياسي إلزامي لجميع جلسات ووكلاء المنصة.
