### 1.2 مسألة مسارات التنفيذ المحددة مسبقاً (Deterministic Paths)

**المكان:** `backend/services/aiAgent/CEOAgent.js:200-350`

**المشكلة:**
الكود يحتوي على سلسلة `if/else if/else` كبيرة تحدد ماذا سيفعل الوكيل بناءً على النتيجة من `relevanceEngine`:
```javascript
if (intentResult.marketingCampaign >= 0.7) {
  executionPlan = [
    'create_facebook_campaign',
    'launch_ad_group',
    'write_ad_copy',
    'generate_visuals',
    'start_campaign',
    'generate_report'
  ];
}
```

**النتيجة:**
إذا كانت درجة `marketingCampaign >= 0.7`، النظام **سيعمل نفس الـ 6 خطوات بالضبط** بغض النظر عن:
- ماذا قال المستخدم بالضبط؟
- هل يريد تخصيصاً معيناً؟
- هل هناك بيانات متاحة مسبقاً؟

**مثال:** المستخدم يقول "فقط أنشئ الحملة ولا تضيف إعلانات بعد"، النظام سيضيف الإعلانات تلقائياً.

## 2. الحلول الحديثة لعام 2026 (Research-Based)

### 2.1 حل مشكلة تصنيف النوايا (Intent Classification)

**الحل الحديث:** **Tool Calling for Intent Classification (June 2026)**

**المصدر:** بحث حديث 21 مايو 2026 - DEV.to

**الفكرة:**
بدلاً من استخدام مطابقة كلمات مفتاحية، نُعرف كل "النية" كـ "أداة" (Tool) مع مخطط JSON خاص بها، ثم نُجبر النموذج على اختيار الأداة المناسبة باستخدام `tool_choice: "required"`.

**مثال تطبيقي:**

```typescript
// 1. نُعرف النوايا كـ Tools (وليس كلمات مفتاحية)
const marketingCampaignTool = {
  type: "function",

    parameters: {
      type: "object",
      properties: {
        platform: {
          type: "string",
          enum: ["facebook", "instagram", "tiktok", "google", "snapchat"],
          description: "المنصة التي سيتم إنشاء الحملة عليها"
        },
        objective: {
          type: "string",
          description: "هدف الحملة (مثال: زيادة المبيعات، زيادة التفاعل)"
        },
        needsClarification: {
          type: "boolean",
          description: "هل نحتاج لسؤال المستخدم المزيد؟"
        }
      },
      required: ["platform", "needsClarification"]
    }
  }
};

const marketResearchTool = {
  type: "function",
  function: {
    name: "conduct_market_research",
    description: "عندما يريد المستخدم بحثاً عن السوق أو تحليل منافسين",
    parameters: {
      type: "object",
      properties: {
        targetAudience: { type: "string" },
        competitors: { type: "array", items: { type: "string" } },
        needsClarification: { type: "boolean" }
      }
    }
  }

// 2. نُجبر النموذج على اختيار أداة (لا ردود نصية غير منضبطة)
const response = await openai.chat.completions.create({
```

**لماذا هذا أفضل من الكلمات المفتاحية عام 2026؟**
| الطريقة القديمة (Keywords) | الطريقة الحديثة (Tool Calling) |
|---|---|
| تعتمد على تطابق نصي مباشر | يفهم المعنى والسياق |
| مشاكل التداخل (نفس الكلمة في عدة مصفوفات) | النموذج يختار الأداة الأنسب بناءً على الوصف |
| لا يفهم اللباقة (مثال: "بإمكانك مساعدتي في...") | يفهم جميع أنماط اللغة |
| لا يمكنه تحديد ما هو "مفقود" من المعلومات | يحدد تلقائياً `needsClarification: true` |

**متطلبات التقنية:**
- OpenAI API compat (Groq يدعم هذا بالكامل)
- ملف definition لكل Intent بصيغة JSONSchema
- `tool_choice: "required"` لإجبار الـ structured output

### 2.2 حل مشكلة مسارات التنفيذ المحددة مسبقاً

**الحل الحديث:** **LLM-Native Orchestration + LangGraph Supervisor (2026)**

**المصدر:** بحث 28 مارس 2026 - ASOasis

**الفكرة:**
بدلاً من تحديد الخطوات مسبقاً في الكود (`if/else if/else`)، نسمح للـ LLM نفسه أن يخطط الخطوات بناءً على:
1. طلب المستخدم
2. الأدوات المتاحة
3. السياق
4. النتائج السابقة (ردود الأدوات)

**نمط التوصية لهندسة عام 2026:**

```
┌─────────────────────────────────────────────────────────┐
│                   🧠 Supervisor Agent                     │
│  (النموذج الكبير - gpt-oss-120b أو Claude أو Groq)     │
├─────────────────────────────────────────────────────────┤
│  المسؤوليات:                                              │
│  1. فهم طلب المستخدم (Intent Recognition)               │
│  2. تقييم الأدوات المتاحة (Capabilities Assessment)     │
│  3. تخطيط الخطوات (Dynamic Planning)                     │
│  4. تنفيذ الأداة (Tool Execution)                        │
│  5. فحص النتيجة (Result Validation)                      │
│  6. تكرار أو إنهاء (Loop or Finish)                      │
└─────────────────────────────────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Tool 1       │  │ Tool 2       │  │ Tool N       │
│ (Facebook)   │  │ (Market      │  │ (Report)     │
│ Campaign     │  │ Research)    │  │ Generator    │
└──────────────┘  └──────────────┘  └──────────────┘
```

**مثال عملي باستخدام LangGraph (الصياغة في JS):**

```typescript
// هذا مثال مبسط لمفاهيم LangGraph
// يمكن تطبيق نفس الفكرة بدون مكتبة خارجية

const llm = new OpenAI({
  apiKey: process.env.GROQ_API_KEY,
  baseURL: "https://api.groq.com/openai/v1",
  model: "openai/gpt-oss-120b"
}).bindTools([facebookTool, researchTool, reportTool]);

// الحالة التي يشاركها جميع الخطوات
interface AgentState {
  messages: BaseMessage[];
  plan: string[];
  executedTools: string[];
  results: Record<string, any>;
  needsClarification: boolean;
  clarificationQuestions: string[];
}

// الخطوة 1: المخطط (Planner) - يختار الأداة التالية أو ينهي
const plannerNode = async (state: AgentState): Promise<AgentState> => {
  const response = await llm.invoke([
    SystemMessage(
      `أنت مدير تنفيذي رقمي في شركة MaxP. مهمتك:
       1. افهم طلب المستخدم
       2. اختر الأداة المناسبة من قائمة الأدوات
       3. إذا كانت المعلومات غير كافية، اضف needsClarification: true
       4. إذا انتهى كل شيء، أجب المستخدم بلغة عربية طبيعية.
       
       القاعدة الذهبية: لا تختار أداة إلا إذا كنت متأكداً من المعلومات المطلوبة لها.`
    ),
    ...state.messages
  ]);

  // ✅ هنا السحر: النموذج يقرر بنفسه ماذا سيفعل بعد
  // إما: يستدعي أداة (tool_calls)
  // أو: يرد على المستخدم (content مباشر)

  return {
    ...state,
    messages: [response]
  };
};

// الخطوة 2: منفذ الأدوات (Tool Executor)
const toolNode = new ToolExecutor({ tools: availableTools });

const executeTools = async (state: AgentState): Promise<AgentState> => {
  const lastMessage = state.messages[state.messages.length - 1];
  if ("tool_calls" in lastMessage && lastMessage.tool_calls.length > 0) {
    const toolOutputs = await toolNode.batch(lastMessage.tool_calls);
    return {
      ...state,
      messages: toolOutputs,
      executedTools: [...state.executedTools, lastMessage.tool_calls[0].name],
      results: {
        ...state.results,
        [lastMessage.tool_calls[0].name]: toolOutputs[0].content
      }
    };
  }
  return state;
};

// الخطوة 3: التوجيه (Router) - يحدد أين نذهب بعد
const routeAfterPlanner = (state: AgentState): "tools" | "end" => {
  const lastMessage = state.messages[state.messages.length - 1];
  if ("tool_calls" in lastMessage && lastMessage.tool_calls.length > 0) {
    return "tools"; // ننفذ الأداة ثم نعود للمخطط
  }
  return "end"; // ننهي المحادثة
};

// بناء الرسم البياني (Graph)
const workflow = new StateGraph(AgentState)
  .addNode("planner", plannerNode)
  .addNode("tools", executeTools)
  .addEdge(START, "planner")
  .addConditionalEdges("planner", routeAfterPlanner)
  .addEdge("tools", "planner"); // ← حلقة: أداة → مخطط → أداة → إلخ

const CEOAgent = workflow.compile();
```

**مقارنة بين الطريقتين:**

| الطريقة القديمة (Deterministic Paths) | الطريقة الحديثة (LLM-Native Loop) |
|---|---|
| مسارات ثابتة في الكود | مسارات ديناميكية يقررها النموذج لكل حالة |
| `if (intent > 0.7) → الخطوات 1,2,3,4,5,6` | `while (not_done) { النموذج يختار الأداة التالية أو ينهي }` |
| لا يتكيف مع نتائج الأدوات | يتكيف: إذا فشلت الأداة، قد يغير المسار |
| لا يسأل توضيحاً | يسأل تلقائياً إذا `needsClarification: true` |
| مثال: "اعمل حملة" → دائماً 6 خطوات | مثال: "اعمل حملة" → يسأل: "أي منصة؟ أي هدف؟ ميزانية؟" |

**القاعدة الذهبية لعام 2026:**
> "لا تحدد المسار في الكود. خصّص الحلقات (ReAct loops) ودع النموذج يقرر في كل خطوة ماذا سيفعل بعد بناءً على النتائج التي حصل عليها."

**النمط الموصى به:** **ReAct + Tool Calling Loop**

كل تكرار:
1. النموذج يقرأ الرسائل السابقة
2. يختار إما: استدعاء أداة (مع معالجاتها) أو إنهاء بالرد النهائي
3. إذا استدعى أداة: ننفذها نحن في الكود ونضيف النتيجة إلى الرسائل
4. نعود للخطوة 1

### 2.3 حل مشكلة قوالب الردود الثابتة

**الحل الحديث:** **Context-Aware LLM Response Generation (2026)**

**الفكرة:**
بدلاً من استخدام قوالب نصية ثابتة، نرسل البيانات النهائية إلى النموذج مع تعليمات واضحة حول:
1. **الشخصية:** كيف يتحدث وكيل المدير التنفيذي؟
2. **اللغة:** عربية فصحى؟ عامية؟ مخلوطة؟ (بناءً على ما استخدمه المستخدم)
3. **التنسيق:** هل يحتاج إلى نقاط؟ جداول؟ ملخص؟
4. **السياق:** ماذا قال المستخدم سابقاً؟

**مثال على ملف تعريف شخصية الوكيل (CEO Persona):**

```typescript
const ceoPersonaPrompt = `
أنت المدير التنفيذي الرقمي لشركة MaxP.

# شخصيتك:
- واثق但 لا متكبر
- يركز على النتائج والأرقام
- يجيب باللغة التي يستخدمها المستخدم (عربية إذا كان المستخدم عربي)
- يختصر لكن لا يفوت التفاصيل المهمة
- إذا كان هناك مشكلة، يقترح حلولاً وليس مجرد وصف للمشكلة

# تنسيق الردود:
- استخدم رموز توضيحية (✅ ❌ 📊 📈) بشكل معتدل
- استخدم نقاط عند تعداد الأمور
- إذا كانت النتائج تحتوي على أرقام، ركّز على أهمها
- إذا كان هناك "توقع" أو "تنبؤ"، اذكر صراحة أن هذا تخمين وليس حقيقة

# لغة الرد:
- إذا كتب المستخدم بالعربية، أجب بالعربية
- إذا كتب المستخدم بالإنجليزية، أجب بالإنجليزية
- لا تترجم كلمات مثل "Facebook" أو "Campaign" إذا كانت شائعة في المجال

# مثال على رد جيد:
✅ حملتك على الفيسبوك جاهزة!

📊 ملخص الإعدادات:
• الميزانية اليومية: 150 ريال
• الهدف: زيادة المبيعات
• الجمهور: الرياض (18-45 سنة)

🚀 هل تريد مني تشغيلها الآن أم تعديل شيء؟

# ماذا لا تفعل:
- لا تستخدم جملاً فارغة مثل "أنا سعيد بمساعدتك"
- لا تكرر المعلومات أكثر من مرة
- لا تضف تفاصيل تقنية غير مفهومة للعميل العادي
- لا تعد بتأكيدات حول نتائج الحملات (المستقبل غير مؤكد)
`;
```

**كيفية إنشاء الرد النهائي دون قوالب ثابتة:**

```typescript
const oldWay = campaignCompleteTemplate(campaignName, metrics);
```

**لماذا هذا أفضل عام 2026؟**
| القوالب الثابتة | التوليد الديناميكي بـ LLM |
|---|---|
| نفس الرد لكل مستخدم | رد مخصص لكل سياق وكل مستخدم |

## 3. مخطط الهجرة المقترح (Migration Roadmap)

### المرحلة 1: الإصلاح السريع (يوم 1-2)

**الهدف:** إزالة مشاكل التداخل الكبيرة في الكلمات المفتاحية

**الإجراءات:**
1. قم بمراجعة `agentIntentRelevanceService.js`
2. إزالة أو تقليل الكلمات العامة مثل "اعمل" و "إنشاء" من جميع المصفوفات
3. اجعل الكلمات المفتاحية أكثر تحديداً لكل Intent
4. أضف وزناً (Weighting): الكلمات في المصفوفة الأولى لها وزن أعلى

**مثال على التحسين:**
```javascript
// قبل (القديم):
marketingCampaignKeywords: ['حملة', 'اعمل', 'إنشاء', 'إعلان', 'تسويق', ...]

// بعد (المحسن):
marketingCampaignKeywords: [
  // عالية الوزن (تحديدية جداً):
  { word: 'حملة تسويقية', weight: 100 },
  { word: 'facebook campaign', weight: 100 },
  { word: 'حملة على الفيسبوك', weight: 100 },
  
  // متوسطة الوزن:
  { word: 'حملة', weight: 50 },
  { word: 'إعلانات', weight: 40 },
  
  // منخفضة الوزن (عامة):
  { word: 'اعمل', weight: 10 },
  { word: 'إنشاء', weight: 10 },
]
```

### المرحلة 3: تنفيذ ReAct Loop (يوم 6-10)

**الهدف:** إزالة الـ `if/else if` الكبيرة وجعل التنفيذ ديناميكياً

**الإجراءات:**
1. تعريف جميع الأدوات الفعلية بصيغة OpenAI Function calling
2. بناء الحلقة الأساسية: `while → LLM chooses tool → execute → repeat`
3. إضافة حالة `needsClarification` للأسئلة التوضيحية
4. كتابة اختبارات للسيناريوهات الغامضة

**الهيكل المنطقي للـ ReAct Loop:**

```typescript
interface CEOAgentConfig {
  model: string;
  tools: ToolDefinition[];
  systemPrompt: string;
  maxIterations: number; // مثال: 10 كحد أقصى للحلقة
}

class DynamicCEOAgent {
  private config: CEOAgentConfig;
  private state: AgentState;

  async execute(userMessage: string): Promise<string> {
    this.state.messages.push({ role: "user", content: userMessage });
    let iterations = 0;

    while (iterations < this.config.maxIterations) {
      const response = await this.callLLMWithTools();

      // حالتان محتملتان فقط:
      
      if (response.tool_calls && response.tool_calls.length > 0) {
        // الحالة 1: النموذج يريد استدعاء أداة
        const toolResult = await this.executeTool(response.tool_calls[0]);
        this.state.messages.push({
          role: "tool",
          tool_call_id: response.tool_calls[0].id,
          content: JSON.stringify(toolResult)
        });
        iterations++;
        continue;
      } else {
        // الحالة 2: النموذج أعطى رداً نهائياً (لا يريد أدوات أخرى)
        return response.content;
      }
    }

    return "عذراً، تجاوزت الحد الأقصى للخطوات. هل يمكنك تبسيط طلبك؟";
  }
}
```

**القاعدة الذهبية في هذه المرحلة:**
> "لا توجد `else if (intent === X) → الخطوات الثابتة` في الكود. الوحيد الذي يقرر الخطوات هو النموذج في كل تكرار بناءً على ما حدث حتى الآن."

### الفئة 1: الأساسيات (Basic Scenarios)

#### 1.1 فهم اللهجات العربية المختلفة (BASIC-001)
**السيناريو:** اختبار فهم اللهجات: مصري، فصحى، خليجي، شامي

**مثال على المدخلات:**
- "عايز اعمل منتج جديد" (مصري)
- "أريد إنشاء منتج جديد" (فصحى)
- "ابغى اسوي منتج جديد" (خليجي)
- "بدي اعمل منتج جديد" (شامي)

**الحالة الحالية في الكود:**
- `agentIntentRelevanceService.js` يعتمد على **كلمات مفتاحية محددة**
- الكلمات مثل "عايز"، "ابغى"، "بدي" **غير موجودة** في مصفوفات الكلمات المفتاحية
- الكلمة الوحيدة المشتركة قد تكون "منتج" أو "اعمل"

**المشكلة المتوقعة:**
- الصيغ باللهجات المختلفة قد **لا يتم تصنيفها بشكل صحيح** لأن الكلمات غير موجودة في الـ hints
- قد تضطر للاعتماد فقط على كلمات مثل "منتج" إذا كانت موجودة

**التوصية الحديثة 2026:**
- **لا تحل هذه المشكلة بإضافة المزيد من الكلمات المفتاحية** (لأن اللهجات لا حصر لها)
- الحل الصحيح هو **Tool Calling for Intent Classification**
- النموذج الحديث (مثل gpt-oss-120b على Groq) **يفهم جميع اللهجات بشكل طبيعي** بدون أي كلمات مفتاحية
- فقط عرّف الأداة بـ `description` جيد، واترك للنموذج يفهم الصياغة

#### 1.2 الأخطاء الإملائية الشائعة (BASIC-002)
**السيناريو:** "عايز اضيف منتج" vs "عايز اضيف منتج" (ضاد/زاد، طاء/ظاء، دال/ذال)

**الحالة الحالية:**
- Keyword-based matching **حساس جداً للأخطاء الإملائية**
- إذا كانت الكلمة في الـ hint هي "اضيف" والمستخدم كتب "اضيف" أو "اضيف" → **لا تطابق**

**المشكلة:**
- المستخدمين العرب يكتبون بهذا النمط بشكل يومي جداً
- النظام سيبدو "غبياء" في عيونهم لأنه لا يفهم الأخطاء البسيطة

**التوصية 2026:**
- مرة أخرى: **Tool Calling هو الحل**
- النماذج اللغوية الكبيرة مدربة على ملايين النصوص التي تحتوي على أخطاء إملائية
- هم يفهمون أن "اضيف" و "اضيف" و "اضيف" كلها تقصد نفس الشيء
- لا تحتاج إلى عمل stemming أو normalization أو أي معالجة نصية قديمة

#### 1.3 الأسئلة الغامضة — الحاجة للتوضيح (BASIC-003) ⚠️ عالي الخطورة
**السيناريو:**
- "اعمل واحد جديد" — أي واحد؟ منتج؟ وكيل؟ طلب؟
- "كم عندنا اليوم" — كم مبيعات؟ كم موظف حاضر؟ كم طلب؟
- "عندنا مشكلة" — أي نوع المشاكل؟
- "محتاج مساعدة" — في إيه؟

**النتيجة المتوقعة:**
- ✅ يطلب توضيح بدلاً من تخمين خاطئ
- ❌ لا يفترض ولا يخمن

**الحالة الحالية في الكود:**

تحليل `agentIntentRelevanceService.js` و `CEOAgent.js`:

1. **الـ relevance engine يحسب درجات لجميع النوايا**
   - مثلاً: "اعمل واحد جديد"
   - قد يعطي: `marketingCampaign: 0.4`, `productCreation: 0.3`, `agentSpawning: 0.3`
   - الأرقام منخفضة ولا يوجد فائز واضح

2. **ماذا يحدث بعد ذلك في CEOAgent.js؟**
   - التحقق: `if (intentResult.marketingCampaign >= 0.7) → مسار الحملات`
   - التحقق: `else if (intentResult.productCreation >= 0.7) → مسار المنتجات`
   - **ماذا لو لم يصل أي شيء لـ 0.7؟**

3. **المشكلة:**
   - إذا كانت جميع الدرجات منخفضة (مثلاً أقل من 0.5)
   - هل يذهب إلى مسار `fallback`؟
   - ماذا يفعل الـ fallback؟ هل يسأل توضيحاً أم يرد بـ "أنا لا أفهم"؟

4. **تحكم أعمق:**
   - في التصميم الحالي، **لا يوجد آلية واضحة لـ "طلب توضيح"**
   - النظام إما يختار مساراً (حتى لو بنسبة منخفضة) أو يذهب لـ fallback عام
   - **لا يسأل المستخدم خيارات محددة** مثل: "هل تقصد منتج جديد أم وكيل جديد؟"

**هذه مشكلة كبيرة جداً في التصميم الحالي.**

```typescript
// 2. قبل استدعاء الأداة، قارن ما لدينا بما هو مطلوب في الـ schema
// 3. إذا كان هناك حقول required مفقودة → اسأل المستخدم عنها

// مثال باستخدام نهج حديث:
const checkRequiredFields = (toolSchema: any, collectedData: any): string[] => {
  const missing = [];
  for (const [field, config] of Object.entries(toolSchema.properties)) {
    if (toolSchema.required.includes(field) && !collectedData[field]) {
      missing.push(field);
    }
  }
  return missing;
};

// في الـ ReAct loop:
// - النموذج يختار أداة `product.create`
// - نرى في الـ parameters: ما هو موجود وما هو مفقود
// - إذا كان `needsClarification: true` أو كانت حقول required مفقودة
// - نضيف رسالة إلى المحادثة: "أنا بحاجة لمعرفة اسم المنتج وسعره قبل المتابعة."
// - نعود للـ LLM ليصيغ السؤال للمستخدم بشكل طبيعي
```

**الخلاصة لهذه الفئة:**
السيناريوهات هنا جيدة جداً لاختبار الـ routing واختبار آلية جمع المعلومات. التصميم الحالي يعتمد على matching ثابت، وسيفشل في الحالات التي تحتاج إلى حوار متعدد الخطوات لجمع المعلومات.

**المدخلات:**
- "" — رسالة فارغة
- "..." — نقاط فقط
- "؟" — علامة استفهام فقط
- "🙂" — إيموجي فقط
- "asdfghjkl" — حروف عشوائية
- "12345" — أرقام فقط

**النتيجة المتوقعة:**
- ✅ لا يتحطم (no crash)
- ✅ يطلب مدخلاً مفهوماً بطريقة مهذبة
- ❌ لا يقوم باي إجراء افتراضي خاطئ

**التحقق من الكود:**
- هل هناك validation لـ empty string في بداية التنفيذ؟
- ماذا يحدث إذا أرسل المستخدم إيموجي فقط؟
- هل الـ relevance engine تعطي درجات قريبة من الصفر للجميع؟
- وأين يذهب بعد ذلك؟

**توصية بسيطة:**
- أضف validation في البداية للـ edge cases هذه
- إذا كان النص أقل من 3 أحرف (عدا إذا كان "كم" أو "لماذا" إلخ) أو يحتوي فقط على رموز
- ارد مباشرة بـ: "أنا لم أفهم طلبك. هل يمكنك صياغته بطريقة أوضح؟"
- لا تمرر هذا النص للـ LLM أو للـ relevance engine أبداً (يوفر تكلفة ويمنع سلوك غير متوقع)

#### 7.4 اختبار الـ Deterministic Paths — الرد "ثابت" (EDGE-004)
**المشكلة المكتشفة:**
الـ CEO Agent لديه 3 مسارات تنفيذ حتمية تؤدي إلى قوالب رد ثابتة في `agentToolResultPresenter.js`

**الاختبار:**
1. اسأل: "كم موظف الحاضرين؟"
2. سجل الرد
3. اسأله نفس السؤال مرة أخرى
4. قارن

**النتيجة المتوقعة لو كان LLM generation حقيقي:**
- ✅ المعلومات نفسها + الصياغة مختلفة قليلاً

**النتيجة لو كان قالب ثابت:**
- ❌ نفس الرد حرفياً

**مصدر القوالب الحالية:**
- `renderAttendance()`
- `renderAgentList()`
- `renderProductList()`
- وغيرها من دوال الـ rendering في `agentToolResultPresenter.js`

**التوصية 2026:**
- احتفظ بهذه الدوال كـ "مستخرج بيانات" (Data Extractor) لا كـ "مُصيغ ردود"
- يعني: تجعل الدالة تعيد كائن JSON ببيانات الحضور النظيفة
- ثم أرسل هذا الـ JSON إلى الـ LLM مع تعريف الشخصية ليرد عليه
- لا تجعل الدالة تعيد نصاً جاهزاً

**مثال على التحسين:**
