# خطة إصلاح سير عمل نظام الأشعة — تجربة العميل والإنتاجية

> **الحالة:** معتمدة (13 أغسطس 2026)
> **المصادر:** الكود الفعلي (`radiology.prisma`, `radiologyController.js`, `radiologyAppointmentsController.js`, `ScheduleTab.tsx`, `StudiesTab.tsx`, `StudyDetails.tsx`, `RadiologyReportsTab.tsx`, `dicomUtil.js`) + `radiology-execution-plan.md` (الخطة الأمنية/المالية التكميلية)
> **الفكرة المحورية:** الموديل المفاهيمي (Order → Study → Report) مطابق لمعايير RIS/DICOM/HL7، لكن طبقة العرض اليومي تخفيها: رقم مزدوج وعشوائي، طلب متعدد الفحوصات مبعثر، صفر إجراءات جماعية، ولا طابور واحد للشغل. **الهدف: أن يحس المستخدم بأن الحالة = زيارة واحدة متماسكة.**

---

## مبدأ الترتيب

1. **الأساس أولًا:** توحيد الرقم والطلب (يُبنى عليه كل عرض لاحق).
2. **الإنتاجية:** الإجراءات الجماعية (أعلى عائد على وقت الاستقبال/التقني).
3. **اليومي:** الطابور + الـ Stepper الأحادي (الروح المفقودة).
4. **الذكاء:** TAT + التوصيل الذكي + بوابة الأطباء.
5. **التجربة:** التحصيل عند الاستقبال + خط زمني للمريض.

## Sprint A — الرقم الموحّد + الطلب كوحدة (الأساس)

### A1. ربط رقم الحالة برقم الحجز (إلغاء العشوائية)
**الوضع الحالي:** `studyNumber = RAD-YYYYMMDD-XXXX` عشوائي (`dicomUtil.js:14-17`)، والحجز له `bookingNo` (B-0001) مستقل. رقمين غير مرتبطين.

**الحل:**
- `convertToStudy` يولّد رقم الحالة **من رقم الحجز**: `ORD-YYYYMMDD-<seq>-<فحص>` حيث `<seq>` تسلسلي يومي مشتق من الحجز، و`<فحص>` = A/B/C لفحوصات الطلب المتعدد. يُحفظ في `studyNumber` (يبقى `@unique`) و`accessionNumber` (موجود أصلاً غير مستخدم).
- إضافة عمود **"رقم الحجز"** في قائمة الحالات + بطاقة "تفاصيل الحالة" (عبر `appointmentId` → `bookingNo`).
- طباعة اللاصقة والـ PDF تستخدم **رقم الطلب** نفسه (الـ Accession في DICOM).
- **Backfill:** سكربت يملأ `accessionNumber` للدراسات القديمة من حجزها (متاح عبر `appointmentId`) أو يتركه فارغًا وعرض `bookingNo` فقط.
- **تحقق:** اختبار أن `convertToStudy` لحجز بـ3 فحوصات ينتج `ORD-...-A/B/C`، وتصادم P2002 مستحيل (تسلسلي)، وبيلد أخضر.

### A2. عرض "الطلب" كوحدة واحدة
**الوضع الحالي:** حجز بـ3 فحوصات → 3 صفوف منفصلة في "الحالات" بلا رابط مرئي.

**الحل:**
- **قائمة الحالات:** toggle "عرض كطلبات / كحالات". في وضع "طلبات": تجميع حسب `appointmentId` تحت سطر أب (رقم الحجز، المريض، التقدم `2/3 فحوصات`، إجمالي المدفوع) قابل للطي، والسطور الفرعية هي الحالات.
- **StudyDetails:** كارت جديد **"فحوصات الطلب"** يعرض إخوة الحالة (نفس `appointmentId`) مع حالة كل فحص + تنقّل فوري.
- **تحقق:** متصفح: حجز بفحصين → يظهر تحت طلب واحد، والتقدم يتحدث عند تقديم أحدها.

## Sprint B — الإجراءات الجماعية (أعلى عائد إنتاجية)

### B1. Backend — endpoints جماعية (كلها `{ ids: [] }`)
في `radiologyRoutes.js`/`radiologyAdminRoutes.js`:
- `POST /appointments/bulk/convert` — تحويل مجموعة حجوزات (يعيد ملخص: نجح/فشل لكل id).
- `POST /appointments/bulk/checkin` — حضور جماعي.
- `POST /studies/bulk/advance` — تقديم الحالة لمرحلة تالية (التحقق من انتقال صالح لكل حالة).
- `POST /studies/bulk/deliver` — تسليم جماعي (يبقى شرط الصور/التقرير الخارجي لكل حالة).
- `POST /studies/bulk/labels` — لاصقات متعددة (قائمة PDF أو ZIP).
- `POST /reports/bulk/advance` — مراجعة/توقيع/تسليم جماعي للتقرير.

**التنفيذ:** إعادة استخدام دوال الفردي الحالية (مثل `advanceStatus`, `markDelivered`) داخل loop مع `companyId` scoping + جمع أخطاء per-item وإرجاع `{ successCount, failed: [{id, error}] }` (لا فشل ذري — كل عنصر مستقل).
**تحقق:** اختبارات jest لكل endpoint: حالة صالحة/غير صالحة/غير تابعة للشركة + مدفوعات/تسليم جماعي.

### B2. Frontend — شريط اختيار متعدد
- **الحجوزات:** checkboxes + شريط سفلي (تحويل جماعي / حضور جماعي).
- **الحالات:** checkboxes + (تقديم جماعي / تسليم جماعي / طباعة لاصقات).
- **التقارير:** checkboxes + (مراجعة جماعية / توقيع جماعي / تسليم جماعي).
- UI: `selectAll` في الرأس، حالة تحميل، تأكيد، toast ملخص، إعادة جلب بعد التنفيذ.
**تحقق:** متصفح: اختيار 3 صفوف → تقديم جماعي → كلها تتحدث وتظهر في السجل.

## Sprint C — طابور اليوم + Stepper أحادي (الروح المفقودة)

### C1. نافذة "طابور اليوم"
**Backend:** `GET /radiology/queue/daily` يجمّع في استدعاء واحد:
- `pendingCheckIn`: حجوزات اليوم لم تحضر بعد.
- `imagingQueue`: حالات `PENDING_IMAGING` (فلاتر: جهاز/موديول/أخصائي) — ترتيب حسب أولوية/قديم.
- `readyForReport`: حالات `IMAGED` / `PENDING_REPORT`.
- `readyForDelivery`: حالات `REPORTED`.
- `stuck`: حالات عالقة > X ساعة في أي مرحلة (من `RadiologyStudyStatusHistory`).
**Frontend:** view جديدة "طابور اليوم" (من أعلى الحجوزات أو تبويب مستقل) بأعمدة المراحل: استقبال → تصوير → تقرير → تسليم، مع أزرار فردية/جماعية لكل عمود، وعداد لكل مرحلة.
**تحقق:** متصفح: بيانات حقيقية تعرض الـ 4 أعمدة + عداد + فلاتر أجهزة.

### C2. Stepper أحادي بدل تضخم الأبعاد
**الوضع الحالي:** 4 أبعاد حالة (طلب/تجهيز/دفع/تقرير) + حالة حجز + حالة Rology.
**الحل:** اشتقاق **مرحلة رئيسية واحدة** لكل حالة (`استقبال → تصوير → تقرير → تسليم`) من سلسلة `status`، تُعرض كـ stepper صغير في صف القائمة + في هيدر التفاصيل، بينما الدفع بادج ملونة جانبية (🔴 غير مدفوع / 🟢 مسدد) وتفاصيل الأبعاد تبقى في صفحة التفاصيل فقط.
**تحقق:** متصفح: كل حالة تظهر بمرحلة واضحة واحدة + بادج الدفع، وتقارير/مدفوعات لا تشوش القائمة.

## Sprint D — الذكاء: TAT + توصيل النتائج + بوابة الأطباء

### D1. تحليلات وقت الدوران (TAT)
**Backend:** `GET /radiology/statistics/tat` يعتمد على `RadiologyStudyStatusHistory` (موجودة ومسجّلة لكل انتقال):
- متوسط/أدنى/أقصى زمن لكل مرحلة (استقبال→تصوير، تصوير→تقرير، تقرير→تسليم).
- حسب الموديول / الأخصائي / الطبيب المحيل.
- حالات طارئة عالقة + تصنيف "زمن الدوران الإجمالي".
**Frontend:** أقسام في `StatisticsTab` (أشرطة + جدول TAT + فلاتر تاريخ).
**تحقق:** اختبار jest للحسابات على history وهمي + متصفح يعرض أرقامًا حقيقية.

### D2. توصيل ذكي عند التسليم
**Backend:** بعد `markDelivered` (أو `bulk/deliver`):
- إرسال PDF التقرير للمريض عبر **واتساب** (البنية جاهزة: `whatsappMessageHandler.sendImage`) — best-effort مع `try/catch`.
- إشعار **الطبيب المحيل** "النتيجة جاهزة" (رسالة نصية/صورة).
- Config per company: toggle في `RadiologySetting` (`deliverSmsPatient`, `notifyReferringDoctor`) + احترام موافقة المريض.
**تحقق:** دراسة DELIVERED → رسالة واتساب للمريض (محاكاة أو real إذا توفرت جلسة).

### D3. بوابة الأطباء المحوّلين (نسخة خفيفة أولًا)
**Backend:** `GET /radiology/referring-physicians/:id/results` — دراسات مكتملة لمريض معين (موجودة جزئيًا في عمولات الأطباء) + عدد غير المقروء.
**Frontend:** في `ReferringPhysiciansTab`: زر "نتائج" لكل طبيب → نافذة تعرض حالات مرضاه المحوّلين ومستوى قراءتها (مقرأ/لم يُقرأ) + ختم قراءة.
**تحقق:** متصفح: الطبيب يفتح النتائج ويظهر عدد غير المقروء.

## Sprint E — تجربة الاستقبال والمراجع

### E1. تحصيل عند الاستقبال (استقبال واحد بدل خطوتين)
**الوضع الحالي:** "مريض فوري" → حجز CHECKED_IN → "تحويل لدراسة" → ثم "الدفع" — 3 خطوات منفصلة.
**الحل:** زر **"استقبال وإنشاء الحالات"** في الحجوزات: مدخل واحد يجمع (المريض + الفحوصات + **دفعة أولى اختيارية** method/amount + جهاز + تأمين) ثم ينفّذ check-in + convert + تسجيل الدفعة في خطوة واحدة، ويعيد لصفحة الحالات.
**تحقق:** متصفح: مريض جديد → خطوة واحدة → 3 حالات منشأة + دفعة مسجلة + وردية محدثة.

### E2. خط زمني لزيارات المريض
**الحل:** تطوير نافذة "دراسات المريض" في `RadiologyPatientsTab` إلى **خط زمني**: كل مجموعة زيارة (appointmentId) → كارت بتاريخها وفحوصاتها وحالة كل فحص وتقاريرها، مرتب زمنيًا.
**تحقق:** متصفح: مريض له زيارتان → زيارتان مرتبتان.

### E3. كشف تعارض الجهاز (time + device)
**الحل:** عند اختيار جهاز + معاد في الحجز، فحص `RadiologyAppointment` لحجوزات أخرى على نفس `deviceId` في نفس اليوم/المعاد (الموجود `timeSlotTaken` يحسب الوقت فقط — توسيعه للجهاز) + تحذير مرئي.
**تحقق:** اختبار backend + متصفح يُحذّر عند تعارض.

### E4. إعادة تنظيم القائمة حسب رحلة العمل
**الحل:** تجميع تبويبات/قائمة الأشعة في مجموعات واضحة مع **رؤية حسب الدور**:
- **اليوم:** طابور اليوم / الحجوزات / الحالات / التقارير الطبية
- **الموارد:** الفحوصات / الأسعار / الأخصائيون / الأطباء المحوّلون / الأجهزة
- **المالية:** المدفوعات / فواتير التأمين / الدفتر / الورديات / شركات التأمين
- **تحليلات:** اللوحة / الإحصائيات / عرض سعر
- **إعدادات:** تعاقدات / فروع / التقارير / الإعدادات
(السياق: 20 تبويب حاليًا؛ تقليل الظاهر للاستقبال/التقني إلى مجموعة "اليوم" فقط حسب الدور.)
**تحقق:** متصفح: دور الاستقبال يرى مجموعة اليوم فقط.

## مخاطر ومهّدات

| الخطر | المهّد |
|---|---|
| **تغيير الترقيم يكسر البيانات القديمة/الـ unique** | أبقِ `studyNumber @unique` + تسلسل من الحجز + سكربت backfill غير مدمر + فترة انتقالية (عرض bookingNo لو accession فارغ) |
| **جلسات متوازية تعدّل نفس الملفات** | العمل في ملفات جديدة أولًا + إعادة فحص `git status` قبل أي commit + عدم `git stash` |
| **إرسال واتساب تلقائي يُزعج/يُحسب كسبام** | toggle لكل شركة + best-effort + احترام موافقة المريض + اختيار صورة/نص |
| **مجاميع الطابور/TAT ثقيلة** | اعتماد `RadiologyStudyStatusHistory` + فهارس `createdAt`/`companyId+status` + حد أزمنة مع `truncated` |
| **الدفعة الجماعية بلا تحقق انتقال صالح** | كل endpoint يستخدم نفس `validateRadiologyStudyTransition` لكل عنصر ويعيد أخطاء per-item (لا فشل ذري) |
