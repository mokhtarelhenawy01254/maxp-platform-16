### [FIX] Unique Name Constraint and Deletion of AI Agents

- **Date**: 2026-06-26
- **Description**: Creating a new active agent with the same name as a soft-deleted/archived agent resulted in a unique key violation. Also, archived agents could not be permanently deleted from the database or restored easily from the UI.

### [FIX] AI Hub Auto-Reply Settings Did Not Reach WhatsApp Runtime
- **Date**: 2026-06-23
- **Description**: A company could show auto-reply enabled in the AI Hub/ai-service while WhatsApp, Messenger, Instagram, or Telegram backend runtime still treated AI auto-reply as disabled.
- **Root Cause**: The new AI Hub settings live in `ai.ai_settings`, while legacy customer-channel runtime checks read Prisma `AiSetting`, mapped to `public.ai_settings`. Enabling auto-reply through ai-service could therefore leave the legacy table empty or stale.
- **Additional Root Cause**: Meta can deliver multiple products through the same app callback. If WhatsApp Cloud events were posted to the existing `/api/v1/webhook` callback, the Facebook/Messenger controller returned `EVENT_RECEIVED` without passing `whatsapp_business_account` payloads to the WhatsApp Cloud controller.
- **Resolution**: Added an effective AI settings resolver that reads `ai.ai_settings` first and falls back to `public.ai_settings` for legacy tenants. Customer-channel auto-reply gates now use the resolver, preserving safe disabled defaults while preventing split-brain settings. The generic Meta webhook endpoint now forwards WhatsApp Business Account verification and POST payloads to the WhatsApp Meta controller.
- **Files Modified**:

### [FIX] WhatsApp Baileys Connection Replaced In PM2 Cluster
- **Date**: 2026-06-23
- **Description**: WhatsApp AI auto-replies could be generated by the correct assigned agent but delivery was unreliable because the connected Baileys session repeatedly closed with `statusCode: 440` (`connectionReplaced`).
- **Root Cause**: Production `maxp-backend` was running multiple PM2 cluster instances, and each process called `WhatsAppManager.restoreAllSessions()` during startup. Every instance opened a socket for the same WhatsApp session, so WhatsApp replaced the previous connection in a loop.
- **Resolution**: Added a singleton process ownership helper and limited WhatsApp session restoration to PM2 instance `0` by default. Non-owner backend instances still serve HTTP traffic but skip Baileys socket ownership.
- **Frontend Guard**: The AI Hub channel routing page now defaults the auto-reply switch to disabled if the auto-reply read endpoint fails, matching the backend safe default instead of showing a misleading enabled state.
- **Files Modified**:
    - `backend/server.js`
    - `backend/utils/processOwnership.js`
    - `backend/tests/utils/processOwnership.test.js`
    - `frontend/src/pages/admin/ChannelRoutingPage.tsx`

### [FIX] Meta Cloud Webhook Could Match Deleted Duplicate Session
- **Date**: 2026-06-23
- **Description**: WhatsApp Cloud API webhooks could resolve to an older duplicated `META_CLOUD` session for the same `metaPhoneNumberId`, including rows marked with `metadata.isDeleted=true`.
- **Root Cause**:
    1. `whatsappMetaWebhookController` used an unordered `findFirst` across phone number identifiers without filtering deleted duplicate sessions or preferring the default/latest connected configuration.
    2. The deleted-session filter used `NOT metadata contains ...` directly, which excluded active Meta sessions whose `metadata` column was `null`. This made Meta verify-token checks return `403` and made inbound message lookup skip the active session.
- **Resolution**: Centralized Meta session lookup, restricted it to `META_CLOUD`, ignored deleted metadata rows, explicitly allowed `metadata: null`, and ordered by `isDefault` then `updatedAt` so inbound messages attach to the active session.
- **Files Modified**:
    - `backend/controller/whatsappMetaWebhookController.js`
    - `backend/tests/controller/whatsappMetaWebhookController.test.js`

### [FIX] WhatsApp AI Auto-Reply Failed On Connected Session With Null Socket
- **Date**: 2026-06-22
- **Description**: Production WhatsApp AI auto-reply generated the correct agent response but failed before delivery with `Cannot read properties of null (reading 'sendMessage')`.
- **Root Cause**:
    1. `WhatsAppMessageHandler.sendText` trusted `session.status === 'connected'` and called `session.sock.sendMessage(...)` without verifying that the Baileys socket was still present and sendable.
    2. A session could remain marked connected in memory while the socket was already unavailable, so the AI pipeline completed but outbound WhatsApp delivery crashed.
    3. Optional outgoing message metadata was accepted by the handler but not persisted by `saveOutgoingMessage`.
    4. `WhatsAppManager.syncProfile` read `session.sock.user` again after async profile calls, so a socket cleared during reconnect could still cause a null-user crash.
- **Resolution**:
    1. Added a Baileys send-readiness guard that reconnects and waits briefly for a usable socket before sending.
    2. Re-checks the sendable session after the typing delay so a socket that drops mid-send does not produce a null dereference.
    3. Persisted optional outgoing metadata for both Baileys and Meta Cloud text sends.
    4. Captured a stable socket/user snapshot before profile sync work and reused it through the async flow.

### [FIX] WhatsApp QR Restore, Manual Logout Boundary, and History Import
- **Date**: 2026-05-18
- **Description**: A disconnected/QR-pending Baileys session could stop showing QR after the backend process restarted, and newly linked numbers started with empty MaxP chat history unless new messages arrived.
- **Root Cause**:
    1. QR codes live in the active Baileys socket and were lost on PM2/backend restart unless the session restorer recreated `QR_PENDING` sessions.
    2. Unexpected Baileys `loggedOut`, Bad MAC, or `403` forbidden socket failures could be treated too much like reconnectable transient errors or final logout, even when the user had not logged out from MaxP or WhatsApp intentionally.
    3. Initial link did not expose a UI option to request Baileys full-history sync, and historical `append` message batches were not handled as quiet imports.
- **Resolution**:
    1. Restore `QR_PENDING` sessions on startup so the same MaxP session can generate a fresh QR/pairing state after restart.
    2. Reserve `LOGGED_OUT` for explicit manual logout; unexpected auth corruption and Baileys `403` socket closes clear only auth state and return the session to relink/QR recovery.
    3. Added an import-history checkbox to the add-session dialog and wired `importHistory`/`syncFullHistory` through the API into Baileys.
    4. Import `messaging-history.set` chats, contacts, and messages without unread increments, realtime notifications, AI, CRM sync, or old media downloads.

### [FIX] WhatsApp Reconnect QR & Pairing Recovery
- **Date**: 2026-05-17
- **Description**: Disconnected Baileys sessions could not be re-linked from the same MaxP session; reconnect returned no QR or WhatsApp pairing code, forcing operators to delete and recreate the session.
- **Root Cause**:
    1. Transient Baileys socket closes were persisted as `DISCONNECTED`, even when WhatsApp had not logged out the linked device.
    2. The reconnect endpoint reused an existing in-memory session and did not force a fresh socket/link state.
    3. Corrupted auth key updates and Bad MAC recovery could delete or strand the MaxP session instead of clearing auth and showing a new link prompt.
    4. The single-session endpoint still requested old Prisma relation count names (`messages`, `contacts`), so the UI could hit a 500 after reconnect even when QR generation succeeded.
- **Resolution**:
    1. Keep transient disconnects in `CONNECTING` and schedule automatic reconnect; only mark `LOGGED_OUT` on a real WhatsApp logout.
    2. Reconnect now force-restarts the socket and returns QR or pairing code on the same session record.
    3. Auth state key deletes are persisted correctly, and corrupted auth is cleared without deleting the MaxP session.
    4. `GET /sessions/:id` now counts `whatsAppMessages` and `whatsAppContacts`, matching the current schema.
- **Verification**:
    - `backend: node --check backend/services/whatsapp/DatabaseAuthState.js`
    - `backend: node --check backend/services/whatsapp/WhatsAppManager.js`
    - `backend: node --check backend/controller/whatsappController.js`
