# سيناريوهات عميل فيسبوك وماسنجر - Wofod / MaxP

> الغرض: تغطية أغلب الأسئلة والنيات التي ممكن تيجي من عميل على Facebook Messenger، وتحويلها لاختبارات للوكيل `FACEBOOK_SALES_SUPPORT`.
> آخر تحديث: 2026-05-25

## قواعد عامة للوكيل

- لا يخترع سعر، مخزون، خصم، مدة شحن، أو حالة طلب.
- يستخدم أدوات القراءة قبل أي تأكيد:
  - `product.search` للمنتجات والأسعار.
  - `inventory.check` للمقاسات/الألوان/التوفر.
  - `shipping.rates` للشحن.
  - `order.lookup` لمتابعة الطلب.
  - `customer.info` عند احتياج بيانات العميل.
- يستخدم `order.create_draft` فقط بعد تأكيد: المنتج، الكمية، الاسم، الهاتف، المدينة/المحافظة، والمقاس/اللون عند الحاجة.
- يستخدم `agent.handoff` عند الشكاوى، الاسترجاع، الخصومات الخاصة، الغموض العالي، أو أي قرار يحتاج إنسان.

### SC-T02: ❓ استفسار قبل الشراء (Pre-purchase Questions)

**الهدف**: اختبار دقة الرد بدون هلوسة — يستخدم بيانات حقيقية من الكتالوج.

👤 **العميل**: الخامة دي جلد طبيعي ولا صناعي؟

🤖 **الوكيل**:
```
[داخلي] product.search(query: "Swan High Skotch")
→ { material: "جلد صناعي مقاوم (PU Leather)", description: "..." }
[داخلي] الوكيل يقرأ وصف الخامة من الكتالوج فقط — لا يخترع ولا يضيف
```
الخامة المستخدمة في **Swan High Skotch** هي **جلد صناعي مقاوم (PU Leather)** وليست جلد طبيعي. لكنها خامة عالية الجودة ومقاومة للمياه والاستخدام اليومي. فيه حاجة تانية عايز تعرفها؟

👤 **العميل**: وبتفرق عن الطبيعي في إيه؟

🤖 **الوكيل**:
```
[داخلي] الوكيل ليس لديه بيانات مقارنة جلد طبيعي vs صناعي في الكتالوج
→ يقرر الرد بموضوعية بدون اختراع
```
الصراحة، عندي معلومات عن المنتج نفسه وهو **جلد صناعي مقاوم**، لكن ما عنديش تفاصيل مقارنة شاملة بين الطبيعي والصناعي. اللي أقدر أقوله: الجلد الصناعي اللي فيه مقاوم للمياه وأسهل في التنظيف والصيانة، وسعره أقل طبعاً (499 جنيه). هل تفضل تجربه؟

👤 **العميل**: مقاس 43 موجود؟

🤖 **الوكيل**:
```
[داخلي] inventory.check(productNameOrSku: "Swan High Skotch", productSize: "43")
→ inStock: true, quantity: 8
```
موجود ✅ مقاس 43 متاح. عايز أي لون؟

👤 **العميل**: رمادي

🤖 **الوكيل**:

### SC-T03: 🔁 مقارنة منتجات (Product Comparison)

**الهدف**: اختبار قدرة الإيجنت على المقارنة الموضوعية وتوجيه العميل حسب الاستخدام.

👤 **العميل**: أنهي أفضل، الـ High Skotch ولا الـ Walker؟

🤖 **الوكيل**:
```
[داخلي] product.search(query: "Swan High Skotch", limit: 1)
→ { price: 499, description: "كوتشي رياضي متعدد الاستخدامات، نعل مبطن" }
[داخلي] product.search(query: "Swan Walker", limit: 1)
→ { price: 425, description: "كوتشي يومي خفيف، نعل إسفنجي مريح، سعر اقتصادي" }
[داخلي] الوكيل يقارن بناءً على بيانات مؤكدة فقط
```
الاتنين كويسين والاختيار حسب استخدامك:

- **High Skotch (499 جنيه)**: أنسب لو عايز حاجة للمشي اليومي والتمارين الخفيفة — نعل مبطن، خامة جلد صناعي مقاوم.
- **Walker (425 جنيه)**: أنسب لو عايز كوتشي يومي عادي وموفر — نعل إسفنجي مريح، خامة قماش وجلد، سعر أقل.

إيه اللي هتستخدمه فيه عشان أساعدك تختار؟

👤 **العميل**: هلبسه يومي عشان الشغل، محتاج حاجة تقيلة شوية

🤖 **الوكيل**:

### SC-T09: 😡 عميل غاضب (Angry Customer)

**الهدف**: اختبار التهدئة والاحترافية بدون دفاع أو جدال.

👤 **العميل**: الطلب اتأخر ومش هشتري تاني!

🤖 **الوكيل**:
```
[داخلي] الوكيل يكتشف غضب — يتحول فوراً لوضع التهدئة
[داخلي] order.lookup(customerPhone: من سياق المحادثة أو يطلبها)
→ يحتاج رقم الطلب أو الهاتف
```
أنا آسف جداً لتأخر الطلب 😔 حقك عليا. أقدر أتفهم إحباطك تماماً. عشان أساعدك بأسرع طريقة، ممكن تقلي رقم الطلب أو رقم هاتفك؟

👤 **العميل**: رقمي 01011122333

🤖 **الوكيل**:
```
[داخلي] order.lookup(customerPhone: "01011122333")
→ { orderId: "ORD-150", status: "pending", createdAt: "2026-05-10", daysSinceOrder: 16 }
[داخلي] الوكيل يقرر: 16 يوم في حالة pending = تأخير غير مقبول → تصعيد فوري
```
الطلب **ORD-150** من يوم 10 مايو — 16 يوم وحالته لسه قيد الانتظار. ده تأخير غير مقبول فعلاً وأنا اعتذرلك بصدق.

```
[داخلي] agent.handoff(targetType: "human",
  reason: "تأخير طلب — عميل غاضب",
  summary: "الطلب ORD-150 معلق من 16 يوم، العميل غاضب جداً، يحتاج اتصال عاجل من الفريق البشري للاعتذار وحل الموقف")
→ Handoff completed
```
حولت طلبك فوراً للفريق المسؤول. هيتواصلوا معاك النهاردة أو بكرة الصبح على أقصى تقدير. وعد ✋

👤 **العميل**: طيب، مستني

🤖 **الوكيل**: وأنا في انتظار متابعتهم معاك. لو محتاج أي حاجة تانية، أنا موجود. وشكراً لصبرك 🤝

**الحكم**: الإيجنت اعتذر، لم يدافع، جمع البيانات، صعد بسرعة — ✅ تهدئة احترافية.

### SC-T10: 🧠 سؤال عام مش واضح (Ambiguous Intent)

**الهدف**: اختبار الاستيضاح بدلاً من التخمين.

👤 **العميل**: عندك حاجة حلوة؟

🤖 **الوكيل**:

أكيد عندنا حاجات كويسة! 😊 بس عشان أساعدك بالضبط:
- عايز **كوتشي/جزمة** ولا **تيشيرت** ولا **إكسسوارات**؟
- لو كوتشي، عايزه لـ **المشي اليومي** ولا **الرياضة** ولا **خروج**؟

```
→ High Skotch أنسب للخروج (أفخم)
```
الأنسب للخروج هو **Swan High Skotch** — شكله أنيق، جلد صناعي لمعة، يناسب الخروجات والمناسبات الكاجوال. سعره **499 جنيه**. تحب تشوف ألوانه؟

👤 **العميل**: عايز أبيض

🤖 **الوكيل**:
```
[داخلي] inventory.check(productNameOrSku: "Swan High Skotch", productSize: "", productColor: "أبيض")

مقاسك كام عشان أتأكد من التوفر؟
```
أبيض موجود ✅ مقاسك كام عشان أتأكد من التوفر؟

**الحكم**: الإيجنت ما افترضش، سأل أسئلة توضيحية، وضيق الخيارات — ✅ استيضاح ذكي.

**الإجمالي: 798 جنيه**

## سيناريوهات أولوية للاختبار الحي

### LIVE-001: الرد على رسالة معينة داخل محادثة طويلة

- **الهدف**: يتعامل الوكيل مع آخر رسالة أو رسالة محددة بدون ما يخلط بينها وبين رسائل قديمة.
- **مثال العميل**: "طب والمقاس 42؟" بعد كلام سابق عن أكثر من منتج.
- **المتوقع**:
  - يربط السؤال بالمنتج الأقرب في السياق.
  - لو السياق يحتمل أكثر من منتج، يسأل: "تقصد مقاس 42 في أنهي موديل؟"
  - لا يرد برد عام على كل المحادثة.
- **الأدوات**: `inventory.check` بعد تحديد المنتج.

### LIVE-002: الكلام على أكثر من منتج في نفس المحادثة

- **الهدف**: يفصل بين المنتجات ولا يخلط السعر/المقاس/المخزون.
- **مثال العميل**: "عايز أعرف سعر ده وده، والاسود في التاني موجود؟"
- **المتوقع**:
  - يرقم المنتجات أو يسميها بوضوح.
  - يستخدم `product.search` لكل منتج غير مؤكد.
  - يستخدم `inventory.check` للمنتج المطلوب فقط.
  - يسأل توضيح لو "ده وده" غير مفهوم من الصور/السياق.

### LIVE-003: عمل أوردر من محادثة فيسبوك

- **الهدف**: تحويل نية الشراء لمسودة طلب آمنة.
- **مثال العميل**: "تمام عايز واحد أسود مقاس 42، اسمي أحمد ورقمي 01000000000 والمنصورة."
- **المتوقع**:
  - يتحقق من المنتج والمقاس/اللون.
  - يطلب العنوان التفصيلي لو ناقص.
  - ينفذ `order.create_draft` بعد اكتمال البيانات.
  - يرد بملخص مسودة الطلب ولا يدعي أن الطلب اتأكد نهائياً.

### LIVE-004: اعتراضات العميل

- **الهدف**: التعامل مع اعتراضات السعر/الشحن/الثقة بدون وعود غير مؤكدة.
- **أمثلة**:
  - "غالي."
  - "الشحن كتير."
  - "أنا خايف المقاس ما يطلعش مظبوط."
  - "ينفع خصم؟"
- **المتوقع**:
  - يشرح القيمة أو السياسة المؤكدة.
  - لا يخترع خصم.
  - يصعد بـ `agent.handoff` عند الخصومات الخاصة أو اعتراض يحتاج قرار.

### LIVE-005: العميل يرسل صورة منتج

- **الهدف**: لما العميل يبعت صورة ويسأل "عندكم زي ده؟"
- **المتوقع**:
  - لو النظام لا يملك فهم صورة مؤكد، يطلب وصف مختصر أو اسم المنتج.
  - لو الصورة مرتبطة بسياق بوست/إعلان محفوظ، يستخدم السياق.
  - يصعد لو العميل محتاج مطابقة بصرية دقيقة.
- **الأدوات**: `product.search` أو `agent.handoff`.

### LIVE-006: العميل يطلب صورة منتج

- **الهدف**: طلب صور إضافية/ألوان/صورة على الطبيعة.
- **مثال العميل**: "ممكن صورة للون الأسود؟"
- **المتوقع**:
  - يرسل/يشير للصور المتاحة فقط لو النظام يدعم إرسال صور المنتج.
  - لو غير متاح، يصعد أو يقول إن الصور المتاحة هي الموجودة بدون اختراع.
  - لا يرسل صورة منتج مختلف.

### LIVE-007: تحديث بخصوص الطلب

## أولويات الإصلاح المقترحة

1. **تثبيت رد المقاس/اللون**: عند وجود كيان مقاس أو لون في رسالة العميل، يجب أن يحتوي الرد النهائي على نفس القيد صراحة، لا يكتفي بتوفر المنتج العام.
2. **فصل تنفيذ الأدوات عن الرد النهائي**: لو `order.create_draft` أو `order.lookup` فشل، يجب إرسال رد اعتذار/طلب بيانات أو تصعيد بدلاً من الصمت.
3. **منع تسريب أسماء الأدوات الداخلية**: أي صياغة مثل "هل يمكنني استخدام أداة..." أو "سأستخدم أداة..." يجب أن تزال أو تستبدل برد طبيعي، لأن العميل لا يجب أن يرى طبقة التنفيذ الداخلية.
4. **دعم مرفقات العميل**: تخزين `attachments` من Messenger داخل سياق الوكيل، ثم:
   - لو النظام لا يدعم الرؤية: يطلب وصف الصورة أو يصعد.
   - لو الرؤية مفعلة: يرسل صورة المنتج/الوصف إلى موديل vision، ثم يطابقها بالكتالوج.
5. **دعم إرسال صور المنتج**: لو `product.search` رجع `mainImage/images`، يرسل الصورة عبر Messenger Send API، أو يرسل رابط/يصعد لو الصورة غير صالحة.
6. **اختبارات انحدار**: إضافة اختبارات محلية لسيناريوهات `LIVE-001` إلى `LIVE-007` على مستوى webhook -> agent -> response delivery.

## مصادر تحقق 2026

- Meta Messenger Platform Send API: يحتاج Page access token، صلاحية `pages_messaging`، ورسالة من العميل خلال نافذة 24 ساعة أو موافقة خارجها. يدعم إرسال الصور عبر `message.attachment.type=image` مع `payload.url`، ويدعم عدة صور عبر `message.attachments`.
- Facebook Help يوضح أن إدارة الصفحة تستطيع الرد على تعليقات الصفحة برسائل مباشرة عند توفر صلاحيات الصفحة.
- OpenAI Images/Vision يوضح أن النماذج الحديثة تستطيع تحليل صور كمدخلات عبر URL أو Base64/File ID، مع حدود حجم وأنواع ملفات، وهذا يصلح لمسار "العميل أرسل صورة منتج".

## بيانات اختبار مقترحة لكل سيناريو

- `customerName`: اسم عربي قصير.
- `customerPhone`: رقم مصري صحيح.
- `city`: القاهرة، الجيزة، الإسكندرية، المنصورة، طنطا.
- `product`: منتج فعلي من كتالوج Wofod/Swan عند الاختبار.
- `size/color`: قيم موجودة وقيم غير موجودة لاختبار الرفض الآمن.
