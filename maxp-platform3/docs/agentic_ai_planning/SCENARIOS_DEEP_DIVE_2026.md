### السيناريو 1.1: فهم اللغة العربية العامية والفصحى
**المعرف:** `BASIC-001`

**المدخلات المقترحة:**
1. "عايز اعمل منتج جديد" (مصري)
2. "أريد إنشاء منتج جديد" (فصحى)
3. "ابغى اسوي منتج جديد" (خليجي)
4. "بدي اعمل منتج جديد" (شامي)

**تحليل الكود الحالي:**
- الملف: `backend/services/aiAgent/agentIntentRelevanceService.js`
- النوع: Keyword-based matching
- الكلمات المفتاحية في `PRODUCT_CREATION_HINTS`: ["منتج", "اضيف", "جديد", "إنشاء", "اعمل", "إضافة", "سلة", "catalog", "catalogue", "SKU", "مخزون", "سعر"]

**المشكلة:**
- الكلمات مثل "عايز"، "ابغى"، "بدي"، "اسوي" **غير موجودة** في مصفوفات الكلمات المفتاحية
- الاعتماد كلي على كلمات مثل "منتج" و "اعمل"
- إذا اختلفت الصياغة وذهبت بدون هذه الكلمات → **فشل في الـ routing**

**الحالة المتوقعة للاختبار:**
- "أريد إنشاء منتج جديد" → ربما ينجح (يحتوي على "إنشاء" و "منتج")
- "عايز اعمل منتج جديد" → يعتمد على "اعمل" و "منتج" (لكن "اعمل" موجودة في 6 مصفوفات → تعارض)
- "ابغى اسوي منتج جديد" → "اسوي" غير موجود → يعتمد فقط على "منتج"
- "بدي اعمل منتج جديد" → "بدي" غير موجود → يعتمد على "اعمل" و "منتج" → تعارض

**توصية 2026:**
1. **لا تحل هذا بإضافة المزيد من الكلمات المفتاحية** (اللهجات لا حصر لها)
2. الحل الصحيح: **Tool Calling for Intent Classification**
3. عرّف أداة `create_product` بـ `description` جيد:
   ```
   "عندما يريد المستخدم إنشاء منتج جديد أو إضافة سلعة للمخزون أو تحديث كتالوج المنتجات"
   ```
4. النموذج (مثل gpt-oss-120b) **يفهم جميع اللهجات بشكل طبيعي** بدون أي كلمات مفتاحية
5. إجبار `tool_choice: "required"` لضمان الـ structured output

**مستوى الخطورة:** عالي

### السيناريو 1.2: الأخطاء الإملائية الشائعة
**المعرف:** `BASIC-002`

**المدخلات المقترحة:**
1. "عايز اضيف منتج" (صحيح)
2. "عايز اضيف منتج" (خطأ شائع: ضاد/زاد)
3. "عايز اضيف منتج" (خطأ: طاء/ظاء)
4. "كم موظف النهارده" (مصري صحيح)
5. "كم موظف النهاردة" (خطأ شائع: دال/ذال)

**تحليل الكود الحالي:**
- Keyword-based matching يعتمد على `includes` أو تطابق نصي صارم
- إذا كانت الكلمة في الـ hint هي "اضيف" والمستخدم كتب "اضيف" → **لا تطابق**
- إذا كانت "نهارده" في الـ hint و "نهاردة" في الإدخال → **لا تطابق**

**المشكلة:**
- المستخدمين العرب يكتبون بهذا النمط بشكل يومي جداً
- الأخطاء بين: ضاد/زاد، طاء/ظاء، حاء/خاء، دال/ذال، سين/صاد
- النظام سيبدو "غير ذكي" لأنه لا يفهم الأخطاء البسيطة التي يفهمها البشر

**الحالة المتوقعة للاختبار:**
- "عايز اضيف منتج" → ربما ينجح إذا "اضيف" في الـ hints
- "عايز اضيف منتج" → **فشل** لأن "اضيف" != "اضيف"
- "عايز اضيف منتج" → **فشل** لأن "اضيف" != "اضيف"
- "كم موظف النهارده" → نجح إذا "نهارده" موجود
- "كم موظف النهاردة" → **فشل**

**الحلول القديمة التي لا ننصح بها في 2026:**
- إضافة جميع الاختلافات الإملائية إلى الـ hints (ليس عملياً)
- استخدام Normalization أو Stemming (يعمل جزئياً لكنه قديم)

**توصية 2026:**
- مرة أخرى: **Tool Calling هو الحل**
- النماذج اللغوية الكبيرة مدربة على ملايين النصوص التي تحتوي على أخطاء إملائية
- هم يفهمون أن "اضيف" و "اضيف" و "اضيف" كلها تقصد نفس الشيء
- هم يفهمون أن "نهارده" و "نهاردة" هي نفسها
- **لا تحتاج إلى أي معالجة نصية خاصة** فقط اعرّف الأداة بـ description جيد واترك للنموذج يفهم

**مستوى الخطورة:** عالي

### السيناريو 1.3: الأسئلة الغامضة — الحاجة للتوضيح
**المعرف:** `BASIC-003` ⚠️ **أهم سيناريو في هذه الفئة**

**المدخلات المقترحة:**
1. "اعمل واحد جديد" — أي واحد؟ منتج؟ وكيل؟ طلب؟
2. "كم عندنا اليوم" — كم مبيعات؟ كم موظف حاضر؟ كم طلب؟
3. "عندنا مشكلة" — أي نوع المشاكل؟
4. "محتاج مساعدة" — في إيه؟

**النتيجة المتوقعة (التصميم الصحيح):**
- ✅ يطلب توضيح بدلاً من تخمين خاطئ
- ✅ يسأل خيارات محددة: "هل تقصد منتج جديد أم وكيل جديد؟"
- ❌ لا يفترض ولا يخمن

**تحليل الكود الحالي بعمق:**

الملفات المعنية:
1. `backend/services/aiAgent/agentIntentRelevanceService.js`
2. `backend/services/aiAgent/CEOAgent.js`

**خطوات التنفيذ الحالية:**
1. المستخدم يرسل رسالة غامضة مثل "اعمل واحد جديد"
2. `calculateRelevance` تحسب درجات لجميع النوايا:
   - مثلاً:
     - `marketingCampaign: 0.4` (لأن فيها "اعمل")
     - `productCreation: 0.3` (لأن فيها "جديد" وربما "اعمل")
     - `agentSpawning: 0.3` (لأن فيها "اعمل")
     - `orderDraft: 0.2`
   - جميع الدرجات **منخفضة** ولا يوجد فائز واضح
3. في `CEOAgent.js`:
   ```javascript
   if (intentResult.marketingCampaign >= 0.7) {
     // مسار الحملات
   } else if (intentResult.productCreation >= 0.7) {
     // مسار المنتجات
   } else if (intentResult.agentSpawning >= 0.7) {
     // مسار الوكلاء
   } else {
     // ماذا يحدث هنا؟
   }
   ```

**المشكلة الكبيرة:**
- إذا كانت جميع الدرجات **أقل من 0.7**
- هل يذهب إلى مسار `else`؟
- ماذا يفعل الـ `else`؟
- هل يسأل توضيحاً؟ أم يرد بـ "أنا لا أفهم"؟ أم يختار الأعلى حتى لو منخفض؟

**تحكم أعمق في الكود:**
- في التصميم الحالي، **لا يوجد آلية واضحة لـ "طلب توضيح"**
- النظام إما يختار مساراً (حتى لو بنسبة منخفضة إذا كان هناك `else if` يأخذ الأعلى) أو يذهب لـ fallback عام
- **لا يسأل المستخدم خيارات محددة** مثل: "هل تقصد منتج جديد أم وكيل جديد؟"

**هذه هي أخطر مشكلة في التصميم الحالي لهذه الفئة.**

**توصية 2026 (الحل الصحيح):**

استخدم **Tool Calling مع معلمة `needsClarification` و `confidence`** في كل أداة، بالإضافة إلى **أداة خاصة للتوضيح**:

**الخطوة 1: أضف حقول التوضيح إلى كل أداة schema**
```typescript

        name: { type: "string", description: "اسم المنتج" },

        },

          type: "string",

        }

```

**الخطوة 2: أنشئ أداة خاصة للتوضيح نفسها**

**الخطوة 3: السماح للنموذج باختيار `ask_user_for_clarification`**

- أو اجعل `ask_user_for_clarification` ضمن قائمة الأدوات المتاحة للاختيار

**كيف سيعمل هذا على "اعمل واحد جديد":**

4. النموذج يختار استدعاء أداة `ask_user_for_clarification` بدلاً من أي أداة أخرى
5. الـ parameters ستكون شيئاً مثل:
   ```json
   {
     "possibleIntents": [
       {"intentName": "create_product", "userMessage": "إنشاء منتج جديد"},
       {"intentName": "spawn_agent", "userMessage": "إنشاء وكيل جديد"},

   }
   ```
6. نحن في الكود نرى أن الأداة المستدعاة هي `ask_user_for_clarification`
7. نعرض السؤال للمستخدم **بدلاً من القيام بأي إجراء افتراضي** أو تخمين خاطئ

**هذا هو سلوك 2026 الصحيح للأسئلة الغامضة.**

### السيناريو 1.4: الردود المتنوعة — عدم التكرار
**المعرف:** `BASIC-004`

**الخطوات:**
1. اسأل السؤال نفسه 3 مرات منفصلة
2. سجل كل رد
3. قارن بين الردود

**المدخلات المقترحة:**
- "عندنا كام منتج؟" × 3
- "ما هي تقارير اليوم؟" × 3

**النتيجة المتوقعة لو كان LLM generation حقيقي:**
- ✅ المعلومات نفسها
- ✅ الصياغة مختلفة قليلاً (طبيعة اللغة)
- ❌ ليس نفس الرد حرفياً كل مرة (علامة قوالب ثابتة)

**تحليل الكود الحالي:**

الملف: `backend/services/aiAgent/agentToolResultPresenter.js`

يحتوي على دوال مثل:
- `renderAttendance()`
- `renderAgentList()`
- `renderProductList()`
- `renderOrderSummary()`
- وغيرها

**مثال من الكود (تخميني بناءً على التحليل السابق):**
```javascript
const renderProductCount = (count) => {
  return `✅ لدينا حالياً **${count}** منتج في الكتالوج.
    
يمكنك البحث عن منتج معين أو سؤالي عن المنتجات الأكثر مبيعاً.`;
};
```

**المشكلة:**
- إذا استخدمت هذه الدوال، الرد **نفسه حرفياً كل مرة**
- هذا مؤشر واضح على أن الـ LLM **لا يستخدم في توليد الردود النهائية**
- المستخدم سيشعر أنه يتحدث مع روبوت قديم جداً (مثل ردود IVR الهاتفية)

**مقارنة:**
| نفس الرد حرفياً ×3 | ردود متنوعة بنفس المعلومات |
|---|---|
| ❌ علامة قوالب ثابتة | ✅ علامة LLM generation حقيقي |
| يشعر المستخدم بالروتينية | يشعر المستخدم بالطبيعية |
| لا يحتاج إلى API calls في كل مرة | يحتاج إلى API call في كل مرة |

**توصية 2026:**

**النهج المختلط (Hybrid Approach) الأفضل:**

1. **الاحتفاظ بالقوالب كـ Fallback فقط (ولا تستخدمها عادة):**
   - إذا فشل الـ LLM (مثلاً: timeout، error، rate limit)
   - فقط في هذه الحالة، استخدم القالب الثابت

2. **في الحالة العادية: استخدم LLM لإنشاء الرد:**
   - أنشئ ملف تعريف شخصية موحد (`ceoPersona.js`)
   - قم بتحويل دوال الـ rendering الحالية إلى دوال **Data Extractor** لا **Response Generator**
   - يعني: تجعل الدالة تعيد كائن JSON ببيانات نظيفة، لا نص جاهز

**مثال على التحسين:**

```typescript
// قبل (قديم — Response Generator):
const renderProductCount = (count) => {
  return `✅ لدينا حالياً **${count}** منتج في الكتالوج.
    
يمكنك البحث عن منتج معين أو سؤالي عن المنتجات الأكثر مبيعاً.`;
};

// بعد (حديث 2026 — Data Extractor):
const extractProductCountData = (rawData) => {
  // فقط تنظيف البيانات وإخراجها بشكل منظم
  return {
    totalProducts: rawData.total || 0,
    lastUpdated: rawData.timestamp || new Date().toISOString(),
    context: rawData.context || "general"
  };
};

// ثم في مكان آخر (Response Generation via LLM):
const generateResponse = async (extractedData, userHistory, persona) => {
  const response = await openai.chat.completions.create({
    model: "openai/gpt-oss-120b",
    messages: [
      { role: "system", content: persona },
      ...userHistory,
      { 
        role: "user", 
        content: `هذه البيانات من نظام المنتجات:
${JSON.stringify(extractedData, null, 2)}

صيغ لي رداً مناسباً للمدير باللغة العربية. اجعله طبيعياً وليس روتينياً.`
      }
    ],
    temperature: 0.6, // بعض التنوع ولكن ليس كثيراً
    max_tokens: 300
  });
  
  return response.choices[0].message.content;
};
```

**نصائح إضافية للـ Response Generation:**
- للردود العادية: `temperature: 0.5 - 0.7`
- للتقارير الرسمية: `temperature: 0.2 - 0.3` (أقل تنوعاً، أكثر دقة)
- للأفكار الإبداعية: `temperature: 0.8 - 0.9`
- استخدم **Few-Shot Examples** في الـ system prompt لجعل الأسلوب متسقاً

**مستوى الخطورة:** متوسط (يؤثر على تجربة المستخدم وليس الوظيفية)

#### السيناريو 2.1.1: استعلامات HR — الحضور

```typescript
// - تُستخدم للـ context المباشر للرسائل
// - تُفسر عند "إغلاق المحادثة" أو بعد فترة
interface ThreadMemory {

  messages: Message[];
  createdAt: Date;
  expiresAt: Date;
}

// 2. User Memory (الذاكرة الخاصة بالمستخدم عبر كل المحادثات)
// - تُستخدم للـ Continuity عبر الجلسات
// - لا تنتهي صلاحيتها (أو تنتهي بعد شهور طويلة)
interface UserMemory {
  userId: string;
  companyId: string;
  
  // العمل الجاري غير المكتمل
  activeTasks: ActiveTask[];
  
  // التفضيلات المتعلمة
  preferences: UserPreferences;
  
  // ملخص المحادثات السابقة (مختصر)
  conversationSummaries: ConversationSummary[];

interface ActiveTask {
  id: string;

  collectedData: Record<string, any>;
  lastInteractionAt: Date;
  conversationLink: string; // ربط بالمحادثة الأصلية
}

// 3. Global/Knowledge Memory (ذاكرة عامة للشركة)
// - لا تتعلق بمستخدم معين
// - مثل: معلومات عن المنتجات، السياسات، الإجراءات القياسية
interface CompanyMemory {
  companyId: string;
  // ...
}
```

1. حمل `UserMemory` الخاص به
2. تحقق من `activeTasks`
3. إذا كانت هناك مهام غير مكتملة حديثة:

4. أو انتظر أن يسأل المستخدم عنها صراحة

### السيناريو 4.1: استخدام المهارة الموجودة
**المعرف:** `HERMES-001`
**المفهوم:** Skills as Procedural Memory

**المتطلبات الأولية:** يجب أن تكون فيه مهارة مسجلة مسبقاً (مثلاً: مهارة "مراقبة المخزون")

**المدخلات المقترحة:**
1. "استخدم مهارة مراقبة المخزون"
2. "شغل مهارة تقارير الفيسبوك"
3. "نفذ المهارة اللي اسمها X"

**النتيجة المتوقعة:**
- ✅ يتعرف على اسم المهارة
- ✅ يحمل تعليمات المهارة
- ✅ ينفذ الخطوات المطلوبة

**التحليل العميق:**

هذا السيناريو يختبر **بنية نظام المهارات**

الأسئلة:
1. **ماهي "المهارة" في التنفيذ؟**
   - مجرد سجل في قاعدة البيانات بـ `name` و `description`؟
   - أم لها ملفات حقيقية على القرص؟ (`skill.json`, `SKILL.md`)
   
2. **ماذا يحدث عند "استخدام المهارة":**
   - هل يتم تحميل `SKILL.md` وإضافته إلى الـ System Prompt أو الـ Context؟
   - أم أن اسم المهارة مجرد routing لـ tools معينة؟
   - أم أنها لا تفعل شيء فعلياً؟

3. **هل هناك "ذاكرة إجرائية" للمهارة؟**
   - مثلاً: المهارة تتعلم من الأخطاء في المرات السابقة؟
   - أم أنها تنفذ نفس الخطوات بالأمس واليوم وغداً بدون تغيير؟

**تصور بسيط لنظام مهارات جيد:**

```

   - يمكن أن يكون هذا عبر Keyword (إذا كان بسيطاً) أو عبر Tool Calling

2. ✅ التحميل: يحمّل تعريفات المهارة من المصدر:
   - من قاعدة البيانات؟

3. ✅ الحقن في السياق:
   - يأخذ محتوى `SKILL.md` (الذي يحتوي على خطوات العمل مثلاً)
   - يضيفه إلى المحادثة كـ System Message أو Assistant Message
   - مثلاً: "أنت الآن تقوم بتنفيذ مهارة مراقبة المخزون. خطوات المهارة: 1. افحص المخزون المنخفض... 2. ..."
```

### السيناريو 4.2: إنشاء مهارة وتخصيصها لوكيل
**المعرف:** `HERMES-002`
**المفهوم:** Skill Creation + Agent Assignment

**الخطوات:**
1. اسأل إنشاء مهارة جديدة
2. قدم لها الـ trigger phrases و steps
3. عينها على وكيل محدد
4. اختبر أن الوكيل يستخدمها

**المدخلات المقترحة:**
1. "اعمللي مهارة جديدة اسمها 'متابعة الطلبات المتأخرة'"
2. "عطي المهارة لوكيل المخزون"
3. سأل الوكيل: "نفذ مهارة متابعة الطلبات"

**التحليل:**

هذا سيناريو **متقدم جداً** ويختبر:
1. إنشاء المهارة (كتابة `skill.json` و `SKILL.md`)
2. ربط المهارة بالوكيل
3. استرجاع المهارة عند الحاجة

**التساؤلات:**
- عند قول "اعمللي مهارة جديدة"، هل يفهم النظام أنه يحتاج لجمع معلومات عن:
  - اسم المهارة؟
  - وصفها؟
  - خطواتها؟
  - الـ trigger phrases؟
  - الأدوات المسموح لها؟

- عندما يخلق المهارة:
  - هل يكتب ملفات حقيقية؟
  - أم مجرد سجل في قاعدة بيانات؟

- عندما "يعطي المهارة لوكيل المخزون":
  - ماذا يعني هذا الربط؟
  - هل يضيف الـ trigger phrases للوكيل؟
  - هل يضيف المهارة إلى "المهارات المتاحة" للوكيل في ذاكرته؟

**توصية للتنفيذ التدريجي:**

لا تحاول بناء نظام مهارات كامل يتعلم ذاتياً من البداية (Self-improving). ابدأ ببساطة:

**المرحلة 1 (الآن): المهارات اليدوية**
- المهارات يخلقها المطور يدوياً عبر كتابة `skill.json` و `SKILL.md`
- يتم تحميلها عند الحاجة
- لا يوجد إنشاء مهارات عبر المحادثة بعد

**المرحلة 2 (قريباً): الإنشاء عبر المحادثة**
- يمكن للمستخدم قول "خلق لي مهارة جديدة"
- النظام يسأله المعلومات الأساسية
- النظام يكتب الملفات أو قاعدة البيانات
- لكن لا يوجد تعيين لوكيل بعد

**المرحلة 3 (لاحقاً): التعيين والربط**
- ربط المهارات بالوكلاء
- تحميل المهارات التابعة للوكيل عند بدء المحادثة معه

**المرحلة 4 (المستقبل): التطوير الذاتي (Self-improving)**
- بعد تنفيذ المهارة، يتم تقييم النتيجة
- يتم كتابة `lessons-learned.md`
- المرة القادمة، المهارة ستكون أفضل

**مستوى الخطورة:** منخفض (هذا feature متقدم جداً وليس أساسي لـ MVP)

### السيناريو 5.1: الموافقة — أدوات الكتابة لا تنفذ مباشرة
**المعرف:** `PAPERCLIP-001`
**المفهوم:** Human-in-the-Loop Approvals for Write Tools

**الأدوات التي يجب أن تتطلب موافقة (من tool-registry.json):**
1. `agent.spawn` — موافقة
2. `skill.create` — موافقة
3. `product.create` — موافقة
4. `product.updatePrice` — موافقة
5. `order.create_draft` — موافقة

**الاختبار المقترح:**
جرب أي من هذه الأوامر وتأكد أنها لا تنفذ مباشرة:
1. "اعمل وكيل جديد" — هل يروح لـ approval أم ينفذ مباشرة؟
2. "انشئ منتج جديد" — هل يروح لـ approval أم ينفذ مباشرة؟
3. "الغي الطلب رقم X" — هل يروح لـ approval أم ينفذ مباشرة؟

**النتيجة المتوقعة:**
- ✅ تنشئ مسودة (draft) فقط
- ✅ تتطلب موافقة من خلال `humanApprovalService`
- ✅ لا تغير قاعدة البيانات بدون موافقة

**التحليل المعمق — هذا الأهم في كله:**

السؤال المحوري:
> هل الحقل `requiresApproval: true` في `tool-registry.json` مجرد **وصف توثيقي**؟
> أم أنه **يغير فعلياً سلوك التنفيذ** في الكود؟

**السيناريوهان:**

**السيناريو A (السيئ): مجرد وصف**
- المطور كتب `requiresApproval: true` في الـ JSON للتوثيق فقط
- في الكود، عند اختيار الأداة، يتم استدعاء الـ handler مباشرة بدون أي تحقق
- النتيجة: "اعمل وكيل جديد" → ينشئ الوكيل فوراً بدون أي مسودة أو موافقة
- **هذا خطر كبير جداً**

**السيناريو B (الجيد): مفعّل في التنفيذ**
- في `CEOAgent.js` أو في `toolExecutionService.js`:
  - قبل تنفيذ أي أداة، يتم فحص `tool.requiresApproval`
  - إذا كانت `true`:
    1. لا يتم استدعاء الـ handler الأصلي للأداة
    2. بدلاً من ذلك: يتم إنشاء `Draft` في قاعدة البيانات
    3. يتم إرجاع رسالة للمستخدم: "لقد قمت بإعداد مسودة الإجراء... هل تريد الموافقة والتشغيل، التعديل، أم الإلغاء؟"
  - إذا كانت `false` (Read-only tools عادة):
    1. يتم التنفيذ مباشرة

```
│     │      ┌► تحديث Draft.status: "approved"   │                │

│     │         مع الـ params المحفوظة           │                │
│     │                                          │                │
│     │    - إذا قال "عدل" أو "2":              │                │
│     │      └► ادخل حوار تعديل المسودة          │                │
│     │                                          │                │
│     │    - إذا قال "ألغِ" أو "3":             │                │
│     │      └► تحديث Draft.status: "cancelled"  │                │
│     │         وأخبر المستخدم بالإلغاء          │                │
│     │                                          │                │
│     └─────────────────────────────────────────┘                │
│                          │                                      │
│                          ▼                                      │
│           if (tool.requiresApproval === false)                 │
│           (Read-only tools مثل hr.attendance_today)            │
│                          │                                      │
│                          ▼                                      │
│           8. التنفيذ المباشر دون موافقة                        │
│              استدعاء الـ handler مباشرة                        │
│              عرض النتيجة على المستخدم                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**نقاط إضافية مهمة لـ Paperclip-style:**

1. **سجل المسودات (Draft Log):**
   - كل مسودة يجب أن تُحفظ مع:
     - من أنشأها؟
     - متى أنشأتها؟
     - ما هي الـ parameters؟
     - ما هي الحالة النهائية (approved, cancelled, modified)؟
     - من وافق أو ألغى؟

2. **سجل التدقيق (Audit Trail — انظر السيناريو 5.2):**
   - كل إجراء (حتى إنشاء المسودة) يجب أن يُسجل في الـ Audit
   - هذا سجيل **append-only** (لا يمكن الحذف أو التعديل عليه)

3. **الموافقات المتعددة (Multi-level Approvals) — متقدم:**
   - بعض الإجراءات قد تحتاج موافقة شخصين مختلفين
   - مثلاً: خصم أكثر من 20% يحتاج موافقة مدير المبيعات ثم المدير المالي
   - هذا يمكن إضافته لاحقاً، لكن المفاهيم الأساسية للمسودة والموافقة هي نفسها

**مستوى الخطورة:** **عالية جداً**
- هذا يتعلق بسلامة البيانات والعمليات
- إذا تم تنفيذ إجراء خطأ بدون موافقة، قد يكون من الصعب تراجعه
- Paperclip concept في الأساس هو **التحكم والسلامة والمراقبة**

### السيناريو 5.2: سجل التدقيق — Audit Trail
**المعرف:** `PAPERCLIP-002`
**المفهوم:** Append-only Audit Trail لكل قرار

**الأداة:** `audit.read`

**الخطوات:**
1. نفذ أي عملية (حتى read-only)
2. سأل سجل التدقيق: "أخر 5 عمليات؟" أو "سجل العمليات اليوم؟"
3. أو استخدم الأداة مباشرة: استدعاء `audit.read`

**المدخلات المقترحة:**
1. "سجل عمليات اليوم؟"
2. "أخر 10 قرارات؟"
3. "عرض الـ audit trail"

**النتيجة المتوقعة:**
- ✅ كل عملية مسجلة مع timestamp
- ✅ يظهر من قام بالإجراء (userId)
- ✅ يظهر الأداة المستخدمة والنتيجة
- ✅ يظهر الـ companyId للعزل (انظر السيناريو 5.3)

**ما الذي يجب تسجيله في كل إجراء Audit:**

```typescript
interface AuditRecord {
  id: string;           // UUID
  companyId: string;    // للعزل بين الشركات (Multi-tenant)
  userId: string;       // من قام بالإجراء
  sessionId: string;    // المحادثة التي حدث فيها (اختياري)
  
  action: {
    type: "tool_call" | "message_sent" | "draft_created" | "draft_approved" | "draft_cancelled" | "login" | "logout";
    toolName?: string;      // إذا كان tool_call
    draftId?: string;       // إذا كان يتعلق بمسودة
    params?: Record<string, any>;  // المعاملات (يجب تعميتها إذا كانت حساسة مثل كلمات المرور)
  };
  
  result: {
    success: boolean;
    errorMessage?: string;
    summary?: string;       // ملخص مختصر للنتيجة
  };
  
  timestamp: Date;
  
  // مفتاح: هذا السجل غير قابل للتعديل أو الحذف بعد إنشائه
  // Append-only
  immutable: true;
}
```

**الأسئلة للتحقق من الكود:**

1. **متى يتم الكتابة في Audit:**
   - قبل تنفيذ الإجراء أم بعده؟
   - أم كلاهما (بداية ونهاية)؟
   - مثالي: تسجيل البدء، ثم تسجيل النهاية مع النتيجة

2. **ماذا يحدث في حالة الخطأ:**
   - هل يتم تسجيل الفشل في Audit أيضاً؟
   - أم يتم تسجيل النجاحات فقط؟
   - يجب تسجيل **كل شيء** بما في ذلك الأخطاء

3. **القراءة من Audit:**
   - عند سؤال "أخر 5 عمليات"، هل يفلتر تلقائياً بـ `companyId` الخاص بالمستخدم؟
   - أم يمكنه رؤية عمليات شركات أخرى؟ (هذا خطأ أمني كبير إذا حدث)

4. **Append-only:**
   - هل هناك طريقة لتعديل أو حذف سجل Audit بعد إنشائه؟
   - يجب ألا تكون هناك (أو تكون مقتصرة على أدمن سوبر بمفاتيح خاصة)

**توصية:**

إذا لم يكن هناك نظام Audit Trail حقيقي بعد، فالحد الأدنى الذي يجب فعله:

```typescript
// على الأقل، سجل كل استدعاء أداة في ملف نصي أو قاعدة بيانات بسيطة
const logToolCall = async (
  companyId: string,
  userId: string,
  toolName: string,
  params: Record<string, any>,
  success: boolean,
  resultSummary: string
) => {
  const record = {
    timestamp: new Date().toISOString(),
    companyId,
    userId,
    toolName,
    params: sanitizeParams(params), // إزالة الحقول الحساسة
    success,
    resultSummary: resultSummary.substring(0, 200) // ملخص مختصر
  };
  
  // اكتب في قاعدة البيانات أو في ملف logs
  await db.auditLogs.create(record);
  // أو: await appendToLogFile(`audit-${companyId}.log`, JSON.stringify(record));
  
  console.log(`[AUDIT] ${toolName} by ${userId}@${companyId}: ${success ? 'SUCCESS' : 'FAILED'}`);
};
```

ثم بعد كل تنفيذ أداة (نجاح أو فشل):
```typescript
await logToolCall(
  companyId,
  userId,
  toolName,
  params,
  executionResult.success,
  executionResult.summary || executionResult.errorMessage
);
```

**مستوى الخطورة:** عالي (للأمن والتتبع والامتثال)

### السيناريو 5.3: عزل الشركات — Company Scoping
**المعرف:** `PAPERCLIP-003`
**المفهوم:** Multi-tenant Isolation

**الاختبار النظري:**
- هل كل أداة فيها `companyScoped: true`؟
- هل من الممكن لشركة A أن ترى بيانات شركة B؟

**التحقق من tool-registry.json (من ملف السيناريوهات السطر 338):**
> ✅ كل الأدوات فيها `"companyScoped": true`

**نقاط التأكد الإضافية (من السطر 339-341):**
- ✅ `workingMemoryService` يفلتر بـ companyId؟
- ✅ `episodicMemoryService` يفلتر بـ companyId؟
- ✅ كل أدوات الـ catalog و orders بفلتر companyId في الـ handler؟

**تحليل أعمق لعزل الشركات:**

هذا هو **الأساس في أي نظام Multi-tenant**

المخاطر الرئيسية:
1. **Injection في الـ queries:**
   - مثلاً: `SELECT * FROM products WHERE companyId = ?`
   - إذا لم يتم تمرير companyId بشكل صحيح أو تمكن المستخدم من التلاعب به → **تسرب بيانات**

2. **الذاكرة:**
   - عند حفظ شيء في `workingMemory` أو `episodicMemory`
   - هل يتم الفهرسة بـ companyId دائماً؟
   - عند الاسترجاع: هل يتم الفلتر بـ companyId دائماً؟

3. **ملفات المساحة:**
   - إذا كان نظام ملفات للمساحة (OpenClaw-style)
   - هل مساحة كل شركة في مجلد منفصل؟
   - `workspaces/company-A/` vs `workspaces/company-B/`
   - هل هناك تحقق أن المستخدم لا يمكنه الوصول لمجلد شركة أخرى؟

4. **Audit Trail (السيناريو السابق):**
   - عند قراءة Audit، هل يفلتر تلقائياً بـ companyId؟
   - أم يمكن لشركة رؤية audit شركة أخرى؟

**القاعدة الذهبية لعزل الشركات:**

> **لا تثق أبداً في أن الـ frontend أو المستخدم سيمرر companyId بشكل صحيح.**
> **دائماً احصل على companyId من الجلسة المصادقة (Authenticated Session) وليس من الـ parameters أو الـ body.**

**مثال على الكود الخطأ:**
```typescript
// ❌ خطأ: companyId مأخوذ من الـ parameters التي يرسلها المستخدم
app.get('/api/products', async (req, res) => {
  const companyId = req.query.companyId; // المستخدم يمكنه تغيير هذا!
  const products = await db.products.findMany({ where: { companyId } });
  res.json(products);
});
```

**مثال على الكود الصحيح:**
```typescript
// ✅ صحيح: companyId مأخوذ من الـ JWT token أو Session
app.get('/api/products', async (req, res) => {
  const companyId = req.authenticatedUser.companyId; // من الـ session بعد الـ login
  const products = await db.products.findMany({ where: { companyId } });
  res.json(products);
});
```

**تطبيق هذا المبدأ على الـ Agent:**

في `CEOAgent.js` وجميع الخدمات:
- `companyId` يجب أن يأتي من **جلسة المستخدم المصادقة** فقط
- لا يجب أن يكون قابلاً للتمرير عبر رسالة المستخدم أو parameters الأدوات

إذا كان هناك أداة تحتاج إلى عمل شيء يتعلق بشركة أخرى (سيناريو متقدم جداً مثل Admin Super)، يجب أن يكون لديه صلاحيات خاصة جداً وفصل تام.

**نقاط للفحص في الكود الحالي:**

1. ابحث عن `companyId` في الكود:
   - كيف يتم تمريره؟
   - هل يأتي من `req.user.companyId` أو `session.companyId`؟
   - أم يأتي من `body.companyId` أو `query.companyId`؟

2. في `workingMemoryService.save()` و `recall()`:
   - هل هناك `companyId` في الـ parameters؟
   - هل يتم الفلترة به دائماً؟

3. في استعلامات قاعدة البيانات (Products, Orders, Agents, إلخ):
   - هل كل استعلام يحتوي على `{ where: { companyId: ... } }`؟
   - أم هناك استعلامات بدون هذا الفلتر؟

**مستوى الخطورة:** **عالية جداً — حرجة**
- هذا يتعلق بالأمن وخصوصية البيانات بين الشركات
- إذا تم اختراق العزل، شركة ترى بيانات شركة أخرى → كارثة
- Paperclip concept يضع Company Isolation كـ First-class Concern

### السيناريو 6.1: Tool-Based Intent Classification (بدلاً من Keywords)
**المعرف:** `TECH-2026-001`
**التقنية:** Native Tool Calling as Intent Classifier (2026 SOTA)

**المشكلة الحالية (المذكورة في السطر 353 من ملف السيناريوهات):**
> Keyword-based: "اعمل" موجود في 6 مصفوفات مختلفة → تعارض

**المدخلات لنفس النية (إنشاء منتج) لتجربة الـ routing:**
1. "عايز اضيف منتج جديد"
2. "انشئ لي حذاء"
3. "اعمللي كوتشي جديد"
4. "حط منتج جديد في الكتالوج"
5. "أريد إضافة سلعة للمخزون"
6. "Add a new product" (إنجليزي)

**النتيجة المتوقعة (2026 SOTA):**
- ✅ الكل يروح لنفس النية (`products.manage` أو `product.create`)
- ✅ لا يعتمد على وجود كلمة معينة
- ✅ يفهم السياق (كلمة "حذاء" → منتج)

**النتيجة الحالية (Keyword-based) — المتوقعة:**
- ⚠️ قد تفشل بعض الصياغات لأنها لا تحتوي على الكلمات في `PRODUCT_CREATION_HINTS`
- الصياغة 6 "Add a new product" → **شبه مؤكد أن تفشل** لأن الكلمات الإنجليزية غير موجودة في الـ hints

**التحليل المقارن:**

| الميزة | Keyword-based (الحالي) | Tool Calling (2026) |
|---|---|---|
| **فهم المعنى** | ❌ لا، فقط مطابقة نصية | ✅ نعم، يفهم المعنى والسياق |
| **تداخل الكلمات ("اعمل" في 6 مصفوفات)** | ❌ مشكلة كبيرة → routing خاطئ | ✅ لا مشكلة → النموذج يفهم بناءً على الجملة كاملة |
| **اللهجات المختلفة** | ❌ يفشل ما لم تكن الكلمات في الـ hints | ✅ يفهم بشكل طبيعي |
| **الأخطاء الإملائية** | ❌ حساس جداً | ✅ متسامح بشكل طبيعي |
| **اللغة المختلطة (عربي+إنجليزي)** | ❌ غالباً يفشل | ✅ يفهم بشكل طبيعي |
| **استخراج الـ parameters** | ❌ يحتاج إلى NER منفصل أو Regex | ✅ مدمج في الـ JSONSchema |
| **صيانة الكلمات المفتاحية** | ❌ عمل مستمر ومتعب | ✅ لا توجد كلمات مفتاحية لتصيانها — فقط اكتب description جيد |
| **الوقت المطلوب لإضافة Intent جديد** | - إضافة مصفوفة كلمات جديدة<br>- تعديل الـ weights والـ thresholds<br>- تعديل الـ routing code | - كتابة Tool definition (JSONSchema + description)<br>- إضافتها للـ tools array |

**مثال توضيحي لقوة Tool Calling في هذه الحالة:**

**المدخل:** "اعمللي كوتشي جديد"

**تحليل Keyword-based (المتوقع):**
- البحث عن الكلمات:
  - "اعمل" → موجودة في 6 مصفوفات (marketingCampaign, productCreation, agentSpawning, ...)
  - "كوتشي" → غير موجود في أي مصفوفة على الأرجح (إذا لم يكن مضافاً بشكل يدوي)
  - "جديد" → موجودة في عدة مصفوفات
- النتيجة: **تعتمد على الترتيب** وليس المعنى. ربما تذهب لأول مصفوفة تحتوي على "اعمل" وليس بالضرورة لإنشاء المنتج.

**تحليل Tool Calling (المتوقع):**
- النموذج يرى تعريف أداة `create_product`:
  ```
  description: "عندما يريد المستخدم إنشاء منتج جديد أو إضافة سلعة للمخزون أو تحديث الكتالوج"
  ```
- النموذج يفهم أن "كوتشي" هو نوع من **الأحذية** وهو **منتج**
- النموذج يفهم أن "اعمللي ... جديد" تعني **إنشاء**
- النتيجة: ✅ يختار أداة `create_product` بثقة عالية
- وعلاوة على ذلك: يقوم بملء الـ parameters:
  ```json
  {"name": "كوتشي", "confidence": 0.9, "needsClarification": false}
  ```
  أو ربما:
  ```json
  {"name": "كوتشي", "confidence": 0.85, "needsClarification": true, "clarificationReason": "لم يذكر السعر والمخزون"}
  ```

**هذا هو الفرق الجوهري بين عامي 2020 و 2026 في هندسة الـ Agents.**

**توصية نهائية لهذا السيناريو:**

**هجرة كاملة من Keyword-based إلى Tool Calling-based Intent Classification:**

1. **المرحلة الأولى (الأسبوع 1-2):**
   - أنشئ تعريفات Tools لكل Intent موجود
   - اجعل النظام القديم يعمل كـ Fallback إذا فشل الـ API
   - اختبرها على السيناريوهات في هذه الفئة

2. **المرحلة الثانية (الأسبوع 3-4):**
   - تحويل الـ routing الأساسي ليستخدم Tool Calling أولاً
   - مراقبة النتائج وحل المشاكل
   - إزالة الـ Keyword-based تدريجياً من المسارات الرئيسية

3. **المرحلة الثالثة (الأسبوع 5+):**
   - الاحتفاظ بـ Keyword-based فقط كـ Fallback طوارئ
   - جميع المسارات الجديدة تستخدم Tool Calling
   - إضافة intents جديدة فقط عبر Tool definitions

**مستوى الخطورة/الأهمية:** **عالية جداً — هذا هو التغيير الجذري الأهم**

- السؤال: هل هناك مسار محدد سلفاً لهذا النوع من المهام المركبة؟
- أم أن الـ LLM لديه الحرية الكاملة لاختيار أي أداة وأي ترتيب في أي وقت؟

**التحليل المعمق:**

المشكلة مع **Deterministic Paths مثل:**
```javascript
if (intentResult.marketingCampaign >= 0.7) {
  executionPlan = [
    'create_facebook_campaign',
    'launch_ad_group',
    'write_ad_copy',
    'generate_visuals',
    'start_campaign',
    'generate_report'
  ];
}
```

هي أن:
1. **الخطة محددة قبل فهم الطلب تماماً:**
   - المستخدم قد يقول "فقط أنشئ الحملة ولا تضيف إعلانات بعد"
   - لكن المسار ثابت وسوف يضيف الإعلانات

2. **لا تكيف مع النتائج:**
   - إذا فشلت خطوة (مثلاً: إنشاء الحملة فشل)
   - هل المسار يتغير؟ أم يستمر بنفس الخطة؟

3. **لا يمكن للنموذج أن يقترح مساراً غير متوقع:**
   - في مثالنا: مقارنة مبيعات شهرين ثم إرسال واتساب
   - إذا لم يكن هناك مسار محدد لهذا المزيج تحديداً → ماذا يحدث؟

**نمط 2026 الصحيح: ReAct Loop أولاً وأخيراً بدون مسارات حتمية:**

```
┌─────────────────────────────────────────────────────────────┐
│                    ReAct Loop (نموذج 2026)                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  while (not finished and iterations < maxIterations) {      │
│                                                             │
│    1. أرسل المحادثة الكاملة للنموذج مع قائمة الأدوات      │
│                                                             │
│    2. النموذج يختار إحدي خيارين فقط:                      │
│       ┌─ Option A: استدعاء أداة (tool_calls موجود)        │
│       │         ├ـ نحدد الأداة والـ parameters             │
│       │         ├ـ ننفذ الأداة في الكود                    │
│       │         └ـ نضيف النتيجة إلى المحادثة كنص Role=Tool│
│       │                                                     │
│       └─ Option B: إنهاء والرد النهائي                     │
│                (لا يوجد tool_calls → الـ content هو الرد)  │
│                                                             │
│    3. نعود للبداية                                          │
│                                                             │
│  }                                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**المفتاح في هذا النمط:**
> **لا توجد `if/else if` تحدد المسار قبل النموذج.**
> **الوحيد الذي يقرر ماذا يفعل بعد هو النموذج بناءً على كل ما حدث حتى الآن.**

**مثال تطبيقي على مهمتنا "قارن المبيعات وأرسل واتساب":**

**التكرار 1:**
- النموذج يرى الرسالة + الأدوات
- يحدد أنه يحتاج أولاً إلى مبيعات الشهر الحالي
- يختار أداة `sales.revenue` مع parameter `period: "current_month"`
- ننفذ الأداة، نحصل على النتيجة: `{ revenue: 50000, orders: 120, avgOrder: 417 }`
- نضيف هذه النتيجة إلى المحادثة

**التكرار 2:**
- النموذج يرى الرسالة الأصلية + نتيجة التكرار 1
- يحدد أنه يحتاج الآن إلى مبيعات الشهر الماضي للمقارنة
- يختار أداة `sales.revenue` مع parameter `period: "last_month"`
- ننفذ الأداة، نحصل على: `{ revenue: 45000, orders: 100, avgOrder: 450 }`
- نضيفها للمحادثة

**التكرار 3:**
- النموذج يرى كل ما سبق
- يحلل المقارنة "ذهنياً" (لا يستدعي أي أداة للتحليل إذا لم تكن موجودة)
  - إيرادات زادت 5000 جنيه (+11%)
  - الطلبات زادت 20 طلب (+20%)
  - لكن متوسط قيمة الطلب انخفض من 450 إلى 417 جنيه
- يحدد أنه الآن يحتاج إلى إرسال هذا الملخص عبر الواتساب
- يختار أداة `whatsapp.send` مع:
  ```json
  {
    "phoneNumber": "01012345678",
    "message": "📊 تقرير مقارنة المبيعات:\n\n✅ الشهر الحالي: 50,000 جنيه (120 طلب)\n📅 الشهر الماضي: 45,000 جنيه (100 طلب)\n\n📈 الزيادة: 5,000 جنيه (+11%)\n⚠️ انخفاض متوسط الطلب: من 450 لـ 417 جنيه"
  }
  ```
- ننفذ الأداة، نحصل على النتيجة: `{ success: true, messageId: "..." }`
- نضيفها للمحادثة

**التكرار 4:**
- النموذج يرى كل ما سبق
- يحدد أن المهمة انتهت بنجاح
- لا يختار أي أداة (لا tool_calls)
- بدلاً من ذلك، يكتب رداً نهائياً للمستخدم:
  > "✅ تمت المهمة بنجاح!\n\nلقد قارنت بين مبيعات الشهر الحالي والشهر الماضي، وقمت بإرسال ملخص المقارنة عبر الواتساب إلى الرقم 01012345678.\n\nهل تريد مني أي تفاصيل إضافية؟"

**هذا هو سلوك 2026 الصحيح للمهام المركبة متعددة الخطوات.**

**مستوى الخطورة/الأهمية:** **عالية جداً**
- بدون هذا، الوكيل محدود بالمسارات التي خطط لها المطور
- مع هذا النمط، الوكيل يمكنه التعامل مع مهام لم يخطط لها المطور تحديداً

### السيناريو 6.3: فهم اللغة المختلطة (Arabizi + Code-switching)
**المعرف:** `TECH-2026-003`
**التقنية:** Modern NLP تتفهم code-switching بشكل طبيعي

**المدخلات المقترحة:**
1. "عندي product اللي مخزونو less than 10 — send alert"
2. "run الـ sales report لـ today و compare مع yesterday"
3. "update الـ price لـ product ID 123 لـ 550 جنيه"
4. "شوف الـ low stock products و create discount 10% لهم"
5. "agent اللي اسمه شيرين — assign لها task جديد"

**النتيجة المتوقعة (2026):**
- ✅ يفهم الصياغة المختلطة بشكل طبيعي
- ✅ ي route للنية الصحيحة
- ✅ يستخرج المعاملات بشكل صحيح

**النتيجة الحالية (Keyword-based) — المتوقعة:**
- ⚠️ احتمالية عالية للفشل لأن الكلمات الإنجليزية مش في مصفوفات الـ hints

**تحليل كل مدخل مقابل نظام Keyword-based:**

| المدخل | الكلمات الإنجليزية فيه | ماذا يفعل Keyword-based غالباً؟ | ماذا يفعل Tool Calling؟ |
|---|---|---|---|
| "عندي product اللي مخزونو less than 10" | product, less than | يفهم "مخزون" ربما، لكن "product" و "less than" لا → routing غامض أو خاطئ | يفهم أن "product" يعني منتج، "less than 10 مخزون" يعني منخفض → يختار `inventory.check` أو `product.lowStock` |
| "run الـ sales report لـ today" | run, sales report, today | "تقرير" أو "مبيعات" قد تكون موجودة، لكن "sales report" بالإنكليزي لا | يفهم تماماً → `sales.revenue` أو `order.summary` |
| "update الـ price لـ product ID 123" | update, price, product, ID | "سعر" و "منتج" قد تكون موجودة، لكن "update" و "ID" لا | يفهم → `product.updatePrice` مع parameters `productId: "123"` و `newPrice: ...` |
| "شوف الـ low stock products" | low stock, products | "مخزون قليل" قد تكون موجودة أو لا | يفهم تماماً → `product.lowStock` |
| "agent اللي اسمه شيرين — assign لها task" | agent, assign, task | "وكيل" قد تكون موجودة، لكن "assign" و "task" لا | يفهم → يتعلق بالوكلاء، ربما `agent.list_agents` أو `agent.read_state` أو `agent.assign_task` إذا كانت موجودة |

**نقطة مهمة:**
هذه المشكلة **لا يمكن حلها بشكل كامل بإضافة المزيد من الكلمات المفتاحية** لأن:
- Code-switching يمكن أن يكون بأي نمط (كلمة إنجليزي، جملة عربية، إلخ)
- الإنجليزية يمكن أن تكون متعربة ("رن" بدلاً من "run")
- الكلمات الجديدة تظهر كل يوم

**الحل الوحيد المستدام في 2026 هو أن يفهم النموذج اللغة مباشرة، وليس الاعتماد على مطابقة الكلمات.**

**مستوى الخطورة/الأهمية:** عالي إلى متوسط
- يعتمد على مدى استخدام المستخدمين لهذا النمط من الكلام
- إذا كانوا غالباً يكتبون بالعربي الفصحى، المشكلة أصغر
- إذا كانوا يمزجون، فهي مشكلة كبيرة

### السيناريو 6.4: التفكير المنطقي (Reasoning) قبل الإجراء
**المعرف:** `TECH-2026-004`
**التقنية:** Model reasoning قبل tool calling (2026 models تستخدم reasoning chains بشكل أفضل)

**السيناريو:**

> **"العميل محمد اشترى حذاء ب 800 جنيه، والآن عايز يستبدله بحذاء ب 600 جنيه. ايه اللي أصح إعمله؟"**

**الـ Reasoning المنطقي المطلوب:**
1. العميل دفع 800 جنيه
2. المنتج الجديد بسعر 600 جنيه
3. الفرق: 800 - 600 = **200 جنيه**
4. الأسئلة المنطقية قبل أي إجراء:
   - ما هي سياسة الاستبدال في الشركة؟
   - هل المنتج الأصلي مشروط بالاستبدال؟ (مثلاً: لم يستخدمه، الفاتورة موجودة، خلال 14 يوم؟)
   - ماذا يفعل بالـ 200 جنيه؟ هل يسترد نقداً؟ أم يظل رصيد للمشتريات القادمة؟
   - هل يحتاج هذا الإجراء إلى موافقة؟

**النتيجة المتوقعة (2026):**
- ✅ يحلل الموقف منطقياً
- ✅ يسأل المعلومات الناقصة
- ✅ يقترح الإجراء المناسب
- ❌ لا يقفز مباشرة لأداة `order.refund` بدون تفكير

**ماذا من المفترض أن يقول الوكيل المثالي:**
> "فهمت الحالة. قبل أن أتمكن من مساعدتك، أحتاج لبعض المعلومات الإضافية:
> 
> 1. هل المنتج الأصلي في حالته الأصلية ولم يستخدم؟
> 2. هل لدى العميل الفاتورة؟
> 3. كم مضى على عملية الشراء؟ (سياسة الاستبدال خلال 14 يوم مثلاً)
> 4. ماذا يفضل العميل بخصوص المبلغ المتبقي (200 جنيه)؟ استرداد نقدي أم رصيد؟
> 
> وبعد ذلك، يمكنني مساعدتك في إجراء الاستبدال بشكل صحيح."

**تحليل التصميم الحالي:**

السؤال:
> ماذا يحدث إذا قال المستخدم "استبدال" أو "استرداد"؟

في نظام Keyword-based + Deterministic Paths:
1. كلمة "استبدال" أو "استرداد" تطابق كلمات مفتاحية معينة
2. النظام يحدد الـ intent (ربما `order.refund` أو `order.cancel` أو مشابه)
3. النظام يتبع المسار الثابت لهذا الـ intent
4. **قد يقفز مباشرة لجمع معلومات لاسترداد بدون تحليل الموقف أو طرح الأسئلة المنطقية**

المشكلة:
- في مثالنا، هذا ليس استرداد كاملاً. هذا استبدال بفرق سعر.
- إجراء `order.refund` قد يكون غير مناسباً تماماً أو يحتاج لتعديل.
- النموذج يجب أن يفهم هذا الفرق المنطقي.

**توصية 2026 لتحسين الـ Reasoning:**

**الخيار 1: استخدام نموذج أفضل في الـ Reasoning (إذا كان متوفراً)**
- بعض النماذج أفضل في الـ Chain-of-Thought
- يمكنك تجربة نماذج مختلفة لمقارنة أدائها في المسائل المنطقية

**الخيار 2: تفعيل CoT (Chain-of-Thought) في الـ Prompt**
- أضف إلى الـ System Prompt شيئاً مثل:
  ```
  قبل أن تقوم بأي إجراء أو تستدعي أي أداة:
  1. حاول فهم الموقف منطقياً خطوة بخطوة
  2. اسأل نفسك: هل هناك معلومات ناقصة أحتاجها قبل المتابعة؟
  3. إذا كان هناك غموض أو نقص في المعلومات، اسأل المستخدم قبل أي إجراء.
  4. لا تقفز مباشرة لاستدعاء أداة إلا إذا كنت متأكداً تماماً من فهمك للموقف.
  ```

**الخيار 3: نمط "Plan-and-Execute" بدلاً من ReAct البسيط للمهام المعقدة**

في ReAct العادي: النموذج يختار أداة أو يرد في كل خطوة.

في Plan-and-Execute:
1. **خطوة التخطيط (المنفصلة):** اطلب من النموذج كتابة خطة مفصلة "ماذا سنفعل خطوة بخطوة" قبل أن يفعل أي شيء
2. **خطوة التنفيذ:** قم بتنفيذ الخطة خطوة بخطوة (يمكن أن يكون ReAct هنا)
3. **خطوة المراجعة:** بعد الانتهاء، هل تم كل شيء بشكل صحيح؟

**مثال على Plan-and-Execute لمسألتنا:**

**الخطوة 1: التخطيط فقط (لا أدوات بعد)**
- System: "أنت مخطط ذكي. صف لي خطواتك المقترحة للتعامل مع طلب المستخدم. لا تستدعي أي أدوات الآن. فقط صف الخطة."
- User: "العميل محمد اشترى حذاء ب 800... يستبدله بـ 600... ايه اللي أصح إعمله؟"
- Response (من النموذج):
  > "الخطة المقترحة:
  > 
  > 1. فهم الموقف منطقياً: استبدال منتج بأرخص بفرق 200 جنيه
  > 2. التحقق من السياسات: سياسة الاستبدال في الشركة (المدة، الشروط)
  > 3. جمع المعلومات الناقصة من المستخدم:
  >    - حالة المنتج (مستخدم أم جديد؟)
  >    - وجود الفاتورة
  >    - مدة الشراء
  >    - رغبة العميل في المتبقي 200 (استرداد أم رصيد؟)
  > 4. بناءً على المعلومات: تحديد الإجراء الصحيح
  >    - قد يكون استرداد جزئي + بيع جديد
  >    - أو تعديل على الطلب الأصلي
  > 5. تنفيذ الإجراء المختار بعد التأكد من الموافقة إذا لزم الأمر"

**الخطوة 2: عرض الخطة للمستخدم ثم التنفيذ**
- يمكنك عرض الخطة على المستخدم لتأكيد أو تعديل
- ثم البدء بالتنفيذ خطوة بخطوة

**فائدة هذا النمط:**
- يفرض على النموذج أن يفكر بشكل عميق قبل أن يبدأ في الفعل
- يقلل من قرارات متسرعة
- المستخدم يمكنه رؤية "ما الذي سيفعله الوكيل" قبل أن يفعله

**مستوى الخطورة/الأهمية:** متوسط إلى عالي
- يعتمد على مدى تعقيد العمليات التي يقوم بها الوكيل
- إذا كانت العمليات بسيطة نوعاً ما، الـ ReAct العادي يكفي
- إذا كانت معقدة وتحتاج تحليل وتفكير، Plan-and-Execute أفضل

### السيناريو 7.1: تعارض "اعمل" — مفتاح متعدد النوايا
**المعرف:** `EDGE-001`
**المشكلة المكتشفة (من السطر 413):**
> كلمة **"اعمل"** موجودة في **6 مصفوفات مختلفة** في `agentIntentRelevanceService.js`

**الاختبار — نفس البداية ونهايات مختلفة تماماً:**

| المدخل | النية المتوقعة | الأداة المتوقعة |
|---|---|---|
| 1. "اعمل اوردر" | إنشاء مسودة طلب | `order.create_draft` |
| 2. "اعمل منتج" | إنشاء منتج | `product.create` |
| 3. "اعمل وكيل" | إنشاء وكيل | `agent.spawn` |
| 4. "اعمل مهارة" | إنشاء مهارة | `skill.create` |
| 5. "اعمل خصم" | خصم | `discount.create_draft` أو `discount.apply` |
| 6. "اعمل إعلان" | إعلان فيسبوك | `facebook_ad.create_draft` |

**المشكلة في نظام Keyword-based:**

**كيف يتم الـ Resolve عادةً:**
1. يحسب درجة لكل Intent بناءً على عدد الكلمات المطابقة أو الوزن
2. الكلمة "اعمل" موجودة في جميعها → تضيف نقاطاً لجميع النواي الست
3. الكلمة الثانية ("اوردر"، "منتج"، "وكيل"...) تضيف نقاطاً لإحدى النواي

**التحذير:**
هذا يعمل **إذا كانت الكلمة الثانية موجودة في الـ hints الخاصة بتلك النية**

ماذا لو؟
- المستخدم قال "اعمل اوردر" و "اوردر" غير موجودة في `ORDER_DRAFT_HINTS`؟
- أو قال "اعمل مهارة" و "مهارة" موجودة أيضاً في مصفوفة أخرى؟

**والأخطر:**

**First-Match Wins أو Highest-Score Wins؟**

إذا كان الكود يستخدم `if/else if` بهذا الشكل:
```javascript
if (containsAny(message, MARKETING_CAMPAIGN_HINTS)) {
  return Intent.MARKETING_CAMPAIGN;
} else if (containsAny(message, PRODUCT_CREATION_HINTS)) {
  return Intent.PRODUCT_CREATION;
} else if (containsAny(message, AGENT_SPAWNING_HINTS)) {
  return Intent.AGENT_SPAWNING;
} // ... إلخ
```

إذا كانت "اعمل" موجودة في `MARKETING_CAMPAIGN_HINTS` وهي الأولى في الترتيب:
- "اعمل اوردر" → سيدخل أول `if` لأن فيه "اعمل"
- **سيذهب إلى حملة تسويقية بدلاً من مسودة طلب!** → **Routing خاطئ بشكل كامل**

حتى لو كان Highest-Score Wins:
- إذا كانت الدرجات متقاربة بسبب الكلمة المشتركة "اعمل"
- قد يذهب للخاطئ بسبب وزن بسيط

**هذه مشكلة بنيوية في نظام Keyword-based Intent Classification.**

**كيف يحلها Tool Calling في 2026:**

### السيناريو 7.2: تعارض "فين" — substring matching bug التاريخي
**المعرف:** `EDGE-002`
**المشكلة التاريخية (السطر 428):**
> كلمة **"فين"** كانت تطابق **"الموظفين"** كـ substring
> لأن الاختبار كان `includes` وليس `includesAnyTokenAware`

**التحقق الحالي من الكود (من السطر 431-433):**
> ✅ في السطر 346 يستخدم الآن `includesAnyTokenAware` لـ `PENDING_RESULT_HINTS`
> ⚠️ لكن **السطر 462 لـ `AGENT_NAME_ACTION_HINTS` لسه يستخدم `includesAny` العادي** (و "فين" موجودة هناك)

**الاختبار:**

| المدخل | النية المتوقعة | ماذا قد يحدث خطأ؟ |
|---|---|---|
| "كم موظفين النهارده؟" | `hr.attendance_today` | "موظفين" يحوي "فين" → قد يذهب لـ `AGENT_NAME_ACTION_HINTS` |
| "فين الوكيل المخزون؟" | `agent.list_agents` أو `agent.read_state` | هذا صحيح بالفعل، "فين الوكيل" يتعلق بالوكيل |
| "فين النتيجة؟" | متابعة نتيجة سابقة | هذا صحيح إذا كان في `PENDING_RESULT_HINTS` |

**شرح المشكلة:**

إذا كان الكود يستخدم `includes` العادي أو `includesAny` الذي يعمل بالمطابقة النصية:

```javascript
"موظفين".includes("فين")  // → true! ❌
//            ^^^^
//           "موظفين" تحوي الحروف "ف-ي-ن" بالترتيب!
```

هذا ليس خطأ في منطق المستخدم. هذا خطأ في تصميم مطابقة النصوص.

**الحل: Token-Aware Matching (الكلمات الكاملة لا الـ substrings):**

`includesAnyTokenAware` من المفترض أنه:
1. يقسم النص إلى كلمات (tokens)
2. يقارن كل كلمة بكاملة وليس كـ substring

```javascript
// إذا استخدم includesAnyTokenAware:
message: "كم موظفين النهارده؟"
tokens: ["كم", "موظفين", "النهارده", "؟"]

hints: ["فين", "اين", "وين"]

// مقارنة: "موظفين" == "فين"؟ → false ✅
// لا تطابق → صحيح
```

**التحذير من ملف السيناريوهات:**
> السطر 462 لـ `AGENT_NAME_ACTION_HINTS` لسه يستخدم `includesAny` العادي (و "فين" موجودة هناك)

**إذا كان هذا صحيحاً:**
- "كم موظفين النهارده؟"
- الكلمة "موظفين"
- إذا تم تمريرها عبر `includesAny` العادي مع مصفوفة تحتوي على "فين"
- → المطابقة → **Routing خاطئ**

**هذا خطأ برمجي صغير لكن أثره كبير جداً في الإنتاج.**

**توصية فورية:**

1. **قم بفحص جميع استخدامات `includesAny` في `agentIntentRelevanceService.js`**
2. **حولها جميعاً إلى `includesAnyTokenAware`** أو ما يعادلها من مطابقة الكلمات الكاملة
3. **لا تترك أي استخدام لـ `includes` العادي لمطابقة النوايا**

**أو الأفضل:**

أسرع في الهجرة لـ **Tool Calling for Intent Classification** وخلِّص نفسك من مشاكل الـ String Matching تماماً.

**مستوى الخطورة:** **عالي جداً — خطأ برمجي فعل في الكود (إذا كان السطر 462 يستخدم includesAny العادي)**

### السيناريو 7.3: الحالات الحدية — الرسائل الفارغة والرموز
**المعرف:** `EDGE-003`
**الوصف:** كيف يتعامل الوكيل مع المدخلات الغريبة؟

**المدخلات المقترحة:**
1. "" — رسالة فارغة تماماً
2. "..." — نقاط فقط
3. "؟" — علامة استفهام فقط
4. "🙂" — إيموجي فقط
5. "asdfghjkl" — حروف عشوائية بلا معنى
6. "12345" — أرقام فقط بدون سياق

**النتيجة المتوقعة:**
- ✅ لا يتحطم (No Crash)
- ✅ يطلب مدخلاً مفهوماً بطريقة مهذبة
- ❌ لا يقوم باي إجراء افتراضي خاطئ
- ❌ لا يحاول تمرير هذه الرسالة للـ LLM إذا كان من الواضح أنها لا معنى لها (يوفر تكلفة)

**التحليل:**

هذه مشاكل **Input Validation**، لا علاقة لها بـ AI بشكل مباشر.

أي نظام جيد يجب أن يحتوي على **طبقة Validation قبل أي معالجة:**

```
المدخل → [Validation Layer] → [إذا كان صالحاً: AI Processing]
                    ↓
             [إذا كان غير صالح: رد مهذب]
```

**ماذا يجب أن يحدث لكل مدخل:**

| المدخل | نوع المشكلة | الرد المناسب |
|---|---|---|
| "" فارغة | فارغة تماماً | "أنا لم أستلم أي رسالة. كيف يمكنني مساعدتك؟" |
| "..." نقاط | غير كافية | "لم أفهم طلبك. هل يمكنك توضيح ما تحتاجه؟" |
| "؟" استفهام | غير كافية | "لديك سؤال؟ كيف يمكنني مساعدتك؟" |
| "🙂" إيموجي | غير كافية | "😊! كيف يمكنني مساعدتك اليوم؟" |
| "asdfghjkl" حروف عشوائية | لا معنى لها | "أنا لم أفهم هذه الرسالة. هل يمكنك صياغة طلبك بشكل أوضح؟" |
| "12345" أرقام فقط بدون سياق | غير كافية | "هل هذا رقم طلب أو رقم منتج؟ يمكنك سؤالي عن تفاصيل طلب معين أو منتج معين." |

**توصية للتنفيذ:**

أضف طبقة Validation بسيطة قبل إرسال الرسالة لأي معالجة ذكاء اصطناعي أو حتى للـ relevance engine:

```typescript
const validateUserInput = (message: string): { valid: boolean; rejectionReason?: string } => {
  const trimmed = message.trim();
  
  // 1. فارغة تماماً
  if (trimmed.length === 0) {
    return { valid: false, rejectionReason: "empty" };
  }
  
  // 2. أقل من 3 أحرف (باستثناء الرموز الشائعة جداً مثل "كم" و "لماذا" لكنها 3 أحرف أو أكثر)
  // تحذير: "كم" حرفين! هذا معنوي. لذا لا تعتمد على الطول وحده.
  // بدلاً من ذلك: تحقق مما إذا كان يحتوي على أحرف أبجدية عربية أو إنجليزية حقيقية
  
  // 3. فقط رموز بدون أحرف كافية
  const hasMeaningfulChars = /[\u0600-\u06FF]|[a-zA-Z]/.test(trimmed);
  if (!hasMeaningfulChars && trimmed.length < 5) {
    // فقط رموز وأرقام وطول قصير
    return { valid: false, rejectionReason: "only_symbols" };
  }
  
  // 4. حروف متكررة جداً مثل "aaaaa" أو ";;;;;" (اختياري)
  
  return { valid: true };
};
```

**ملاحظة هامة:**
لا تجعل Validation صارمة جداً!
- "كم" حرفين لكنها سؤال معنوي جداً
- "؟" وحدها ربما تكون رسالة متابعة (لكن غالباً ليست كافية)
- الأفضل: الـ Validation تمسك فقط الواضح أنها بلا معنى تماماً (فارغة، فقط رموز، حروف عشوائية بلا معنى)، وتبقى للـ AI مهمة فهم الغامضة.

**مستوى الخطورة:** منخفض إلى متوسط
- هذه مشاكل يمكن أن تسبب سلوكاً غريباً أو تحطماً في الحالات الحدية
- لكنها ليست في المسار الرئيسي للاستخدام العادي

```typescript
const rephrasedResponse = await openai.chat.completions.create({

    },
    { role: "user", content: baseText }

return rephrasedResponse.choices[0].message.content;
```
