## Fixed Shipping Class Immediate Save & State Rollback
- **Problem**: When a user created a new shipping class (e.g., "مبرد" with slug "chilled") in the Shipping tab of Store Settings (`/settings/store?tab=shipping`) and refreshed the page, the new class was lost/not registered.
- **Root Cause**: A regression from previous git merge conflicts had reverted the `handleAddShippingClass` method in `StoreSettings.tsx` to only update the local state without immediately calling the backend API to save. The user expected the class to save immediately (similar to other settings pages like branches, shipping zones, and promotions), and the existing Vitest spec `StoreSettingsShippingClasses.test.tsx` specifically expected an immediate save and optimistic rollback behavior.
- **Solution**:
  - Refactored `handleAddShippingClass` in `frontend/src/pages/settings/StoreSettings.tsx` to be asynchronous.
  - Implemented optimistic UI updates: locally adding the class and setting its fee to 0 immediately.
  - Added an immediate API update call to `apiClient.put("/settings/company", ...)` to persist the new shipping class and its fee.
  - Implemented a robust state rollback mechanism that reverts the optimistic updates (shipping classes, fees) and restores the user's input fields (label, key) if the save API request fails.
- **Verification**:
  - Ran the specific Vitest test suite `src/pages/settings/__tests__/StoreSettingsShippingClasses.test.tsx` inside the `frontend/` directory.
  - Both tests (`persists a newly added shipping class immediately` and `rolls back the optimistic row when saving the new class fails`) passed perfectly with exit code 0.
