# سيناريوهات التاجر الكاملة على الموقع

تاريخ الإنشاء: 2026-05-03
النطاق: بورتال التاجر، تسجيل التاجر، إدارة الشركة للتجار، الدروب شيبنج، المخزون، الشحن، العمولات، والصلاحيات.

## القرار التشغيلي

التاجر في هذا الجزء هو شريك دروب شيبنج يورّد أو ينفذ منتجات داخل متجر الشركة. ليس هو نفس مورد المشتريات بالضرورة.

المورد في قسم المشتريات يستخدمه النظام لأوامر الشراء، فواتير الشراء، استلام المخزون، ومدفوعات الموردين. غالبا لا يدخل على بورتال ولا يرى طلبات العملاء.

التاجر في قسم الأفليت والدروب شيبنج يستخدمه النظام لربط منتجات الشركة بمصدر دروب شيبنج، استقبال طلبات موجهة له، تحديث مخزونه وسعره، تنفيذ الطلب أو إضافة رقم تتبع، واحتساب مستحقاته.

نفس الكيان الواقعي ممكن يكون الاثنين معا، لكن داخل النظام الحالي هما مسارين منفصلين: `Merchant` للدروب شيبنج و`Supplier` للمشتريات.

## الأدوات المتوقعة في القائمة الجانبية

### حساب التاجر `MERCHANT`

المفروض يظهر له فقط:

| الأداة | المسار | الفائدة |
| --- | --- | --- |
| بورتال التاجر | `/merchant-portal` | ملخص حسابه وعدد المنتجات والطلبات وطريقة التنفيذ |
| منتجاتي ومخزوني | `/merchant-portal/products` | تحديث سعر التاجر، SKU، المخزون، وتشغيل أو إيقاف المزامنة |
| طلبات الدروب شيبنج | `/merchant-portal/orders` | متابعة الطلبات المرسلة له وتحديث الحالة والتتبع |
| مستحقاتي | `/merchant-portal/commissions` | ملخص عدد العمولات ونسبة التاجر الحالية |
| حسابي | `/profile` | بيانات حساب مبسطة بدون HR أو ملفات موظفين |

المفروض لا يظهر له:

| ممنوع | السبب |
| --- | --- |
| لوحة الشركة `/company-dashboard` | التاجر ليس مالك الشركة |
| إدارة التجار `/merchants` | لا يدير تجار آخرين |
| إدارة المسوقين أو إعدادات الأفليت | صلاحيات الشركة فقط |
| المشتريات والموردين | ليست دورة التاجر اليومية |
| الطلبات العامة `/orders` | يرى طلبات التاجر فقط داخل البورتال |
| العملاء العامة والـ HR والإعدادات العامة | خارج صلاحياته |

### حساب الشركة `OWNER` أو `COMPANY_ADMIN`

المفروض يظهر لها أدوات إدارة التاجر ضمن:

| الأداة | المسار | الفائدة |
| --- | --- | --- |
| التجار والدروب شيبنج | `/merchants` | قائمة تجار الشركة فقط |
| إضافة تاجر | `/merchants/new` | إنشاء تاجر وربطه بالشركة، مع أو بدون حساب دخول |
| تفاصيل التاجر | `/merchants/:id` | عرض بيانات التاجر والمنتجات المرتبطة |
| تعديل التاجر | `/merchants/:id/edit` | تعديل بياناته ونشاطه وعمولته |
| ربط منتج بتاجر | `/merchants/:id` | تحديد سعر التاجر ومخزونه وحالة المزامنة |
| مزامنة المخزون | `/merchants/:id` | تحديث `lastSyncedAt` للمنتجات المفعلة |
| المنتجات والمخزون | حسب قسم المنتجات | تجهيز المنتجات التي ستباع عبر الدروب شيبنج |
| المخازن وشركات الشحن | حسب أقسام المخزون والشحن | تحديد مصدر التنفيذ ومزود الشحن |
| العمولات | `/platform/commissions` | مراجعة عمولات التاجر والمنصة والمسوق |

## ملاحظة مهمة عن الوضع الحالي

الـ backend يدعم حقول مهمة للتاجر:

| الحقل | المعنى |
| --- | --- |
| `fulfillmentMode` | هل التاجر يشحن بنفسه أم التنفيذ من مخزن الشركة |
| `defaultWarehouseId` | المخزن الافتراضي عند التنفيذ من الشركة |
| `defaultShippingCompanyId` | شركة الشحن الافتراضية لطلبات هذا التاجر |

لكن صفحات إدارة التاجر الحالية لا تعرض اختيارا واضحا لهذه الحقول داخل `MerchantRegister` أو `MerchantProfile`. لذلك السيناريوهات أدناه تعتبر ظهور هذه الإعدادات في واجهة الشركة شرط قبول مهم قبل اعتبار دورة التاجر مكتملة بالكامل على الموقع.

## سيناريوهات تجهيز الشركة

### MS-001 تفعيل تطبيقات الشركة المطلوبة

الخطوات:

1. افتح حساب مالك الشركة.
2. تأكد أن التطبيقات المطلوبة مفعلة: `ecommerce-basic`, `order-core`, `order-shipping-turbo`, `order-invoicing`, `inventory-pro`, `affiliate-pro`, `procurement-pro`, `analytics-advanced`, `wallet-system`.
3. افتح القائمة الجانبية.

المتوقع:

- تظهر أدوات التجارة والطلبات والمخزون والأفليت والدروب شيبنج.
- لا تظهر أدوات خاصة بسوبر أدمن لشركة عادية.

### MS-002 تجهيز مخازن الشركة

الخطوات:

1. أنشئ `Main Cairo Warehouse`.
2. أنشئ `Alex Backup Warehouse`.
3. اجعل المخزنين نشطين.

المتوقع:

- المخازن مرتبطة بنفس الشركة.
- أي محاولة لاستخدام مخزن من شركة أخرى تترفض من الـ backend.

### MS-003 تجهيز شركات الشحن

الخطوات:

1. تأكد من وجود `Turbo`.
2. أضف شركات ديمو: `Bosta Demo`, `Aramex Demo`, `DHL Demo`.
3. فعّل الشركات.

المتوقع:

- شركات الشحن تظهر للشركة فقط.
- أي محاولة لربط تاجر بشركة شحن من شركة أخرى تترفض.

### MS-004 تجهيز منتجات دروب شيبنج

الخطوات:

1. أنشئ المنتجات المقترحة.
2. فعّل المنتجات.
3. أدخل مخزون شركة مناسب للمنتجات التي ستنفذ من مخزن الشركة.

المتوقع:

- المنتجات تظهر في شاشة ربط منتجات التاجر.
- المنتج غير النشط لا يدخل في دورة الطلب.

## سيناريوهات تسجيل التاجر

### MR-001 تسجيل تاجر من الدومين الرئيسي مع slug شركة

الخطوات:

1. افتح `/register/merchant`.
2. أدخل slug الشركة.
3. أدخل الاسم والبريد وكلمة مرور 8 أحرف أو أكثر.
4. أرسل النموذج.

المتوقع:

- يتم إنشاء `Merchant` مرتبط بالشركة الصحيحة.
- يتم إنشاء مستخدم بدور `MERCHANT`.
- لا يستطيع التاجر اختيار العمولة أو الـ webhook أو طريقة التنفيذ من صفحة التسجيل العامة.

### MR-002 تسجيل تاجر من سياق الشركة

الخطوات:

1. افتح صفحة التسجيل من دومين أو سياق شركة محددة.
2. املأ بيانات التاجر.
3. أرسل النموذج.

المتوقع:

- يتم ربط الطلب بالشركة من السياق بدون إدخال slug يدوي.
- لا يتم الربط بشركة أخرى.

### MR-003 رفض التسجيل بدون شركة

الخطوات:

1. افتح `/register/merchant` من الدومين الرئيسي.
2. اترك حقل الشركة فارغا.
3. أرسل النموذج.

المتوقع:

- تظهر رسالة تطلب تحديد الشركة.
- لا يتم إنشاء `Merchant` أو `User`.

### MR-004 رفض شركة غير موجودة أو غير نشطة

الخطوات:

1. أدخل slug غير صحيح أو لشركة غير نشطة.
2. أرسل النموذج.

المتوقع:

- يرجع الطلب بخطأ واضح.
- لا يتم إنشاء حساب تاجر.

### MR-005 رفض البريد المكرر

الخطوات:

1. سجل تاجر ببريد معين.
2. حاول تسجيل تاجر آخر بنفس البريد.

المتوقع:

- الطلب الثاني يترفض.
- البريد فريد عالميا للتجار والمستخدمين.

### MR-006 رفض كلمة مرور قصيرة

الخطوات:

1. أدخل كلمة مرور أقل من 8 أحرف.
2. أرسل النموذج.

المتوقع:

- تظهر رسالة أن كلمة المرور يجب ألا تقل عن 8 أحرف.
- لا يتم إنشاء الحساب.

### MR-007 منع إعدادات التشغيل من التسجيل العام

الخطوات:

1. أرسل طلب API عام يحتوي `commissionRate`, `autoFulfill`, `webhookUrl`, `fulfillmentMode`.
2. افحص التاجر الناتج.

المتوقع:

- يتم تجاهل إعدادات التشغيل العامة.
- العمولة وطريقة التنفيذ والـ webhook تظل قرار الشركة.

### MR-008 قرار الموافقة بعد التسجيل العام

الخطوات:

1. سجل تاجر من الصفحة العامة.
2. جرب تسجيل الدخول مباشرة.
3. راجع ظهوره في قائمة تجار الشركة.

المتوقع المنتج:

- لو السياسة المطلوبة هي موافقة الشركة أولا، يجب أن يكون التاجر `غير نشط` أو `pending` حتى تفعله الشركة.
- لو السياسة المطلوبة هي دخول فوري، يجب ألا يرى أي منتجات أو طلبات حتى تربطه الشركة بمنتجات.

ملاحظة تنفيذية:

- السلوك الحالي يميل لإنشاء حساب `MERCHANT` نشط مباشرة. هذا مقبول فقط لو قررنا أن التسجيل العام يعني دخول فوري مع بورتال فارغ إلى أن تضيف الشركة المنتجات.

## سيناريوهات إدارة الشركة للتاجر

### CM-001 إنشاء تاجر من لوحة الشركة بكلمة مرور

الخطوات:

1. افتح `/merchants/new` كمالك أو أدمن شركة.
2. أدخل اسم وبريد وكلمة مرور.
3. احفظ.

المتوقع:

- يتم إنشاء `Merchant`.
- يتم إنشاء `User` بدور `MERCHANT`.
- التاجر يستطيع تسجيل الدخول للبورتال.

### CM-002 إنشاء تاجر بدون كلمة مرور

الخطوات:

1. افتح `/merchants/new`.
2. اترك كلمة المرور فارغة.
3. احفظ.

المتوقع:

- يتم إنشاء سجل التاجر فقط.
- لا يستطيع الدخول للبورتال إلا بعد إنشاء/تعيين مستخدم دخول له.

### CM-003 قائمة التجار تعرض تجار الشركة فقط

الخطوات:

1. أنشئ تاجر في الشركة الأولى.
2. أنشئ تاجر في شركة ثانية.
3. افتح `/merchants` من حساب الشركة الأولى.

المتوقع:

- تظهر تجار الشركة الأولى فقط.
- لا يظهر تاجر الشركة الثانية.

### CM-004 تعديل بيانات التاجر

الخطوات:

1. افتح `/merchants/:id/edit`.
2. عدل الاسم والهاتف والعنوان والعمولة والـ webhook وحالة النشاط.
3. احفظ.

المتوقع:

- تحفظ القيم الجديدة.
- لا يمكن تعديل تاجر لا يتبع الشركة.

### CM-005 تعطيل التاجر

الخطوات:

1. عطل `isActive`.
2. حاول دخول التاجر للبورتال.
3. حاول توجيه طلب جديد له.

المتوقع:

- البورتال يرفض التاجر غير النشط.
- لا يتم اختياره في الدروب شيبنج.

### CM-006 ربط منتج بتاجر

الخطوات:

1. افتح `/merchants/:id`.
2. اختر منتجا من منتجات الشركة.
3. أدخل `merchantSku`, `merchantPrice`, `stock`, `syncEnabled=true`.
4. احفظ.

المتوقع:

- يتم إنشاء أو تحديث `MerchantProduct`.
- لا يتم إنشاء ربط مكرر لنفس `merchantId + productId`.
- سعر الدروب شيبنج للمنتج يتحدث بناء على أرخص تاجر متاح.

### CM-007 مزامنة مخزون التاجر

الخطوات:

1. اربط أكثر من منتج بالتاجر.
2. اجعل بعضها `syncEnabled=true` وبعضها `false`.
3. اضغط مزامنة المخزون.

المتوقع:

- يتحدث `lastSyncedAt` للمنتجات المفعلة فقط.
- تظهر رسالة بعدد المنتجات التي تمت مزامنتها.

### CM-008 ضبط طريقة تنفيذ التاجر

الخطوات:

1. افتح شاشة تعديل التاجر.
2. اختر `MERCHANT` لتاجر يشحن بنفسه.
3. اختر `COMPANY_WAREHOUSE` لتاجر تنفذ الشركة طلباته من مخزنها.
4. اختر مخزن افتراضي وشركة شحن افتراضية.

المتوقع:

- الحقول تحفظ في `Merchant.fulfillmentMode`, `defaultWarehouseId`, `defaultShippingCompanyId`.
- إذا كان التنفيذ `COMPANY_WAREHOUSE` يتم الاعتماد على مخزون الشركة لا مخزون التاجر عند إنشاء الطلب.

حالة واجهة حالية:

- يجب إضافة/إظهار هذه الحقول في واجهة إدارة التاجر إذا لم تكن موجودة في شاشة أخرى.

### CM-009 رفض مراجع تنفيذ لا تخص الشركة

الخطوات:

1. أرسل `defaultWarehouseId` من شركة ثانية.
2. أرسل `defaultShippingCompanyId` من شركة ثانية.

المتوقع:

- الطلب يترفض برسالة أن المخزن أو شركة الشحن لا يتبع هذه الشركة.

### CM-010 منع غير المصرح لهم من إدارة التجار

الخطوات:

1. افتح `/merchants` كمستخدم `AFFILIATE`.
2. افتح `/merchants` كمستخدم `MERCHANT`.
3. جرّب API `/api/v1/merchants`.

المتوقع:

- الواجهة تعيد المسوق إلى `/affiliates/dashboard`.
- الواجهة تعيد التاجر إلى `/merchant-portal`.
- الـ API يرجع `403`.

## سيناريوهات بورتال التاجر

### MP-001 تسجيل دخول التاجر

الخطوات:

1. سجل دخول بحساب `MERCHANT`.
2. افتح `/company-dashboard`.
3. افتح `/merchant-portal`.

المتوقع:

- بعد الدخول يتم توجيهه إلى `/merchant-portal`.
- محاولة فتح لوحة الشركة تعيده إلى بورتال التاجر.
- لا تظهر أدوات الشركة في القائمة الجانبية.

### MP-002 تحميل بيانات الحساب

الخطوات:

1. افتح `/merchant-portal`.
2. راقب طلب `/api/v1/merchant-portal/me`.

المتوقع:

- يرجع التاجر المرتبط بنفس `companyId` ونفس البريد.
- يظهر عدد المنتجات والطلبات والعمولات ونسبة التاجر وطريقة التنفيذ.

### MP-003 بورتال بدون منتجات

الخطوات:

1. سجل تاجر جديد لم يتم ربط أي منتج به.
2. افتح `/merchant-portal/products`.

المتوقع:

- تظهر حالة فارغة واضحة.
- لا تظهر منتجات الشركة كلها.

### MP-004 عرض منتجات التاجر فقط

الخطوات:

1. اربط منتجا للتاجر الأول.
2. اربط منتجا آخر للتاجر الثاني.
3. افتح بورتال التاجر الأول.

المتوقع:

- يرى منتجاته فقط.
- لا يرى منتجات التاجر الثاني.

### MP-005 تحديث منتج التاجر بقيم صحيحة

الخطوات:

1. افتح `/merchant-portal/products`.
2. عدل السعر والمخزون وحالة المزامنة.
3. احفظ.

المتوقع:

- الحفظ ينجح.
- المنتج في الشركة يتحدث سعر الدروب شيبنج الخاص به.

### MP-006 رفض قيم منتج غير صحيحة

الخطوات:

1. أدخل سعر `0` أو قيمة غير رقمية.
2. أدخل مخزون سالب.
3. احفظ.

المتوقع:

- يظهر خطأ واضح.
- لا يتم حفظ القيم.

### MP-007 منع تعديل منتج تاجر آخر

الخطوات:

1. خذ `merchantProductId` تابع لتاجر آخر.
2. أرسل PATCH من حساب التاجر الحالي.

المتوقع:

- يرجع `404` أو منع واضح.
- لا تتغير بيانات المنتج.

### MP-008 عرض مصدر التنفيذ

الخطوات:

1. جهز تاجر `MERCHANT`.
2. جهز تاجر `COMPANY_WAREHOUSE`.
3. افتح البورتال لكل تاجر.

المتوقع:

- يظهر `التاجر يشحن` أو `من مخزن الشركة`.
- التاجر يرى المعلومة للتنفيذ والمتابعة فقط، ولا يختار المخزن أو شركة الشحن.

### MP-009 بروفايل التاجر

الخطوات:

1. افتح `/profile` كتاجر.

المتوقع:

- يظهر حساب تاجر مبسط.
- لا تظهر بيانات موظف: راتب، عهد، جزاءات، ملفات HR.

## سيناريوهات الطلبات والدروب شيبنج

### MO-001 توجيه طلب لمنتج تاجر واحد

الخطوات:

1. اربط منتج `UAT Classic Tee` بتاجر يدوي.
2. أنشئ طلب يحتوي المنتج.
3. اجعل الطلب مؤكد أو في الحالة التي تشغل توجيه الدروب شيبنج.

المتوقع:

- يتم إنشاء `MerchantOrder` واحد.
- يظهر الطلب في بورتال التاجر.
- الطلب الأصلي يتعلم كـ dropshipped.

### MO-002 طلب واحد يتقسم على أكثر من تاجر

الخطوات:

1. أنشئ طلب يحتوي منتجين من تاجرين مختلفين.
2. شغل توجيه الدروب شيبنج.

المتوقع:

- يتم إنشاء `MerchantOrder` لكل تاجر.
- كل تاجر يرى الجزء الخاص به فقط.
- الطلب الأصلي يحتفظ بمرجع legacy لأول `merchantOrder` عند الحاجة.

### MO-003 اختيار أرخص تاجر لديه مخزون كاف

الخطوات:

1. اربط نفس المنتج بتاجرين.
2. اجعل التاجر الأرخص مخزونه أقل من الكمية المطلوبة.
3. اجعل التاجر الأعلى سعرا لديه مخزون كاف.
4. أنشئ الطلب.

المتوقع:

- لا يتم اختيار الأرخص بسبب نقص المخزون.
- يتم اختيار التاجر الذي يستطيع تغطية الكمية.

### MO-004 استبعاد تاجر غير نشط أو مزامنة متوقفة

الخطوات:

1. اربط منتجا بتاجر غير نشط.
2. اربط منتجا بتاجر `syncEnabled=false`.
3. أنشئ طلبا.

المتوقع:

- لا يتم اختيار التاجر غير النشط.
- لا يتم اختيار ربط منتج غير مزامن.

### MO-005 تنفيذ من مخزن الشركة

الخطوات:

1. اضبط تاجر على `COMPANY_WAREHOUSE`.
2. أدخل مخزون المنتج في مخزن الشركة.
3. اجعل مخزون التاجر نفسه `0`.
4. أنشئ طلبا.

المتوقع:

- الطلب ينجح إذا مخزون الشركة كاف.
- يتم حجز مخزون الشركة.
- يظهر للتاجر مصدر التنفيذ `من مخزن الشركة`.
- تظهر بيانات المخزن وشركة الشحن في الطلب.

### MO-006 رفض طلب بلا مخزون كاف

الخطوات:

1. اطلب كمية أعلى من مخزون التاجر أو مخزون الشركة حسب طريقة التنفيذ.

المتوقع:

- لا يتم إنشاء طلب تاجر غير قابل للتنفيذ.
- تظهر رسالة أن المخزون غير كاف.

### MO-007 تاجر تنفيذ تلقائي

الخطوات:

1. اضبط `autoFulfill=true`.
2. أنشئ طلبا موجها لهذا التاجر.

المتوقع:

- يتم إنشاء طلب تاجر ثم تحويله إلى `FULFILLED` تلقائيا.
- يتم إنشاء رقم تتبع تلقائي بصيغة `AUTO-*`.
- يتم تحديث بيانات الشحنة.

### MO-008 تاجر تنفيذ يدوي

الخطوات:

1. اضبط `autoFulfill=false`.
2. أنشئ طلبا.
3. افتح `/merchant-portal/orders`.

المتوقع:

- الطلب يظهر بحالة `PENDING`.
- التاجر يستطيع تغييره إلى `SENT`, `CONFIRMED`, `FULFILLED`, `CANCELLED`, أو `FAILED`.

### MO-009 تنفيذ الطلب برقم تتبع

الخطوات:

1. افتح طلب تاجر يدوي.
2. أدخل رقم تتبع.
3. أدخل مرجع خارجي أو رقم طلب التاجر.
4. غيّر الحالة إلى `FULFILLED`.

المتوقع:

- يحفظ `trackingNumber`.
- يحفظ `merchantOrderId` كمرجع خارجي.
- يحفظ `fulfilledAt`.
- تتحدث الشحنة المرتبطة.
- الطلب الأصلي يتحدث بحالة شحن منفذة عند انطباق القاعدة.

### MO-010 تحديث حالة غير منفذة

الخطوات:

1. غير حالة الطلب إلى `SENT` أو `CONFIRMED`.
2. أدخل رقم تتبع اختياري.

المتوقع:

- الحالة تحفظ.
- الشحنة تتحدث عند وجود تتبع.
- لا يتم وضع `fulfilledAt` إلا عند `FULFILLED`.

### MO-011 إلغاء أو فشل الطلب

الخطوات:

1. غيّر حالة الطلب إلى `CANCELLED`.
2. كرر مع `FAILED`.

المتوقع:

- `fulfilledAt` يتم تصفيره.
- الطلب لا يظهر كمكتمل.
- يجب تحديد سياسة المخزون: هل يتم فك الحجز تلقائيا أم يحتاج خطوة منفصلة.

### MO-012 رفض حالة طلب غير صالحة

الخطوات:

1. أرسل حالة غير موجودة مثل `READY_TO_SHIP`.

المتوقع:

- يرجع خطأ أن حالة الطلب غير صالحة.
- لا تتغير بيانات الطلب.

### MO-013 فلترة طلبات التاجر

الخطوات:

1. أنشئ طلبات بحالات مختلفة.
2. استخدم فلتر `status`.
3. استخدم `limit` و`offset`.

المتوقع:

- يرجع فقط طلبات التاجر الحالي.
- الفلترة والصفحات تعمل بدون تسريب بيانات.

### MO-014 منع تاجر من قراءة طلب تاجر آخر

الخطوات:

1. افتح حساب تاجر أول.
2. حاول تعديل `merchantOrderId` تابع لتاجر ثان.

المتوقع:

- يرجع `404` أو منع واضح.
- لا يتغير طلب التاجر الآخر.

### MO-015 شحنة الطلب

الخطوات:

1. اربط التاجر بشركة شحن افتراضية.
2. أنشئ طلبا للتاجر.
3. افتح الطلب في البورتال.

المتوقع:

- تظهر شركة الشحن.
- يظهر رقم تتبع شركة الشحن عند توفره.
- يظهر مرجع تنفيذ التاجر كسطر مستقل إذا كان مختلفا عن رقم الشحنة الرسمي.

## سيناريوهات العمولات والمستحقات

### MC-001 احتساب عمولة التاجر

الخطوات:

1. اضبط `commissionRate` للتاجر.
2. أنشئ طلبا مكتمل الدفع أو مكتمل التنفيذ حسب قاعدة احتساب العمولة.
3. شغل حساب العمولات.

المتوقع:

- يتم إنشاء عمولة نوعها مرتبط بالتاجر.
- المبلغ يحترم نسبة التاجر.
- تظهر للشركة في شاشة العمولات.

### MC-002 عرض مستحقات التاجر في البورتال

الخطوات:

1. افتح `/merchant-portal/commissions`.

المتوقع الحالي:

- تظهر بطاقة بعدد العمولات ونسبة التاجر.

المتوقع المنتج لاحقا:

- يحتاج التاجر كشف تفصيلي بالمستحقات: الطلب، الحالة، المبلغ، تاريخ الاستحقاق، المدفوع، والمتبقي.

### MC-003 فصل عمولات الأطراف

الخطوات:

1. أنشئ طلب أفليت موجه لتاجر.
2. راجع عمولات `AFFILIATE`, `MERCHANT`, `PLATFORM`.

المتوقع:

- كل طرف له سجل مستقل أو نوع واضح.
- الشركة ترى كل السجلات.
- التاجر لا يرى عمولات المسوق.
- المسوق لا يرى عمولات التاجر.

### MC-004 طلبات السحب

المتوقع المنتج:

- لو التاجر سيأخذ أرباحه من النظام، يحتاج شاشة طلب سحب أو كشف دفع.
- إذا الدفع سيتم خارج النظام، يجب أن تعرض الشاشة كشفا فقط وتوضح أن التسوية تتم يدويا.

حالة واجهة حالية:

- بورتال التاجر يعرض ملخص فقط ولا توجد شاشة سحب تفصيلية للتاجر.

## سيناريوهات الصلاحيات والعزل

### SEC-001 API بورتال التاجر يحتاج تسجيل دخول

الخطوات:

1. افتح `/api/v1/merchant-portal/me` بدون token.

المتوقع:

- يرجع `401`.

### SEC-002 API بورتال التاجر يرفض غير التاجر

الخطوات:

1. افتح `/api/v1/merchant-portal/me` بمالك شركة.
2. كرر بمسوق.

المتوقع:

- يرجع `403` برسالة أن الصفحة مخصصة للتجار فقط.

### SEC-003 ربط التاجر بالبريد والشركة

الخطوات:

1. أنشئ مستخدم `MERCHANT` ببريد لا يطابق سجل التاجر.
2. جرب فتح البورتال.

المتوقع:

- يرفض الدخول لأن سجل التاجر لا يطابق `companyId + email`.

### SEC-004 عزل الشركات

الخطوات:

1. أنشئ شركة ثانية وتاجر ثاني.
2. استخدم حساب الشركة الأولى لمحاولة قراءة تاجر الشركة الثانية.
3. استخدم حساب تاجر الشركة الأولى لمحاولة تعديل منتج تاجر الشركة الثانية.

المتوقع:

- كل المحاولات تترفض.
- لا يحدث تسريب بيانات بين الشركات.

### SEC-005 منع القائمة الجانبية الخاطئة

الخطوات:

1. سجل دخول كتاجر.
2. افحص القائمة الجانبية.

المتوقع:

- تظهر أدوات التاجر فقط.
- لا تظهر أدوات الشركة أو المسوق أو المشتريات.

### SEC-006 منع المسارات الخاصة

الخطوات:

1. كتاجر افتح `/orders`, `/customers`, `/settings`, `/affiliates/dashboard`, `/merchants`.

المتوقع:

- يتم تحويله إلى `/merchant-portal`.
- الـ API الخاص بهذه الصفحات لا يسمح له بالوصول.

## سيناريوهات تجربة المستخدم

### UX-001 صفحة بورتال فارغة مفهومة

الخطوات:

1. افتح بورتال تاجر لا يملك منتجات أو طلبات.

المتوقع:

- تظهر رسائل فارغة مفهومة: لا منتجات بعد، لا طلبات بعد.
- لا يشعر المستخدم أن الصفحة معطلة.

### UX-002 أسماء القائمة واضحة

المتوقع:

- اسم القسم يكون `Merchant Portal` أو `بورتال التاجر`.
- `Products & Stock` يوضح أن التاجر يعدل مخزونه وسعره فقط.
- `Dropshipping Orders` يوضح أن هذه ليست كل طلبات الشركة.
- `Commissions` أو `Payouts` يوضح المستحقات، وليس عمولات المسوقين.

### UX-003 الموبايل

الخطوات:

1. افتح `/merchant-portal` على viewport موبايل مثل `390x844`.
2. افتح منتجاتي وطلباتي.

المتوقع:

- لا يوجد horizontal overflow.
- بطاقات الطلبات والمنتجات قابلة للقراءة.
- أزرار الحفظ وتحديث الحالة قابلة للضغط.

### UX-004 رسائل الخطأ

المتوقع:

- عند رفض السعر أو المخزون يظهر سبب واضح.
- عند رفض الصلاحية تظهر رسالة مفهومة وليست شاشة بيضاء.
- عند عدم وجود تاجر مرتبط بالمستخدم تظهر رسالة: حساب التاجر غير مفعل أو غير مرتبط بهذه الشركة.

## سيناريوهات نقاط الضعف التي يجب مراقبتها

| الكود | النقطة | القرار المطلوب |
| --- | --- | --- |
| GAP-001 | إعدادات `fulfillmentMode`, `defaultWarehouseId`, `defaultShippingCompanyId` موجودة backend ولا تظهر بوضوح في UI إدارة التاجر | إضافة حقولها للشركة قبل اعتبار دورة المخازن والشحن كاملة |
| GAP-002 | التسجيل العام للتاجر ينشئ حساب نشط حاليا | نقرر: موافقة الشركة أولا أم دخول فوري ببورتال فارغ |
| GAP-003 | صفحة مستحقات التاجر تعرض ملخص فقط | إضافة كشف تفصيلي ومدفوعات إذا التاجر سيحاسب من النظام |
| GAP-004 | سياسة فك حجز المخزون عند `CANCELLED` أو `FAILED` تحتاج تأكيد | إما فك الحجز تلقائيا أو إضافة إجراء إداري واضح |
| GAP-005 | مزامنة المخزون حاليا تحدث `lastSyncedAt` فقط | عند الربط الحقيقي مع API تاجر خارجي يجب إضافة pull/push stock |
| GAP-006 | الشركة قد تحتاج بوابة مراجعة طلبات تسجيل التجار العامة | إذا فتحنا التسجيل العام للعملاء الحقيقيين، نحتاج workflow موافقة |

## ترتيب الاختبار المقترح

1. تجهيز شركة جديدة وبيانات الاختبار.
2. اختبار تسجيل التاجر العام والإنشاء من لوحة الشركة.
3. اختبار صلاحيات القائمة والمسارات.
4. ربط المنتجات والمخزون والشحن.
5. تنفيذ طلب تاجر واحد.
6. تنفيذ طلب متعدد التجار.
7. اختبار تاجر تلقائي وتاجر يدوي.
8. اختبار التنفيذ من مخزن الشركة.
9. اختبار العمولات والعزل بين الأطراف.
10. اختبار الموبايل وتجربة الاستخدام.

## قرار المنتج المقترح قبل التطوير القادم

الأولوية التالية ليست إضافة صفحات كثيرة للتاجر، بل إكمال حلقة التشغيل:

1. إضافة إعدادات تنفيذ التاجر في واجهة الشركة.
2. تحديد سياسة موافقة التاجر بعد التسجيل العام.
3. إضافة كشف مستحقات تفصيلي للتاجر.
4. تثبيت سيناريو فك حجز المخزون عند الإلغاء أو الفشل.
5. بعد ذلك نعمل UAT كامل من شركة جديدة بالمتصفح والـ API.
