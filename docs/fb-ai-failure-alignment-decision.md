# قرار معماري: سلوك فشل الـ AI على فيسبوك — محاذاة مع نمط المنصة

**الحالة**: معتمد ومُنفّذ · 2026-11-13 · بناء على مراجعة عميقة بطلب مختار («الكلام ده معيوب جداً ومش مناسب لطبيعة المنصة»)

## القرار
مسار تصعيد فيسبوك محاذى لنمط واتساب المرجعي: **فشل الـ AI = تنبيه لحظي للفريق + صمت تام للعميل** — الفريق البشري هو طبقة الاستعادة. حُذفت رسالة الاعتذار الثابتة الكاذبة («ثواني بس هحول حضرتك لأحد زملائنا في خدمة العملاء...فوراً»).

## ليه (التحليل)
- **واتساب = النمط المرجعي**: فشل → `flagThreadForHumanTakeover` + socket/ActivityLog → **صفر رسائل للعميل** — والمنصة عندها ~18 موظف لكل شركة كطبقة استعادة
- **الفيس كان الشاذ**: رسالة ثابتة واحدة لكل فشل (أكبر إشارة كشف AI) + وعد زائف («فوراً») + تصعيد غير متناسب (ترحيب بسيط → خدمة عملاء)
- **البناية الموجودة تكفي**: transport retry ×3 (`aiServiceRetry.js`) + سلسلة fallback الموديلات داخل المحرك (deepseek→gemini→groq — `skills_pipeline.py`) + تنبيه لحظي للفريق
- **تصميم Retry تقدمي + Outbox + Sweeper فُحص ورُفض**: over-engineering فوق معمارية قائمة بنفس الهدف (350 سطر جنب بنيوة in-memory debounce). المستند المقترح سُحب واستُبدل بهذا القرار
- **الحادثة المرجعية** (فشل عابر بعد restart على رسالة «السلام عليكم») كانت من الحالات التي التصعيد البشري يغطيها أصلاً

## المطبق
- `allFunctions.js` فرع التصعيد: حذف `handoverNotice` + سجل الرسالة الوهمي — إبقاء flag الفريق + log واضح («customer untouched»)
- ما يبقى قائماً من الموجة السابقة (سليم الموقع): رد الاحتفاظ خارج ساعات العمل (cooldown 4س) + TZ fix للـ3 بوابات + 24/7 toggle API

## الدرس المسجل
قبل بناء محرك استعادة جديد: **افحص نمط المنصة المرجعي في القنوات الأخرى** — أي اختلاف عنه انحراف يستدعي تبرير، مش فرصة تطوير.
