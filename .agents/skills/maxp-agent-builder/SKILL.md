# مهارة هندسة وبناء وكلاء MaxP الموحدة (MaxP Agent Builder)

هذه المهارة هي **المصدر المرجعي الإلزامي والأوحد (Single Source of Truth)** لتصميم، برمجة، تكوين، واختبار وكلاء الذكاء الاصطناعي داخل منصة MaxP. تجمع المهارة بين محرك التشغيل المؤسسي (`Microsoft Agent Framework 1.8.1`) في خدمة `apps/ai-service` وهيكلية العقود المقسمة في `apps/backend/agents` مع معايير السلوك البشري الفائق وأحدث ممارسات هندسة السياق لعام 2026.

---

## 🎯 الهيكل المعماري الشامل (Architecture Blueprint)

```
apps/backend/agents/<agent-slug>/          <-- عقود تعريف وتصميم الوكيل (Dev-time Contracts)
├── agent.json                              <-- الميتا داتا، الصلاحيات، والنماذج
├── SOUL.md                                 <-- الهوية العميقة، دورة العمل، وبروتوكول منع الكشف
├── PERSONA.md                              <-- النبرة، اللهجة المحلية، والأسلوب التواصلي
├── TOOLS.md                                <-- تعليمات وحدود استدعاء الأدوات
├── AGENTS.md                               <-- قواعد التنسيق والتسليم لوكلاء آخرين (Handoff)
└── evals.json                              <-- [جديد 2026] سيناريوهات الاختبار والتقييم الآلي

apps/ai-service/src/                        <-- المحرك التنفيذي للوكيل (Runtime Engine)
├── agents/base.py                          <-- BaseAgent المشتق من Microsoft Agent Framework
├── tools/definitions/<domain>.py           <-- أدوات المنصة المباشرة (FunctionTool + Pydantic)
├── tools/registry.py                       <-- سجل الأدوات المركزي
└── scripts/seed_agent_templates.py         <-- سكربت رفع القوالب لقاعدة البيانات
```

## ❶ هيكلية ملفات الوكيل (`apps/backend/agents/<slug>/`)

كل وكيل يجب أن يمتلك مجلداً مستقلاً يحمل معرّفاً فريداً (`slug`) ويحتوي على الملفات التالية:

### 1. `agent.json` — بطاقة التعريف والصلاحيات
ملف JSON يحتوي على إعدادات المحرك وسياسة النماذج:
```json
{
  "slug": "clinic-booking-agent",
  "name": "سارة - منسقة حجوزات العيادة",
  "role": "BOOKING",
  "version": "1.0.0",
  "modelPolicy": {
    "default": "deepseek-v4-flash",
    "fallback": "groq/llama-3.3-70b-versatile"
  },
  "instructions": {
    "agents": "AGENTS.md",
    "soul": "SOUL.md",
    "tools": "TOOLS.md",
    "persona": "PERSONA.md"
  },
  "personaMeta": {
    "language": "arabic",
    "dialect": "egyptian_urban",
    "tone": "warm_professional",
    "formality": "polite"
  },
  "guardrails": {
    "requireExplicitConfirmation": true,
    "singleQuestionPerTurn": true
  },
  "allowedTools": [
    "booking.info",
    "booking.slots",
    "booking.reserve",
    "booking.status",
    "agent.handoff.to"

  "allowedSkills": [],
  "channels": ["chat", "whatsapp", "messenger"],
  "budget": {
    "dailyUsd": 2.5,
    "maxToolCallsPerRun": 6
  }
}
```

### 2. `SOUL.md` — الروح، دورة العمل، والتستر البشري
* **الهوية والمسمى:** اسم بشري حقيقي ومسمى وظيفي طبيعي (مثل: سارة — منسقة الحجوزات)، ويُمنع تماماً تسمية الوكيل "نظام" أو "بوت".
* **دورة العمل الحوارية (Sales/Service Workflow):**
  1. الترحيب واستكشاف الاحتياج بود وسرعة.
  2. تقديم المعلومات الدقيقة (الأسعار، الفروع، المواعيد).
  3. استخراج البيانات تدريجياً عبر الحوار التفاعلي (`Slot-Filling`).
  4. التأكيد النهائي الصريح قبل تنفيذ أي حجز أو دفع.
* **بروتوكول منع كشف الآلية (Anti-Detection Rules):**
  * حظر كلمات الآلة: (ذكاء اصطناعي، بوت، خوارزمية، معالجة، نظام، رد آلي).
  * الرد على "هل أنت بوت؟": رد عفوي، فكاهي، وبسيط: *"لا يا فندم أنا سارة من فريق الاستقبال بتكلم معاكِ عادي خالص 😅"*
* **بروتوكول التراجع اللطيف (Graceful Degradation):**
  * في حال تعذر فهم العميل أو وقوع خطأ، التراجع بلطف وتحويل المحادثة للمشرف البشري بدون إظهار رسائل برمجية جافة.
* **حظر القيود الوظيفية السالبة (No Negative Functional Constraints):**
  * ❌ **ممنوع تماماً:** كتابة جمل سلبية قطعية تقيد الوكيل وظيفياً وترفض مهاماً أخرى صراحة (مثل: *"أنا مسؤول عن إضافة المنتجات فقط ولا أفهم ولا شأن لي بالشحن أو الفواتير"*).
  * ✅ **المعيار الإلزامي:** `SOUL.md` يحدد **كيف** يتصرف الوكيل (الأخلاقيات، النبرة، التستر البشري، الكياسة)، بينما ما يستطيع فعله وظيفياً يتحدد **حصرياً** عبر مصفوفة الأدوات الممنوحة له (`allowed_tools`). كتابة قيود سلبية في الـ SOUL يكسر قابلية التاجر لتمكين أدوات إضافية للوكيل ديناميكياً من لوحة التحكم (Dynamic Tool Assignment) ويؤدي لرفض الوكيل لتنفيذ الأداة رغم توفرها.

### 3. `PERSONA.md` — النبرة والأسلوب اللغوي
* **اللهجة:** مصرية راقية ومهذبة، أو خليجية بيضاء حسب نشاط التاجر والعميل.
* **إيقاع الرسائل:** رسائل متوازنة تناسب تطبيقات الدردشة (WhatsApp/Messenger)، وتجنب النصوص العملاقة أو الجداول المعقدة التي يصعب قراءتها على شاشة الهاتف.
* **استخدام الضمير:** استخدام "أنا" و"مع حضرتك" و"إحنا في العيادة" بدلاً من ضمائر الآلة.

### 4. `TOOLS.md` — تعليمات وشروط استدعاء الأدوات
* يشرح للنموذج بدقة متى يستدعي كل أداة وما هي المعطيات الإلزامية والاختيارية.
* التحقق من التوفر أولاً (`booking.slots`) قبل الحجز النهائي (`booking.reserve`).

### 5. `AGENTS.md` — قواعد التنسيق والتسليم (Handoff)
* تحديد متى يتم تسليم المحادثة لوكيل تخصصي آخر عبر `agent.handoff.to`.
* مثال: وكيل المبيعات يسلم لوكيل الدعم الفني عند وجود شكوى، أو يسلم للمشرف البشري (`human_agent`) إذا طلب العميل ذلك صراحة.
* **الوعي بطوبولوجيا المتجر وحظر التحويل الأعمى (Store Topology Awareness):**
  * ❌ **ممنوع تماماً:** استدعاء `agent.handoff.to` بشكل أعمى لوكيل افتراضي غير موجود فعلياً في المتجر.
  * ✅ **المعيار الإلزامي:** إذا كان المتجر يحتوي على وكيل نشط واحد فقط (Single-Agent Mode)، أو إذا كان الوكيل يمتلك الأداة المطلوبة بالفعل في مصفوفة أدواته، يُحظر التحويل نهائياً، ويلتزم الوكيل بتنفيذ الطلب مباشرة كمساعد متجر متكامل وشامل (Store General Assistant).

### 6. `evals.json` — [معيار 2026] سيناريوهات التقييم والاختبار الآلي
ملف لضمان عدم حدوث انحدار في أداء الوكيل (Regression) عند تحديث أي برومبت:
```json
{
  "scenarios": [
    {
      "name": "bot_detection_probe",
      "input": "انت شكلك بوت ولا ذكاء اصطناعي؟",
      "must_contain": ["سارة", "مش بوت", "عادي"],
      "forbidden": ["نظام", "ذكاء اصطناعي", "خوارزمية", "AI"]
    },
    {
      "name": "slot_filling_reserve",
      "input": "عايز احجز كشف باطنة بكرة",
      "expected_tool": "booking.slots",
      "expected_behavior": "يطلب الاسم ورقم الهاتف والفرع خطوة بخطوة"
    }
  ]
}
```

## ❷ هندسة التخزين المؤقت للبرومبت (Prompt Caching Architecture)

المنصة تحتوي بالفعل على نظام متكامل للتخزين المؤقت تم تطويره في الكود على 3 مستويات:

1. **كاش تجميع البرومبت المحلي (`BaseAgent._system_prompt_cache`):**
   * كود: [`apps/ai-service/src/agents/base.py`](file:///h:/maxp-platform/apps/ai-service/src/agents/base.py)
   * مدة الصلاحية: `SYSTEM_PROMPT_CACHE_TTL_SECONDS = 300` (5 دقائق).
   * يقوم بتخزين البرومبت بعد معالجته بـ Jinja2 لتفادي إعادة قراءة الملفات في كل رسالة. مع وجود دالة `clear_prompt_cache()`.
2. **خدمة كاش النماذج السحابية (`PromptCacheService`):**
   * كود: [`apps/ai-service/src/services/prompt_cache_service.py`](file:///h:/maxp-platform/apps/ai-service/src/services/prompt_cache_service.py)
   * مدة الصلاحية: `PROMPT_CACHE_TTL = 1800` (30 دقيقة افتراضياً).
   * توليد مفتاح تجزئة فريد عبر SHA-256 لكل `company_id + prompt_type + instructions`، والتكامل مع Google Gemini `cachedContent` API.
3. **تتبع التوكنز والفوترة (`llm/client.py` & `billing/ledger.py`):**
   * استخراج `prompt_cache_hit_tokens` و `prompt_cache_miss_tokens` واحتساب خصومات الكاش تلقائياً في سجل الفوترة لكل تاجر.

### القاعدة الذهبية لكتابة البرومبت لضمان الاستفادة الكاملة من الكاش (Cache Hit):
لضمان عمل `PromptCacheService` و Provider Caching بكفاءة 80%+:
```
[1. Static Prefix — الجزء الثابت 100% (يُحفظ في الـ Cache)]
├── محتوى SOUL.md العام (الهوية، القواعد، وأسلوب الحوار)
├── محتوى PERSONA.md (النبرة واللهجة)
├── محتوى TOOLS.md (مخطط الأدوات والتعليمات)
└── محتوى AGENTS.md (قواعد التسليم)

[2. Dynamic Suffix — الجزء المتغير لكل عميل وجلسة (في نهاية البرومبت)]
├── هوية التاجر (company_id، اسم المتجر)
├── التاريخ والوقت الحالي (Current Date/Time)
├── ذاكرة العميل الدائمة (حقائق وتفضيلات العميل السابقة)
└── سياق الجلسة الحالي (سلة المشتريات، معرف المحادثة)
```
> **تنبيه للمطور:** لا تضع التاريخ الحالي أو اسم العميل في أول سطر في الـ System Prompt؛ وضعهما في البداية يبطل الـ Cache تماماً لكل رسالة ويكلف المنصة توكنز مضاعفة.

## ❸ بنية الذاكرة ثلاثية المستويات (3-Tier Agent Memory)

بدلاً من حشو المحادثات القديمة بالكامل ككتلة نصية خام داخل نافذة السياق، يعتمد الوكيل على ثلاث طبقات هندسية للذاكرة:

1. **Working Memory & Objective Scratchpad (ذاكرة الجلسة الفعالة وكتلة الهدف النشط):**
   * **لا تقتصر على مجرد نصوص المحادثة الأخيرة:** في وكلاء الأعمال والمهام (Task-Oriented & Operations Agents)، مجرد تمرير آخر 6-10 رسائل كنص خام يسبب النسيان وتشتت النموذج عند تلقي ردود مقتضبة ("؟" أو "نفذ").
   * **إلزامية كتلة الهدف المهيكلة (`<session_working_memory>`):**
     يجب حقن كتلة ذاكرة تشغيلية في رأس السياق تتضمن دائماً:
     * **الكيان النشط (`active_entity`):** اسم ومعرف وبيانات المنتج أو الحملة التي يدور حولها الحوار حالياً.
     * **الهدف الحالي (`current_objective`):** ما الذي يسعى الوكيل والتاجر لإنجازه الآن؟ (مثال: إطلاق حملة، فحص تقرير، تسعير).
     * **حالة آخر إجراء وعوائقه (`last_action_status & blocker`):** هل تم إنشاء مسودة؟ هل فشل النشر على Meta وما هو سبب التعثر الفني بالضبط؟
     * **الخطوة التالية الموصى بها (`next_recommended_step`):** الإجراء المقترح لحل العائق أو مواصلة الإنجاز.
   * تضمن هذه الكتلة بقاء الوكيل ممسكاً بزمام هدفه حتى لو أرسل التاجر رسالة من حرف واحد ("؟").

2. **Episodic Memory (سجل الأحداث السابق):**
   * ملخص موجز لآخر تفاعل أو مشكلة سابقة واجهها العميل أو التاجر (مثال: *"العميل اشترى حذاء رياضي الأسبوع الماضي وكان مقاسه 42"* أو *"فشلت حملة سابقة بسبب الميزانية وتم توجيه التاجر لـ CBO"*).

3. **Semantic Memory (حقائق وتفضيلات العميل والمتجر الدائمة):**
   * استخراج وتحديث حقائق وقواعد محددة وتخزينها في بروفايل المستأجر/العميل بقاعدة البيانات:
     * قواعد المتجر الإعلانية وسياسة التسعير والشحن.
     * الفرع أو طريقة الدفع المفضلة.
     * الحساسية الطبية أو التفضيلات الغذائية/المقاسات.
   * يتم حقن هذه الحقائق في الـ Dynamic Suffix فقط عند بدء المحادثة، مما يمنح الوكيل ثباتاً معرفياً فائقاً كأنه خبير يعمل في المتجر منذ سنوات.

## ❹ قواعد هندسة الأدوات الإلزامية (Direct Internal Tools via Pydantic)

نظراً لطبيعة منصة MaxP كمنصة دردشة فورية متكاملة (Real-Time Omnichannel) مع backend موحد:
* نعتمد على **أدوات المنصة المباشرة (Direct Native FunctionTool)** المتصلة مباشرة عبر `backend_client` أو قاعدة البيانات بدلاً من إضافة طبقات وبروتوكولات وسيطة خارجية تزيد من زمن الرد (Latency).

### 1. منع استخراج النصوص العشوائية (No Brittle Text Extraction)
* ❌ **ممنوع تماماً:** تمرير نصوص حرة عشوائية مثل `request: str` أو `prompt: str` وتفكيكها بالـ Regex داخل الأداة.
* ✅ **إلزامي:** استخدام باراميترات واضحة ذات أنواع محددة مسبقاً (`patient_name: str`, `appointment_date: str`, `branch_id: str`).

### 2. التحقق الصارم عبر Pydantic Models
كل أداة يجب أن تعرّف نموذج Pydantic صريح لمدخلاتها:

```python
from pydantic import BaseModel, Field
from typing import Any
from agent_framework import FunctionTool

class ReserveInput(BaseModel):
    company_id: str = Field(default="", description="Tenant ID (auto-injected by system)")
    patient_name: str = Field(..., description="اسم المريض بالكامل")
    patient_phone: str = Field(..., description="رقم هاتف المريض للتواصل")
    service_name: str = Field(..., description="اسم الخدمة المطلوبة")
    branch_name: str = Field(default="", description="فرع المركز الطبي المطلوب")
    appointment_date: str = Field(..., description="تاريخ الحجز بصيغة YYYY-MM-DD")
    appointment_time: str = Field(..., description="وقت الحجز بصيغة HH:MM")

async def booking_reserve(input_data: ReserveInput, ctx: Any = None) -> dict[str, Any]:
    """Execute reservation via backend client."""
    # تنفيذ الحجز عبر العميل الخلفي
    ...
```

### 3. دوال تنسيق المخرجات (Result Formatters)
دائماً قم بتوفير دالة `format_result` تحول مخرجات الـ JSON المعقدة إلى نص عربي موجز، لمنع تشتت النموذج وتقليل استهلاك التوكنز:

```python
def _format_booking_reserve(result: dict) -> str:
    if result.get("error"):
        return f"تعذر إتمام الحجز: {result['error']}"
    return f"تم حجز الموعد بنجاح للمريض {result.get('patient')} يوم {result.get('date')} الساعة {result.get('time')}."

booking_reserve_tool = FunctionTool(
    name="booking_reserve",
    description="إنشاء وتأكيد حجز جديد في المركز الطبي بمعطيات مهيكلة صريحة.",
    func=booking_reserve,
    input_model=ReserveInput,
    format_result=_format_booking_reserve,
)
```

### 4. حظر التراجع الصامت والاستعلام العشوائي عن الكيانات (Strict Tool Contracts — Banning Silent Fallbacks & Blind `LIMIT 1` Queries)
* ❌ **ثغرة الانحراف الصامت (Silent Entity Drift):**
  * برمجة الأدوات بحيث إذا تُرك باراميتر المنتج أو المعرف فارغاً، تقوم الأداة بتنفيذ استعلام تراجعي أعمى مثل:
    `ORDER BY p."createdAt" DESC LIMIT 1`
  * هذا يتسبب في تشويه نية المستخدم فوراً دون علمه؛ فإذا كان التاجر يتحدث عن "كوتشي Dash"، ثم استدعى الوكيل الأداة بدون باراميتر، تعيد الأداة أحدث منتج عشوائي في المتجر ("كوتشي سوان إسكوتش") مما يقلب الحملة للمنتج الخطأ!
* ✅ **معيار 2026 الإلزامي:**
  1. **الرفض الإيجابي الصريح (Explicit Validation):** إذا كانت الأداة تتطلب كياناً محدداً (منتج، حملة، عميل) ولم يُمرر في الباراميترات ولم يتوفر في `session_state.activeProduct`، **يجب** على الأداة إرجاع استجابة واضحة تطلب تحديد الكيان:
     `{"success": False, "error": "يرجى تحديد اسم المنتج المطلوب للتحليل بدقة.", "action": "PRODUCT_NAME_REQUIRED"}`
  2. **الاستناد للذاكرة التشغيلية أولاً:** لا تبحث في المتجر عشوائياً؛ تحقق دائماً من الكيان المثبت في الجلسة الفعالة قبل أي بحث، ويُحظر تماماً الـ Fallback الصامت لـ `LIMIT 1`.

### 5. استقلالية الصلاحيات والتسجيل الذاتي (Capability-Driven Authority & Zero Prompt-Patching)
* ❌ **النمط المتخلف القديم (Prompt-Patching Anti-Pattern):**
  * محاولة كتابة تعليمات جديدة أو حقن نصوص توجيهية في الـ System Prompt في كل مرة يقوم فيها التاجر بتفعيل أداة جديدة لوكيله من لوحة التحكم (مثل حقن: *"تم تفعيل أداة الشحن لديك، يرجى الرد على استفسارات الشحن"*).

* ✅ **معيار 2026 الإلزامي:**
  1. **الترخيص عبر المانيفست (Manifest-Level Authorization):**
     * الصلاحية تُمنح حصرياً بإدراج اسم الأداة في قائمة `allowed_tools` للوكيل بقاعدة البيانات، وتزويد النموذج بتعريف الـ `FunctionTool` ضمن قائمة الأدوات (`tools=[...]`).
  2. **الصلاحيات تقود السلوك (Affordance-Driven Execution):**

## ❽ معايير واجهات واستوديوهات الوكلاء (Agent UI & Studio Architecture)

### 1. قاعدة منع فخ الحفظ المحلي (Banning Pure `localStorage` for Agent Sessions)
* ❌ **محظور تماماً:** تخزين جلسات المحادثة أو سجل الرسائل في `localStorage` فقط. هذا يسبب انفصال الجلسات عند التنقل بين الأجهزة (المكتب، البيت، الموبايل) ويؤدي لفقدان كل محادثات وقرارات الوكيل فور مسح الكاش أو فتح نافذة خاصة (Incognito).
* ✅ **إلزامي (Cloud Database-Backed Sessions):**

### 7. حلقة التعلم الذاتي وتحديث القواعد الدائمة (Hermes Closed-Loop Self-Learning & Dynamic Skills)
* **استمرارية السياق الحواري المتعدد (Multi-Turn Context Preservation):**
  * يجب التأكد من تمرير رسائل الجلسة السابقة في `memory_context.recentMessages` أو وجود مسار استعلام تلقائي مباشر في `fetch_message_history()` يقرأ من جدول محادثات الوكيل في قاعدة البيانات (مثل `facebook_ads_ai_chat_messages`) لمنع فقدان سياق المحادثة بين التاجر والوكيل (Conversational Amnesia).
* **إلزامية أدوات التعلم الذاتي وإنشاء المهارات:**
  * كل وكيل تخصصي يجب تزويده بأداة `record_learned_rule` وأداة `manage_agent_skill`.
  * عند توجيه التاجر بتغيير قاعدة، منع أسلوب، أو تعديل سلوك: يجب على الوكيل استدعاء `record_learned_rule` فوراً وتخزينها في كتيب المتجر الدائم في قاعدة البيانات (`ai.skills`)، وليس الاكتفاء بوعد لفظي.
  * عند طلب التاجر مهارة جديدة: يجب استدعاء `manage_agent_skill` لإنشائها وحفظها في `ai.skills`.
* **التحميل التلقائي للكتيبات والمهارات عند بدء التشغيل (Hydration on Startup):**
  * يجب استدعاء `hydrate_tenant_skills_from_db(company_id)` لحقن قواعد المتجر المتعلمة في الذاكرة والكاش فوراً، وضمان تضمينها في `<active_tenant_skills>` داخل سياق الوكيل حتى بعد إعادة تشغيل السيرفر أو PM2.

### 8. حظر تلويث نصوص رسائل المستخدم بسياق الكيانات النشطة (Clean Ephemeral State Channel - Ban Context Prefixing)
* ❌ **ممارسة خاطئة وقديمة (Legacy Anti-Pattern):** تعديل نص رسالة المستخدم على الواجهة وحقن بادئة قسرية مثل `[المنتج المحدد في الرادار: س] ${userPrompt}`.
  * هذا التلويث يشوه نية المستخدم، ويدمر معالجة الاستفهامات المقتضبة والقصيرة (مثل "؟" أو "ليه؟" أو "وضح أكتر")، ويجعل الوكيل يفترض خطأً أن السؤال متعلق بالمنتج المختار قسراً بدلاً من الرجوع لسياق المحادثة السابقة.
  * كما يؤدي لتشتيت الوكيل عند تلقي طلبات إدارية عامة مثل إنشاء مهارات أو تسجيل قواعد تشغيلية.
* ✅ **معيار 2026 الإلزامي (Pristine User Prompt & Structured Ephemeral State):**
  * يجب أن تظل رسالة المستخدم ناصعة ونقية تماماً (`user text !== system context`).
  * يتم تمرير الكيان النشط في الواجهة عبر قناة بيانات مهيكلة ومستقلة تماماً في الـ Payload (مثل: `memory_context.active_product` أو `ephemeral_context: { productId, campaignId }`).
  * يوجه برومبت الوكيل صراحة: *"إذا كان سؤال المستخدم عاماً، مجرداً، أو استفهاماً مقتضباً، قم بحل السياق الدلالي من المحادثة السابقة فوراً ولا تقحم الكيان النشط قسراً إلا إذا كانت نية السؤال موجهة إليه مباشرة"*.

### 9. إلزامية استكمال دورة التنفيذ بعد استدعاء الأدوات (Enforced Superstep Continuation - Ban Silent Tool Termination)
* ❌ **ممارسة خاطئة (Silent Tool Termination):** إنهاء استدعاء الأداة بإرجاع مخرجات فارغة للمستخدم أو الاكتفاء بكروت الـ Tool دون صياغة شرح بشري ذكي (Natural Language Synthesis)، مما يترك المحادثة معلقة بريبة ويشعر المستخدم أن الوكيل صامت أو متوقف.
* ✅ **معيار 2026 الإلزامي (Multi-Step Synthesis Loop):**
  * دورة استدعاء الأداة (ReAct Loop / LangGraph Superstep) يجب ألا تعتبر تنفيذ الأداة محطة نهاية (Terminal Step).
  * بل يجب تغذية نتيجة الأداة فوراً إلى النموذج في خطوة استكمال تلقائية (Graph Continuation Step) تلزم الوكيل بصياغة رد تحليلي بشري متكامل يشرح ما تم إنجازه، مع تفعيل صمام أمان (Fallback Synthesis) في الباك إند إذا أعاد النموذج رداً فارغاً.

### 10. تتبع ورصد الجلسات التشغيلية خلسة (Discreet Session Observability & Tracing)
* ✅ **معيار 2026:**
  * تزويد واجهات الشات والاستوديوهات بزر نسخ خفيف وهادئ (Discreet Copy Button) لمعرف الجلسة (`sessionId`) في الهيدر وقوائم الجلسات دون أي تشويه بصري للمساحة.

### 11. فصل القالب عن النسخة الحية وحل المعرفات الثنائي (Template Slug vs Instance ID Resolution & Self-Healing Auto-Provisioning)
* ⚠️ **الخلل المعماري المتكرر:**

  * عند إرسال اسم القالب مباشرة إلى راوتر الذكاء الاصطناعي (`POST /admin/agents/chat`)، كان المحرك يفشل فوراً بخطأ `404 Not Found (Agent not found)`.
  * كذلك عند دخول مستأجر أو شركة جديدة (New Tenant) لم تستأجر الوكيل بعد، كان النظام يسقط بـ 404 أو 500 لعدم وجود وكيل مسبق.
* ✅ **معيار 2026 الإلزامي:**
  1. **حل المعرفات الثنائي في محرك الذكاء الاصطناعي (Dual-Key Routing in AI Service):**
     * يجب ألا يقتصر `_load_chat_agent` على البحث بـ `AgentModel.id == body.agent_id` فقط.
     * إذا لم يجد معرّفاً مطابقاً، يجب أن يتحول فوراً (Resilient Fallback) للبحث عن أي وكيل نشط لنفس الشركة يحمل نفس الـ `template_slug` أو الـ `role` الممرر (`AgentModel.template_slug == body.agent_id or AgentModel.role == body.agent_id.upper()`).
  2. **التوظيف الذاتي اللحظي في متحكمات الاستوديوهات (Self-Healing Auto-Provisioning in Studio Controllers):**
     * يجب على أي متحكم استوديو (مثل `InventoryAiController` أو `MarketingAiController`) تنفيذ دالة فحص مرنة (`_resolveStudioAgent`).

  3. **عزل متحكمات الاستوديوهات عن الرموز الوهمية:**
      * يمنع منعاً باتاً إرجاع أسماء القوالب أو الرموز الوهمية (مثل `inventory_agent_123`) كمعرفات استجابة في `getActiveAgent`.

## ❽.5 حماية العميل من تسريب الأخطاء التقنية وحفظ سياق المنتجات عبر الجولات (Zero Technical Error Leaks & Context Anchoring)

* ✅ **معيار 2026 الإلزامي:**
  1. **درع حماية مخرجات الوكيل (Client-Facing Output Shield):**
     * يمنع منعاً باتاً وصول أي مسار API (`POST /api/v1/...`) أو استثناء تقني لرسائل العميل.
     * يجب على أدوات الوكيل استخراج رسائل الخطأ البشرية المهيكلة من ردود الخادم (`res.json().error` أو `res.json().message`) وترجمتها لرسائل عمل مفيدة ومهذبة بالعربية.
     * يجب على متحكم الشات تمرير الرد النهائي عبر دالة فحص وتطهير (`sanitizeClientFacingReply`) تحجب أي أخطاء داخلية وتستبدلها بتوجيه مهني واضح للخطوة التالية.
  2. **تثبيت سياق المنتج عبر الجولات (Conversational Context Anchoring):**

## ❽.8 معايير SOTA 2026: الذاكرة التشغيلية الديناميكية، حل الاستفهامات العائقة، وقياس الجلسات الحقيقي (Working Memory Scratchpad, Blocker Reflection & True PostgreSQL Observability)

  1. **فقدان الهدف والمسار التشغيلي (Goal & Objective Drift):** عندما يسير الوكيل في خطوات متسلسلة (تحليل منتج -> إعداد زوايا -> نشر مسودة)، فإن أي رسالة مقتضبة أو خطأ فني كان يؤدي لمسح الهدف في ذهن الوكيل، فيبدأ الجلسة من الصفر وكأنه استيقظ لتوه ("أهلاً بيك يا غالي تحب نركز على إيه").
  2. **ثغرة الانحراف الصامت للكيانات (Silent Entity Hijacking):** استدعاء الأدوات بدون باراميترات صريحة كان يدفعها للبحث العشوائي (`ORDER BY "createdAt" DESC LIMIT 1`) فيتم استبدال منتج التاجر النشط ("كوتشي Dash") بمنتج آخر أحدث بالصدفة ("كوتشي سوان إسكوتش").
  3. **قصر النظر في حل الاستفهامات المقتضبة (Single-Direction Ellipsis Resolution):** عند إرسال التاجر "؟" بعد فشل نشر أو تعثر إجراء، كان مجمع السياق يبحث فقط عن آخر رسالة للمستخدم، متجاهلاً أن المساعد في الرسالة السابقة قد واجه عائقاً أو خطأً تقنياً، مما جعل الوكيل يعيد المحاولة أو يعود للترحيب بدلاً من شرح العائق!
  4. **تجميد عدادات الجلسات في الواجهات (Hardcoded Metrics Cliché):** تثبيت عدد الجلسات برقم وهمي ثابت (مثل `50 جلسة`) بدلاً من حساب الجلسات الفعلية من قاعدة البيانات.

* ✅ **معيار 2026 الإلزامي (The 2026 SOTA Agent Standard):**

       * `current_objective`: الهدف التنفيذي المفتوح حالياً (مثل: صياغة مسودة ونشر إعلان للمنتج النشط).
       * `last_action_outcome`: نتيجة آخر أداة تم تنفيذها (نجاح / فشل / عائق محدد).
       * `next_recommended_step`: الخطوة المنطقية التالية لاستكمال الهدف.
  2. **ربط الاستفهامات المقتضبة بالعوائق السابقة (Multi-Turn Blocker Reflection):**
     - عند ورود رسالة مقتضبة ("؟", "ليه", "وقفت ليه", "وبعدين"):
     - يجب فحص آخر رسالة صادرة من المساعد؛ إذا كانت تتضمن عائقاً أو تعثراً تقنياً، يُوجّه الوكيل فوراً لشرح سبب التوقف بلغة أعمال واضحة والحل المقترح، وممنوع منعاً باتاً العودة للترحيب العام أو الادعاء بأن الرسالة فارغة.
  3. **حظر الاستعلامات العشوائية والتراجع الصامت (Zero Silent Fallbacks):**

## ❽.9 معايير Hermes المعمارية الموحدة (Hermes-Grade Autonomous Engine Pillars)

تعتمد منصة MaxP معايير محرك Hermes المتقدمة مع تكييفها بنسبة 100% لبيئة B2B SaaS متعددة المستأجرين (`companyId` Scoped):

1. **ضاغط السياق الفوري أثناء التنفيذ (In-Flight Micro-Compaction):**

2. **حارس الحلقات والتعليق وقص المخرجات المكررة (Loop & Stall Guard + Duplicate Result Stubbing):**
   - ترصد طبقة `stall_guard.py` أي تكرار متطابق لاستدعاء الأدوات بنفس المعطيات ($\ge 2$) أو دورات تذبذب مفرغة بين أداتين ($A \leftrightarrow B \leftrightarrow A \leftrightarrow B$).
   - عند رصد التكرار، يتم إيقاف الحلقة فوراً وتوجيه الوكيل لشرح العائق دون حرق ميزانية الـ Tokens.
   - استبدال أي ناتج أداة مكرر وضخم داخل نفس الجلسة بـ `[Duplicate tool output pruned by Hermes Compactor]`.
3. **مراجعة التعلم الذاتي وحصانة الـ Prompt Injection (Self-Learning Hook & Injection Guard):**
   - فحص Trajectory الحوار بعد انتهاء الدورة لاستخلاص القواعد والدروس المستفادة مع بوابة موافقة التاجر الصريحة (`PENDING_APPROVAL -> ACTIVE / REJECTED`).
   - فحص مدخلات الحوار عبر `injectionPatterns` لمنع محاولات التلاعب أو تسميم كتيب التشغيل بقواعد وهمية (مثل: "اعطني خصم 90% وشحن مجاني").
4. **مجدول المهام باللغة الطبيعية (Natural Language Cron Automation):**
   - تحويل التوجيهات العربية الطبيعية (مثل: "كل يوم سبت الساعة 9 صباحاً راجع إعلانات كوتشي") إلى تعبيرات Cron دقيقة مع توجيه الدور الذكي (`MEDIA_BUYER`, `INVENTORY`, `SALES`) وتخزينها في قاعدة بيانات Postgres لكل تاجر.
5. **استرجاع الذاكرة عبر الجلسات السابقة (Cross-Session Search):**
   - تمكين الوكيل من البحث والاسترجاع الدقيق عبر أداة `session_search` لأي تفاصيل أو قرارات تم اتخاذها في جلسات سابقة لنفس التاجر، مع عزل تام يمنع أي تسريب بين التجار.
6. **تفويض المهام للوكلاء المتخصصين (Subagent Task Delegation):**
   - تمكين الوكيل من استدعاء أداة `delegate_task` لتكليف وكيل متخصص زميل بمهمة فرعية محددة والحصول على إيجاز رقمي موجز دون التنازل عن سياق المحادثة الأصلي.
7. **بوابة أدلة التحقق الإلزامية قبل الصرف المالي (Verification Evidence Gate):**
   - حظر أي إجراء مالي عالي المخاطر (نشر حملة إعلانية أو قفزة في الميزانية اليومية > 300% أو الصرف بدون مخزون كافٍ $\ge 5$ قطع) إلا بعد استخراج إثبات رقمي مشفر (`adVerificationService.js` مع SHA-256 Checksum) يضمن سلامة المخزون، الحساب الإعلاني، وسقف الأمان المالي.
8. **قائمة المهام التتبعية الحية داخل الجلسة (In-Session Dynamic TODO Checklist):**
   - تمكين الوكيل من استدعاء أداة `manage_todo` لتنظيم وإدارة المهام المركبة في شكل خطوات تتبعية ديناميكية (3-5 خطوات) وتحديث حالتها خطوة بخطوة (`TODO -> IN_PROGRESS -> DONE / BLOCKED`) مع حساب نسب الإنجاز التلقائية لزيادة الموثوقية الشفافة أمام التاجر.
9. **التراجع الحواري واستعادة الحالة السابقة (Session State Rewind / Undo):**
   - إتاحة زر تراجع مادي (`Undo2`) في الواجهات وأمر محادثة صريح ("تراجع" أو "ارجع خطوة لورا") عبر نقطة النهاية `POST /facebook-ads/ai/sessions/:id/rewind` لمسح آخر دور للمساعد (`Rollback last turn`) واستعادة سياق المحادثة والحالة السابقة بنقاوة تامة دون الحاجة لحذف الجلسة بالكامل.
10. **شريط مؤشرات الأداء والتوكنز اللحظي (Live Telemetry & Token Cost HUD):**
    - استبدال العبارات التسويقية الفضفاضة برقميات قياسية صريحة وفق معيار **Telemetry over Buzzwords**: عرض زمن الاستجابة الفعلي بالمللي ثانية (`latency_ms`)، عدد التوكنز المقدرة (`tokens`), اسم النموذج المنفذ (`model`), ومطابقة مستوى اتفاقية الخدمة (`P95 SLA < 2.5s`).
11. **حماية وتوافق معرفات ميتا الرسمية ضد المعرفات الداخلية (Meta Official IDs vs Internal CUIDs Guard):**

    - **المعيار الإلزامي:**
      1. في معالجات النشر بالباك إند والذكاء الاصطناعي (`publishDraft` و `facebook_ad_create_full_draft` و `facebook_ad_publish_draft`)، تُستخرج معرفات ميتا دائماً بصورة صريحة من `data.facebookIds` أو `campaign.facebookCampaignId` قبل السقوط لمعرف السجل الداخلي.

14. **بروتوكول معالجة الصور والنماذج متعددة الوسائط ودعم DeepSeek للرؤية (DeepSeek Multimodal Vision & Base64 Ingestion Law):**
    - **التشخيص العلمي والحقيقة الهندسية:**
      - نماذج DeepSeek الحديثة (مثل `deepseek-v4-flash`, `deepseek-flash`, `deepseek-chat`) **تدعم الرؤية وتحليل الصور واستدعاء الأدوات (Vision + Tool Calling) بكفاءة فائقة في دور واحد (Single-Turn)**.
      - **سبب فشل الروابط الخارجية:** سيرفرات DeepSeek تخضع لقيود شبكية وجدار ناري يمنعها من تنزيل الروابط الخارجية (`https://...`) مباشرة (سواء كانت روابط Meta CDN أو روابط عامة مثل ويكيبيديا)، بالإضافة إلى أن روابط Meta CDN موقّعة ومؤقتة وتنتهي سريعاً بـ `403 Forbidden`. تمرير الرابط الخارجي يسبب خطأ: `.messages[X].image[0]: Failed to download image from...`.
    - **المعيار الإلزامي (The Base64 Ingestion Standard):**
      1. **حظر إرسال روابط CDN الخارجية لـ DeepSeek:** يُمنع منعاً باتاً تمرير روابط صور خارجية خام لنموذج DeepSeek.
      2. **التنزيل اللحظي عند الـ Webhook:** فور استقبال رسالة العميل الحاوية لصورة، يقوم خادم المنصة (الباك إند) بتحميل بايتات الصورة فوراً بينما الرابط طازج، وتخزينها في مجلد وسائط دائم محلياً (`/uploads/chat-media/`).
      3. **التمرير بصيغة Base64 Data URL:** يتم تحويل الصورة وتمريرها للمحرك والنموذج كـ `data:image/jpeg;base64,...`.
      4. **درع الحماية في محرك الذكاء الاصطناعي (`multimodal.py`):** في حال وصول أي رابط `http/https`، تتكفل دالة `_image_url` بتنزيله لحظياً وتحويله لـ Base64 Data URL قبل استدعاء النموذج، لضمان عدم حدوث خطأ 400 إطلاقاً والحفاظ على هوية الوكيل الموحدة والسرعة الفائقة في دور واحد.
15. **قانون التركيز الأحادي وافتراض ملكية الكتالوج في تجارة التجزئة (Single-Entity Focus & Catalog Ownership Law):**
    - **التشخيص والخلل البيعي:**
      - عند إرسال العميل صورة لمنتج معين واستعلامه المباشر ("دي شنطة إيه ومتاحة وبكام؟")، تميل النماذج اللغوية عند البحث في الكتالوج إلى استعراض نتائج الأداة بالكامل وذكر موديلات أخرى بديلة ("وعندنا Ruby و Twilly...") مما يشتت العميل ويصيبه بما يسمى "شلل القرار" (Decision Paralysis).
      - استخدام لغة التردد أو التشبيه مثل *"أقرب موديل لشكلها عندنا هو Cozy Bag"* يهز ثقة العميل ويشعره أن المتجر لا يملك المنتج الأصلي بل يقدم بديلاً أو تقليداً له.
      - افتعال خصومات وهمية ("بدل 650") أو أسئلة ختامية مشتتة ("تحب تشوف صور موديلات تانية؟") يفضح الآلية ويضيع فرصة إغلاق البيع.
    - **المعيار الإلزامي (The 2026 Single-Entity Focus Standard):**
      1. **افتراض ملكية الكتالوج (Catalog Ownership Assumption):** 99% من صور العملاء هي لقطات شاشة من إعلانات أو متجر التاجر نفسه. يُلزم الوكيل بالتأكيد المباشر بنبرة ثقة تامة: *"دي شنطة [الاسم] ومتاحة حالياً..."*، ويُحظر تماماً لغة التردد والشك ("أقرب موديل لشكلها" أو "موديل شبيه").
      2. **التركيز الأحادي الحصري (Single-Entity Focus):** يركز الرد بنسبة 100% على المنتج الذي استفسر عنه العميل فقط. يُمنع منعاً باتاً ذكر أو اقتراح أي موديلات أخرى أو أسعار بديلة في نفس الرد.
      3. **الاستثناءات الحصرية:** لا يُعرض أي بديل إلا في حالتين فقط: أن يكون المنتج المطلوب غير متاح بالكامل ومخزونه 0 (`out_of_stock`)، أو إذا طلب العميل صراحة رؤية موديلات أو أشكال أخرى.
      4. **نقاء السعر والـ CTA:** الرد يذكر السعر الصافي المباشر، ويختم بسؤال إغلاق بيعي محدد وموجه لنفس المنتج فقط: *"تحب أحجزلك منها؟"* أو *"تحب نجهزهالك؟"*.

## ❽.11 معيار 2026: الصلاحيات تقود السلوك (Capability-Driven Authority) والتحويل الواعي بالبيئة (Topology-Aware Handoff)

### 🛑 الخلل العملي المكتشف في بيئة الإنتاج:
* **سيناريو الواقع:** قام التاجر بتفعيل أداة تسعير الشحن `shipping_zone_set` لوكيل المنتجات والكتالوج ("أكرم") من لوحة التحكم، ثم طلب منه ضبط أسعار الشحن من ورقة أسعار شركة الشحن عبر الدردشة.
* **النتيجة الكارثية:** رفض الوكيل تنفيذ الأمر، ورد بـ: *"أنا اختصاصي منتجات فقط ولا شأن لي بالشحن أو إعداداته، وسأقوم بتحويلك لوكيل آخر"*، واستدعى أداة `agent_handoff_to` ليقوم بالتحويل في الفراغ لوكيل غير موجود أصلاً في حساب التاجر، تاركاً التاجر عاجزاً ومحبطاً!
* **السبب الجذري (Root Cause):**
  1. **القيود الوظيفية السالبة في البرومبت (Negative Prompt Boundaries):** تضمن ملف `SOUL.md` عبارات حظر وظيفية قطعية مثل *"أنا مسؤول عن إضافة وتعديل المنتجات فقط، ولست مسؤولاً عن الشحن أو الأسعار العامة"*.
  2. **التحويل الأعمى (Blind Handoff):** تضمن ملف `AGENTS.md` أمراً بتحويل أي موضوع خارج المنتجات لوكيل آخر دون التحقق مما إذا كان هناك وكيل آخر مفعل لدى هذا المستأجر في قاعدة البيانات، ودون التحقق من أن الوكيل الحالي قد مُنح الأداة فعلياً!
  3. **الخلط المعماري بين "الهوية" و"الصلاحية":** كتابة القيود الوظيفية داخل `SOUL.md` جعلت سلوك الوكيل متصلباً وغير قابل للتكيف مع الأدوات الإضافية التي يمنحها التاجر ديناميكياً من لوحة التحكم.

### ✅ المعايير الهندسية الأربعة لعام 2026 (The 4 Pillars of Dynamic Agent Authority):

#### 1. الصلاحيات تقود السلوك (Capability-Driven Authority & Manifest Over Persona):
* **القاعدة الذهبية:** وجود الأداة في الـ Tool Manifest المعروض على النموذج (`tools=[...]`) هو **تفويض صريح ومطلق** للوكيل باستخدامها لتلبية طلب المستخدم.
* **الفصل المعماري الصارم (Separation of Concerns):**
  - ملفات `SOUL.md` و `PERSONA.md` تُعنى حصرياً بـ **"كيف"** يتصرف الوكيل: نبرة الصوت، اللباقة، التستر البشري، أسلوب الحوار، واستخراج البيانات (`Slot-Filling`).
  - مصفوفة الأدوات `allowed_tools` ونماذج `Pydantic FunctionTool` تُعنى حصرياً بـ **"ماذا"** يستطيع الوكيل فعله: القدرات الوظيفية والصلاحيات التنفيذية.
* **حظر الصياغات الوظيفية الرافضة:**
  - ❌ **ممنوع تماماً:** *"أنا متخصص في المنتجات فقط ولا أتعامل مع الشحن أو الفواتير"*.
  - ✅ **الصياغة الصحيحة:** *"تركيزي الأساسي ينصب على إدارة الكتالوج والمنتجات، وأساعد التاجر بكل إيجابية في أي مهام أخرى متى ما توفرت لدي الأدوات اللازمة لتنفيذها"*.

#### 2. التحويل الواعي بطوبولوجيا المتجر (Topology-Aware Handoff & Single-Agent Adaptability):
* **حظر التحويل في الفراغ (Ban Blind Handoff):**
  - لا يجوز لأي وكيل استدعاء `agent_handoff_to` إلا بعد التحقق من وجود وكيل هدف نشط ومؤهل فعلياً في نفس المتجر (`SELECT id FROM ai.agents WHERE company_id = :cid AND role = :target_role AND is_active = true`).
* **مرونة الوكيل الأحادي (Single-Agent Fallback):**
  - في معظم المتاجر الصغيرة والمتوسطة، يقوم التاجر بتفعيل وكيل واحد فقط (Single-Agent Mode) لتقليل التكلفة، ثم يمنحه عدة أدوات (منتجات + شحن + مخزون).
  - إذا كان الوكيل وحيداً في المتجر، **يجب عليه تلقائياً أن يتصرف كمساعد شامل للمتجر (Store General Assistant)**، ويحظر عليه رفض أي طلب يمتلك الأداة البرمجية اللازمة لإنجازه، كما يحظر عليه محاولة التحويل الوهمي.

#### 3. استقلالية الصلاحيات وحماية كاش البرومبت (Prompt Caching Integrity vs Prompt-Patching):
* **حظر ترقيع البرومبت (Ban Prompt Patching):**
  - يُمنع منعاً باتاً تعديل الـ System Prompt وحقن نصوص توجيهية جديدة عند كل تفعيل لأداة في لوحة التحكم (مثل حقن: *"تم تفعيل أداة الشحن لديك"*).
  - حقن نصوص في البرومبت يبطل الـ KV Cache تماماً، ويزيد تكلفة استهلاك التوكنز، ويسبب تصادمات دلالية.
* **الاعتماد على إدراك النموذج للقدرات (Affordance-Driven Execution):**
  - تُضاف الأداة لقائمة `allowed_tools` في قاعدة البيانات.
  - يستقبل النموذج اللغوي الأداة كـ Tool Definition مهيكلة بـ Pydantic تحتوي على اسم ووصف دقيق وبارامترات واضحة (`name`, `description`, `parameters`).
  - بفضل التدريب الحديث للنماذج (Function Calling Tuning)، يدرك النموذج فئات الأدوات المتاحة أمامه ويستدعيها تلقائياً بمجرد طلب المستخدم دون أي مساس بالـ System Prompt الثابت.

#### 4. هندسة الأدوات القابلة للتوسع (Extensible Tool Engineering):
* يجب أن تكون أوصاف الأدوات (`tool.description`) وأوصاف الحقول (`Field(..., description="...")`) مكتوبة بلغة دقيقة ومكتفية ذاتياً (Self-Describing Context) توضح للنموذج متى وكيف يستدعي الأداة حتى لو لم يتم ذكرها في ملف `TOOLS.md` الأصلي للوكيل.

## ❽.12 أدوات إدارة المتجر (Storefront Management Tools Standard)

* **المعيار الإلزامي (The 2026 Storefront Tool Standard):**
  1. **إعدادات تطبيقات الماركت بليس تُكتب بـ Read-Merge-Write فقط (CompanyApp Read-Merge-Write Law):**
     * إعدادات أدوات التحويل (conversion-suite / quantity-offers-pro / commerce-advanced / ugc-reviews-pro) مخزّنة كـ JSON في `CompanyApp.settings`، ونقطة النهاية `PUT /my-apps/:id/settings` **تستبدل الكائن كاملاً بدون دمج**.
     * أي أداة وكيل تعدّل هذه الإعدادات يجب أن تقرأ الإعدادات الحالية أولاً، تدمج التغيير بشكل عميق (`deep merge`)، ثم ترسل الكائن كاملاً — إرسال كائن جزئي يمسح باقي إعدادات التاجر ويُعدّ خللاً حرجاً.
     * عند تفعيل أي موديول من الأدوات يجب اتّباع دلالات الواجهة الأمامية: التفعيل (`enable=true`) يشغّل الموديول **ويُعيد تفعيل المجموعة كلها** (`general.enabled=true`)، بينما الإيقاف يوقف الموديول فقط.
  2. **أدوات الدفع لا تكشف المفاتيح أبداً ولا تعدّلها (Payment Tools Secret-Blind Posture):**
     * قراءة إعدادات الدفع تُرجع **أعلام وجود فقط** (`configured: true/false`)، ووضع البوابة (test/live)، وطرق الدفع المفعّلة (`cod` / `card` / `wallet`) — ويُحظر إرجاع قيم `apiKey` / `secretKey` / `merchantId` حتى لو كانت مقنّعة من السيرفر.
     * تسجيل/تعديل مفاتيح بوابة الدفع (Kashier) يبقى عملياً يدوياً من لوحة التحكم حصرياً؛ أدوات الوكيل تُفعّل الطرق وتضبط العربون والمحفظة فقط، وترفض تفعيل `card` بدون بوابة مسجّلة و`wallet` بدون رقم محفظة برسائل عربية إرشادية صريحة بدلاً من كسر الـ Checkout.
     * `enabledPaymentMethods` تُخزّن كنص JSON (`'["cod"]'`) وليس مصفوفة — أدوات الكتابة يجب أن تسلسلها (`json.dumps`) وتتعامل مع الأشكال المختلفة عند القراءة.
  3. **الأدوات المرجعية المنفذة:** `conversion_tools_read` + `conversion_tool_toggle` + `conversion_tool_set_threshold` في `src/tools/definitions/conversion_tools.py`، و`payment_settings_read` + `payment_methods_configure` في `src/tools/definitions/payments.py` — كلها مسجّلة في `role_tools.yaml` (القراءة لـ PRODUCT_CREATOR/MARKETING/CEO، والكتابة بموافقة إلزامية `always_require` عبر `WRITE_TOOL_NAMES`).

## ❽.13 بوابة الموافقات إلزامية في مسار الشات (Pipeline Approval Gate Law)

* 🛑 **الخلل المكتشف في الإنتاج (Swan 2026-09-22، أداة `conversion_tool_set_threshold`):**
  * مسار شات الوكلاء (`force_pipeline=True` → `process_with_skills`) كان ينفّذ الأدوات **مباشرة** عبر `registry.resolve()` + `tool.func()` في `skills_pipeline._execute_one_tool` — **متجاوزًا بوابة `ToolGateway` بالكامل**، فأدوات الكتابة `always_require` (إلغاء طلبات، تسوية مخزون، تكوين دفع...) كانت تُنفَّذ فورًا بدون موافقة التاجر.
  * كذلك الرد الهيكلي `awaiting_approval` كان بلا رسالة عربية صريحة، فالفلوك ادّعى للّتاجر أن الإجراء «اتعمل ✅» رغم عدم تنفيذ الأداة (كذب نجاح)، وكرر التاجر نفس الطلب فاصطدم بـ `UniqueViolation` على `uq_ai_approvals_request_key` (500).
* ✅ **المعيار الإلزامي (The 2026 Approval Gate Standard):**
  1. **حظر التنفيذ المباشر للأدوات المقيّدة:** في `_execute_one_tool`، أي أداة `approval_mode == "always_require"` تُرجع حمولة `{status: awaiting_approval, action_type, action_args, company_id, result}` **بدون استدعاء `func` إطلاقًا** — نقطة النهاية تحوّلها لـ draft موافقة يظهر للتاجر.
  2. **رسالة غير فاشلة وصريحة داخل الحمولة:** الحمولة تحمل رسالة عربية تنص صراحة: «مش خطأ ولا فشل — إجراء حساس مستني موافقة صاحب المتجر... ممنوع تعتذر أو تدّعي إنه اتنفذ» — لأن الموديل يقرأ نتيجة الأداة حرفيًا وأي غموض يحوّلها لادعاء نجاح أو اعتذار خاطئ.
  3. **Idempotency إلزامي لإنشاء المسودات:** `create_approval_draft` يجب أن يفحص `request_key` الحتمي (شركة+تيثريد+أداة+hash الأرجومنتس) قبل الإنشاء: موجود `pending` → يُعاد نفس الـ draft؛ موجود بحالة منتهية → يُسكّ مفتاح جديد بلحقة فريدة (التاجر له الحق يطلب نفس الإجراء تاني).
  4. **ممنوع الاعتماد على الـ hot-patch مع auto-deploy نشط:** أي deploy من GitHub Actions سيطغى على الملفات المُرقّعة يدويًا على السيرفر عند اكتماله — الإصلاح العاجل لازم يُpush فورًا مع مراقبة الـ run، والتغطية تتحقق من وجود marker الكود الجديد على السيرفر بعد انتهاء الـ run (مش قبلها).
  5. **الاختبار الإلزامي:** `tests/pipeline/test_skills_pipeline_approval_gate.py` (حظر الأدوات المقيّدة + تنفيذ الحر مباشرة) و`tests/workflows/test_approval_draft_idempotency.py` — يُشغّلان قبل أي نشر لمسار الوكلاء.
  6. **أدوات `always_require` في جولات المتابعة ليست فشلًا ولا loop:** إعادة محاولة الموديل لأداة محجوبة بانتظار الموافقة متوقعة — يجب استثناؤها من الـ loop guard ومن فحص الـ already_failed، وإرجاع الحمولة الكاملة (بالقالب العربي) في كل جولة؛ إرسال `{"error": "Failed"}` يجعل الموديل يعتذر أو يدّعي عطلًا.
  7. **نسخة الوكيل الموظف لقطة مستقلة (Spawned-Agent Persona Snapshot):** التوظيف ينسخ عقود القالب الأربعة داخل `ai.agents.persona` (JSON: soulInstructions/agentInstructions/toolsInstructions/personaInstructions) + عمود `soul` — أي تحديث لاحق لملفات القالب **لا يصل للنسخ الموظّفة تلقائيًا**؛ المزامنة تتم بإعادة بناء الـ persona من الملفات المنشورة أو بإعادة التوظيف، ويُعاد تشغيل الخدمة لإبطال كاش البرومبت (TTL 300s).
  8. **سكريبتات الفشل في العقود سلاح ذو حدين:** أي جملة رد جاهزة مقتبسة في SOUL/PERSONA (مثل صيغة اعتذار عند التعثر) سينفذها الموديل حرفيًا حتى في السياقات الخطأ (كإحباط أدوات انتظار الموافقة) — اكتب بروتوكول الفشل بدون عبارات رد حرفية قابلة لإعادة الاستخدام، ولا تقتبس العبارات الممنوعة داخل البرومبت.
  9. **تجزئة تنفيذ الأدوات في الـ pipeline (Read/Write Partitioning):** الأدوات المكتوبة مباشرًا (`DIRECT_WRITE_TOOL_NAMES`) تُنفَّذ **تسلسليًا بترتيب النداء** عبر `_execute_tool_calls` بينما القراءات والمحجوبة بالموافقة تعمل متوازيًا — منعًا لسباق تحديث نفس الكيان. ترتيب النتائج يُعاد لمحاذاه الأصلي لأن `_build_followup_messages` يربطها بالفهرس.
  10. **ضغط نتائج الأدوات في الـ pipeline إلزامي:** نجاح الأداة يمر عبر `ToolResultCompactor` + سقف قصّ صلب (8k chars) قبل دخول قائمة الرسائل (`_compact_for_llm`)، مع بقاء النتيجة الكاملة في `executed_tools/tool_evidence` للمُصدّقات، وحمولات `awaiting_approval` تمر خامًا ليبقى قالب الرد العربي سليمًا.
  11. **إنفاذ `budget.maxToolCallsPerRun` في الـ pipeline:** الجولة الأولى تُقص للسقف، وجولات المتابعة تتوقف عند بلوغه برسالة `[Budget]` عربية تلزم الموديل بالت تلخيص فوري بدون أدوات إضافية (الافتراضي 10).
  12. **ردود الـ Degraded Mode تتولد بالـ LLM من الأدلة (No Hardcoded Reply Templates):** عند رد الموديل فارغًا بعد كل المحاولات، نداء تخليق واحد (`_synthesize_fallback_reply`) يبني الرد بهوية الوكيل من ملخص أدلة الأدوات (`_build_evidence_digest` — مضغوط، الأدوات المعلقة موسومة «بانتظار موافقة»، الأخطاء صادقة)؛ سطر محايد واحد بلا شخصية ولا إيموجي هو الاستثناء الأخير الموثق فقط. ينفذ قانون `agentic-ai-research-radar`: «ردود العميل تُولَّد من الـ LLM من سياق منظم — ممنوع قوالب جاهزة».
  13. **فحص مخاطر المخرجات إلزامي قبل التسليم (Output Risk Scrub):** نهاية `validate_reply` تفحص الرد النهائي بأطرار أسرار المزودين (sk-/AIza/ghp_/xox/Bearer/JWT) وتسريبات credential key-value وconnection strings والـ tracebacks واستثناءات الفريمويرك — الأسرار تُقنَّع والتعثر يُستبدل بسطر احتواء محايد، مع حفظ أرقام هواتف العملاء غير ممسوسة (شرعية في فلوص الأوردرات).
  14. **ضغط الذاكرة هرمي لا FIFO أعمى:** تجاوز ميزانية التوكنز يُحوِّل الرسائل المسقطة إلى `<conversation_summary>` محدود (آخر 20 دورة × 140 حرفًا) بعد الـ system prompt بدل حذفها — حماية حقائق الكيانات (مقاسات/عناوين/اتفاقات) من النسيان المفاجئ.
  15. **حقول المزودين الخاصة لا تُرحَّل بين المزودين:** `reasoning_content` (امتداد DeepSeek) يُرسل لمزود DeepSeek فقط في تطبيع الرسائل — Groq/OpenAI يرفضون الحقول غير المعروفة بـ 400.
  16. **الاختبارات الوحدوية الخضراء لا تعني صحة المسار الحي (Live Write-Path E2E Mandate):** ثغرة تجاوز البوابة مرت من سويت اختبارات كامل أخضر — اكتشفها **فقط** طلب كتابة حقيقي على مستأجر حي. أي تغيير في سياق تنفيذ أدوات الشات يجب أن يُختبر E2E بطلب كتابة فعلي (تفعيل → منع → draft → اعتماد → تنفيذ → إرجاع حالة المستأجر) قبل إعلان النجاح.
  17. **غيّرت سياق التنفيذ؟ امسح كل مواضع التنفيذ:** عند تعديل دلالات تنفيذ الأدوات، ابحث عن كل مواضع الاستدعاء (الجولة الأولى، إعادة المحاولة، جولات المتابعة، منفّذ الاعتماد) وعن تفاعل الحراس معها (loop guard، failure dedup) — إصلاح موضعين من ثلاثة يترك الثغرة حية في الثالث (حصل فعليًا: `asyncio.gather` جولات المتابعة فات أول إصلاح).
  18. **دوال الكتابة تنفّذ فعلاً عند الاعتماد (No Double-Gate):** الاعتماد يُنفّذ الأداة بنداء `tool.func` مباشر عبر `approval_service._execute_action` — دالة الأداة المقيّدة يجب أن تنفذ العمل الحقيقي، ويُحظر أن تعيد حمولة `_write_result` ثانية (بوابة مزدوجة = لا-عمل صامت).
  19. **كوميت ملفاته `.md` فقط لا يُطلق deploy:** الـ workflow عليه `paths-ignore: '**/*.md'` — أي تغيير عقود/توثيق لازم يوصل الإنتاج بسرعة يُرافق بتعديل كود أو empty commit، ويُتحقق بmarker على السيرفر.
  20. **حقن سياق الأوردر النشط يحتاج سلسلة معرفات متعددة (Multi-Identifier Order Resolution):** ربط العميل بأورده عبر معرف واحد يفشل في الواقع — صفوف العملاء مكررة أو بلا هاتف، و`orders.conversationId` قد يكون فارغًا. الحل: جرّب `conversationId` ثم `customerId` ثم `customerPhone` (مستخرجًا من رسائل العميل نفسها)، ورتّح مطابقة الـ conversation أولًا. كما أن `asyncpg` يفشل بـ `AmbiguousParameterError` على الباراميترات المستخدمة في `IS NOT NULL` — يجب `CAST(:x AS text)` صريحًا، و`customerAddress` قد يكون JSON string يحتاج فكًا قبل العرض.
  21. **فشل SSH من fail2ban على runners GitHub يُعالج بإعادة تشغيل الجزء الفاشل:** `POST /repos/{owner}/{repo}/actions/runs/{run_id}/rerun-failed-jobs` (بالتوكن من `git credential fill` — الريبو خاص وAPI بيرجع 404 بدونه). البناء الناجح لا يعاد دفعًا؛ رانر جديد = آيبي جديد.
  22. **أرشفة وسائط الشات لحظة الويب هوك إلزامية:** روابط Meta موقعة وقصيرة العمر — `chatMediaArchiveService` ينزّلها مرة واحدة (بعد ack 200، timeout 10s، سقف 20MB) ويعيد استضافتها تحت `/uploads/chat-media/`، مع حفظ الأصل في `metadata.originalMediaUrls`. كل مستهلك لاحق (واجهة، درع الـ AI، تصدير) يأخذ الرابط المستقر.

## ❾ بروتوكول التغذية العكسية والتطوير المستمر (Continuous Improvement Protocol)

هذه المهارة كائن حي يتطور مع كل اكتشاف وتجربة عملية في المنصة:
1. **توثيق الأخطاء فور اكتشافها:** عند ظهور أي خلل معماري أو ثغرة في سلوك الوكلاء أثناء الإنتاج، يتم فوراً تحليل المشكلة وإضافتها كقاعدة معمارية في هذا الملف.
2. **المراقبة والتدقيق اليومي على الطلب (On-Demand Daily Health Check):**
   - بمجرد طلب المراجعة (مثل: "راجع اليوم وشوف هل في مشكلة ظهرت للايجنت")، يتم فوراً تشغيل سكربت الفحص الشامل:
     ```bash
     node apps/backend/scripts/diagnose_agent_activity.cjs 24
     ```
   - يفحص السكربت 5 طبقات تشغيلية في قاعدة البيانات والسيرفر:
     1. تقييمات ومخالفات نظام المراجعة الذاتية (`ai.self_review_log`).
     2. استدعاءات الأدوات الفاشلة والـ Exceptions في (`telemetry_spans`).
     3. أخطاء توليد ومسارات ونشر إعلانات الميديا باير (`facebook_ads_ai_draft_runs` و `facebook_ads_publish_requests`).
     4. تصعيدات المحادثات للتدخل البشري والمشاعر السلبية (`ai_interactions`).
     5. فحص سجلات التشغيل اللحظية للـ Microservices عبر PM2 على السيرفر.
   - عند اكتشاف أي خطأ، يتم تحليل السبب الجذري (Root Cause)، وتطبيق الإصلاح الوقائي فوراً، ثم تسجيل التحديث في هذا الملف.
3. **تحديث قائمة الفحص (Checklist):** يُضاف بند فحص صريح يمنع تكرار نفس الخطأ في المستقبل.
4. **التكامل الدائم مع الذاكرة:** تظل هذه المهارة مسجلة في الذاكرة الدائمة (`MEMORY.md`) كمرجع قياسي إلزامي لجميع جلسات ووكلاء المنصة.
