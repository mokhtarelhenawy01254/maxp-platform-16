## ملخص تنفيذي

نظام الصلاحيات **مبني بشكل صح** (6 أدوار + جدول صلاحيات في الداتابيز بـ169 مفتاح)، لكن **التطبيق غير متسق**:

- **526** استخدام `requireRole` (بيتجاهل جدول الصلاحيات تمامًا)
- **282** استخدام `requireDbPermission` (بيستخدم الجدول)
- **0** استخدام لـ `requirePermission` (المصفوفة القديمة `rbacMiddleware.PERMISSIONS` ميتة لكنها هي اللي بتظهر في لوحة الإدارة)
- **لا يوجد أي row-level scoping** (مدير قسم لا يرى قسمه فقط)

**الخطر الأكبر:** حقل `role` بيتنقل من `req.body` بدون allowlist → **MANAGER على مستوى شركة يقدر يصنع مستخدم `SUPER_ADMIN` على مستوى المنصة** ويكسر حدود كل الشركات.

## F-01 🔴 CRITICAL — تصعيد صلاحيات لـ `SUPER_ADMIN` عبر إنشاء موظف

**الأدلة:**
- `apps/backend/routes/hrRoutes.js:252` — `POST /api/hr/employees` محمي بـ `requireRole(['SUPER_ADMIN','COMPANY_ADMIN','OWNER','MANAGER'])`
- `apps/backend/controller/hrController.js:1598-1602` — يمرّر `req.body` كما هو
- `apps/backend/services/hr/employeeService.js:131` — `user.role = data.role || 'AGENT'`
- `apps/backend/services/hr/employeeService.js:146` — `userCompany.role = data.role || 'AGENT'`
- `apps/backend/middleware/superAdminMiddleware.js:132` — `systemRoles.includes(req.user.role)` يفتح لوحة `/super-admin` كاملة
- `apps/backend/utils/verifyToken.js:542` — `effectiveRole = membership.roleRef?.key || membership.role`

**مسار الاستغلال:** MANAGER يعمل `POST /api/hr/employees` بـ `{"role":"SUPER_ADMIN", ...}` → المستخدم الجديد `User.role='SUPER_ADMIN'` → يتخطى `requireCompanyAccess` وكل الحُرّاس (`rbacMiddleware.js:288-296`, `verifyToken.js:789`, `checkAppAccess.js:327`) → قراءة/كتابة على كل الشركات.

**الإصلاح المطلوب:**
1. allowlist صريح في `employeeService.createEmployee` **و** `updateEmployee`: `['AGENT','MANAGER','COMPANY_ADMIN']` فقط.
2. منع `OWNER`/`SUPER_ADMIN` نهائيًا من هذا المسار (ترقية لـ OWNER تحتاج مسار أدمن منصة منفصل + تأكيد + audit log).
3. رفض أي دور غير موجود في `UserCompaniesRole` بـ 400 واضح.

**معيار القبول:** `POST /api/hr/employees` بـ `role=SUPER_ADMIN` من حساب MANAGER → **403**، ولا يتغير أي صف في `users`.

## F-02 🔴 CRITICAL — MANAGER يقرأ/يعدّل/يعتمد/يصرف الرواتب (فصل مهام مفقود)

**الأدلة:**
- `apps/backend/routes/hrRoutes.js:436-450` — كل مسارات الرواتب `requireRole([...,'MANAGER'])`:
  `POST /payroll:441` · `POST /payroll/generate:442` · `POST /payroll/bulk-pay:445` · `PUT /payroll/:id:447` · `POST /payroll/:id/approve:448` · `DELETE /payroll/:id:450`
- `apps/backend/prisma/seeds/seedPermissions.js:290-323` — دور `MANAGER` **لا يحتوي** `hr.payroll` (متعارض مع الواقع)
- `hrRoutes.js` فيه **0** استخدام لـ `requireDbPermission` → `hr.payroll` غير مطبّق في أي مكان بالكود
- `apps/backend/routes/hrRoutes.js:248` — `PUT /employees/bulk-salaries` (MANAGER)
- `apps/backend/routes/hrRoutes.js:403` — `POST /salary-history` (MANAGER)
- `apps/backend/controller/hrController.js:3516-3596` — الـ handlers تفلتر بـ `companyId` فقط، بدون هوية المستدعي

**المشكلة:** نفس الشخص ينشئ كشف الراتب → يعتمده → يعلّمه مدفوع → يحذف أثر المراجعة.

**الإصلاح المطلوب:**
1. استبدال `requireRole` بـ `requireDbPermission('hr.payroll.create' | '.approve' | '.pay' | '.delete')` على المسارات دي.
2. **فصل مهام إجباري:** `createdById !== approvedById` على الاعتماد (409 لو نفس الشخص).
3. إضافة `hr.payroll` لدور `MANAGER` **فقط** لو قرار العمل يسمح؛ الأفضل `false` وإسناد صلاحية مخصصة.

**معيار القبول:** حساب MANAGER بدون `hr.payroll.approve` → 403 على `/approve`، والحساب اللي أنشأ الكشف لا يستطيع اعتماده.

## F-03 🔴 CRITICAL — `GET /hr/employees` مكشوف لكل موظف وبيرجّع الرواتب

**الأدلة:**
- `apps/backend/routes/hrRoutes.js:250` — لا يوجد `requireRole` على المسار
- `apps/backend/controller/hrController.js:1707-1760` — فلتر "الخصوصية" يستخدم `privilegedRoles` يتضمن **`AGENT`** (`:1732-1738`) → فرع حذف `baseSalary`/`phone`/`nationalId`/`contractType`/`hireDate` **لا يعمل أبدًا لأي دور حقيقي**

**الأثر:** أي موظف يفتح `GET /api/hr/employees` ويشوف رواتب وموبايلات وأرقام قومية لكل الشركة.

**الإصلاح المطلوب:** `privilegedRoles = ['OWNER','COMPANY_ADMIN','SUPER_ADMIN','MANAGER']` (بدون AGENT) + فلترة الحقول حسب `req.user` قبل الإرجاع.

**معيار القبول:** استجابة AGENT لا تحتوي `baseSalary` ولا `nationalId` نهائيًا في الـ JSON.

## F-04 🔴 CRITICAL — أي AGENT يعدّل إعدادات الشركة ويكسر اشتراك التطبيقات المدفوعة

**الأدلة:**
- `apps/backend/routes/settingsRoutes.js:131-197` — `PUT /api/v1/settings/company` يدمج `req.body.settings` بدون أي دور (فقط `authenticateToken` في `:19-24`)
- `apps/backend/middleware/checkAppAccess.js:131-150` — `bypassExpiry` / `allowAccessWhenExpired` / `bypassAppExpiry[]` تمنح وصول دائم

**مسار الاستغلال:** AGENT يبعت `{"settings":{"bypassAppExpiry":["whatsapp-business","hr-core"]}}` → استخدام مجاني دائم.

**الإصلاح المطلوب:** `requireDbPermission('settings.manage')` + **allowlist للحقول القابلة للتعديل** لكل مستوى دور (حقول الفواتير/الاشتراك/التجاوزات = OWNER فقط).

**معيار القبول:** PUT من AGENT → 403؛ ومن OWNER → 200 مع رفض المفاتيح الممنوعة.

**الإصلاح المطلوب:** حذف المسار نهائيًا (أو نقله بعد الحُرّاس + `requireSuperAdmin` + إرجاع حقول آمنة فقط). + قاعدة: **لا route قبل `router.use` الحُرّاس**.

## F-08 🟡 MEDIUM — أدوار غير موجودة وأدوار مخصصة قابلة للتصعيد

**الأدلة:**
- `apps/backend/prisma/schema/enums.prisma:666-674` — `UserCompaniesRole = OWNER|SUPER_ADMIN|COMPANY_ADMIN|MANAGER|AGENT|AFFILIATE`
- `apps/backend/routes/orders.js:1204` + `controller/orderController.js:319` — يفحصان `['MODERATOR','EMPLOYEE']` وهما **غير موجودين في الـ enum** → الشرط ميت، فأي AGENT يعدّل أي أوردر (المقصود: أوردراته فقط)
- `apps/backend/routes/hrRoutes.js:338` — `'HR_MANAGER'` غير موجود في الـ enum ولا في `BUILT_IN_ROLES` → مسار محجوب فعليًا
- `apps/backend/services/permissionService.js:63-95` + `routes/permissionRoutes.js:11` — إنشاء role مخصص بـ `key` غير مُتحقّق منه، و`setUserRole` (`:194-197`) بينسخ الـ key إلى `userCompany.role` لو ضمن `VALID_ROLE_ENUMS` (**يتضمن `SUPER_ADMIN`**) → مسار تصعيد ثانٍ
- `apps/backend/controller/companiesController.js:1628` + `:2095-2160` — `VALID_ROLE_ENUMS` يتضمن `SUPER_ADMIN`؛ COMPANY_ADMIN يقدر يرقّي نفسه، ويقدر كمان يغيّر باسورد OWNER (`:1985-1989`)
- `apps/backend/controller/companiesController.js:2151-2157` — fail-open: لو دور مدمج ناقص، يتعمل تلقائيًا **بكل الصلاحيات**

**الإصلاح المطلوب:**
1. إزالة `SUPER_ADMIN` من كل `VALID_ROLE_ENUMS` على مسارات الشركات/الأدوار المخصصة.
2. توحيد مفردات الأدوار: أي دور مستخدم في الكود لازم يكون موجود في `UserCompaniesRole` (حذف `MODERATOR`/`EMPLOYEE`/`TEAM_LEADER`/`HR_MANAGER` أو إضافتها رسميًا).
3. تحويل fail-open (`findMany({isActive:true})`) إلى **fail-closed** (رفض + تنبيه).

## قيود إلزامية على التنفيذ (Strict Change Isolation)

1. **ممنوع تغيير شكل أي استجابة API مشتركة** — إضافة حقل مسموح، حذف/إعادة تسمية ممنوع. أي حقل هيُخفى (مثل `baseSalary` لغير المصرح) لازم يتفلتر في طبقة جديدة، ويُراجع تأثيرها على `apps/frontend` و`apps/desktop`.
2. قبل تعديل أي controller/service: `node scripts/graph/query-graph.cjs callers <symbol>` — إلزامي، وبعد التعديل `graphify update .`.
3. **OWNER bypass** في `rbacMiddleware.js:288-296` **لا يُمس** (مقصود)، لكن `SUPER_ADMIN` الناتج عن سياق شركة (F-01/F-08) لا يجب أن يصل لهذا الـ bypass أصلاً.
4. كل مسار جديد أو معدّل: **اختبار** يثبت 403 لغير المصرح و200 للمصرح.
5. ممنوع لمس `apps/frontend/src/config/sidebar.ts` بشكل يخفي قوائم عن أدوار كانت شايفاها، إلا بعد تعديل الباك إند أولًا.
