## Why the `growth` slot
`config/facebookAppConfig.js#getFacebookAppKeyConfig(key)` **only** understands `primary` and `growth`; every other key silently falls back to primary. The DB registry (`facebook_apps`) is therefore *not* enough to run a third app.

So MAXP temporarily runs in the `growth` slot:
- registry row `growth` updated via `POST /api/v1/super-admin/platform/meta-apps` → `appId=1121885177390870`, `appSecretRef=FACEBOOK_GROWTH_APP_SECRET`.
- `POST …/meta-apps/growth/test-connection` → `connected: true`, `appName: "MAXP"`.
- `GET /api/v1/facebook-oauth/authorize?app=growth&companyId=…` → `client_id=1121885177390870` ✅

## Known issues found
1. `POST /super-admin/platform/meta-apps` hardcodes `['primary','growth']` → new keys rejected (fixed in local code, not deployed).
2. `getFacebookAppKeyConfig` hardcodes `primary`/`growth` → needs registry-aware lookup for a real 3rd app.
3. `/super-admin/meta-apps` page renders **empty** in production (header only, no app cards) — API returns both apps fine, so it is a frontend rendering bug.
4. `toggleMetaAppStatus` also hardcodes the two keys (fixed locally).
5. Cloudflare 524 on the OAuth callback for accounts with very many pages.
