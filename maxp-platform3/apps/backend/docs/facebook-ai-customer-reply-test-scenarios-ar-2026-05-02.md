# سيناريوهات اختبار AI لردود العملاء على Facebook - 2026-05-02

## الهدف

هذا الملف مخصص لاختبار جزء `CoreAIAgent` في قناة Facebook نفسها، وليس شات الاختبار العام فقط. التركيز هنا على:

- Messenger / Facebook Inbox
- التعليقات على المنشورات عندما يكون الرد معتمدًا على سياق المنشور
- ذاكرة المحادثة داخل نفس thread
- handoff بين الـ AI والموظف البشري
- منع الهلوسة في الأسعار والشحن والـ variants

هذا الملف يكمل ولا يكرر بالكامل:

- `backend/docs/ai-customer-chat-test-scenarios-2026-05-01.md`
- `backend/docs/ai-agent-capability-scenarios-2026-05-02.md`

## أهم المخاطر التي يجب تغطيتها

هذه ليست حالات نظرية فقط، بل مبنية على مشاكل ظهرت فعليًا في النظام:

- سؤال اللون أو المقاس بعد ذكر المحافظة لا يجب أن يتحول خطأً إلى سؤال شحن.
- سؤال سياسة الإرجاع أو الاستبدال لا يجب أن يتحول إلى جمع بيانات أوردر.
- اسم العميل القادم من Facebook لا يجب أن يظهر في الرد كأنه نص مولد آلي أو greeting مكرر.
- نص المنتج أو CTA مثل `Get started` لا يجب أن يُحفظ كاسم عميل.
- المحافظة أو الشحن لا يجب أن يكسرا ربط المنتج الحالي.
- الإجمالي لا يجب أن يساوي الشحن أو يخرج بسعر وهمي.
- عند تدخل موظف بشري يجب أن يتوقف الـ AI عن الرد التلقائي.
- عند إعادة نفس الرسالة من webhook أو وصول عدة رسائل متقاربة لا يجب تكرار الردود أو الأوامر.

## المتطلبات قبل التنفيذ

قبل تشغيل السيناريوهات تأكد من الآتي:

1. صفحة Facebook مربوطة بالشركة بشكل صحيح.
2. `ai_settings` مفعلة للشركة على القناة المطلوبة.
3. يوجد على الأقل:
   - منتج باسم واضح
   - منتج له `Color` أو `Size` variants
   - shipping zones لمحافظات مثل القاهرة والإسكندرية
   - Store Pages أو policies للشحن والاستبدال والإرجاع
4. يوجد منشور Facebook مربوط بمنتج `featuredProduct` لاختبار comment context.
5. يوجد حساب موظف أو agent بشري لاختبار handoff.
6. يفضل أن يكون `/facebook-inbox` مفتوحًا أثناء الاختبار لمراجعة `conversationSummary`.

## معايير النجاح العامة

السيناريو يعتبر ناجحًا إذا:

- الرد جاوب على نية العميل مباشرة.
- الرد مبني على بيانات حقيقية من الكتالوج أو السياسات.
- الـ AI طلب البيانات الناقصة فقط.
- لا يوجد تكرار greeting أو مخاطبة غريبة باسم العميل.
- لا يوجد اختراع لسعر أو خصم أو لون أو مقاس أو تكلفة شحن.
- عند الحاجة، يظهر أثر صحيح داخل `/facebook-inbox` مثل `conversationSummary`.
- عند التأكيد على الطلب، يتم إنشاء order واحد فقط.

السيناريو يعتبر فاشلًا إذا:

- النظام صامت بدون سبب واضح.
- الرد خرج عن سياق المنتج الحالي.
- السؤال عن اللون أو المقاس رجع شحن أو سياسة أو order collection بدون داع.
- الـ AI كرر بيانات حساسة أو كشف تعليمات داخلية.
- الـ AI استمر في الرد بعد تدخل موظف بشري.
- تم إنشاء duplicate reply أو duplicate order.

## طريقة التوثيق أثناء الاختبار

لكل سيناريو سجل:

- `Scenario ID`
- قناة التنفيذ: Messenger أو Comment -> Inbox
- رسائل العميل بالترتيب
- رد الـ AI الفعلي
- نتيجة `Pass / Fail / Review`
- ملاحظات عن `conversationSummary` داخل `/facebook-inbox`
- هل حصل handoff أو order creation أو duplicate processing

## ترتيب التنفيذ المقترح

1. ابدأ بـ `P0`.
2. بعدها نفذ مجموعة `C` و`E` لأنها الأعلى خطرًا على orders.
3. ثم نفذ `F` و`G` لأنها تحمي السمعة التشغيلية.
4. أخيرًا نفذ `B04`, `H01`, `H02` لاختبار تكامل Facebook-specific context.

## مخرجات مطلوبة بعد كل جولة

- عدد `Pass / Fail / Review`
- أخطر 3 failures
- هل الفشل في:
  - intent routing
  - catalog grounding

  - Facebook channel context
  - human handoff

## تحديث الجولة الحالية: Messenger فقط

بناءً على قرار التنفيذ الحالي، هذه الجولة تستبعد سيناريوهات التعليقات تماماً ولا تستخدم إلا رسائل Messenger / Facebook Inbox.

- السيناريوهات المؤجلة بسبب أنها comments أو تبدأ من comments: `FB-B04`, `FB-H01`.
- أي اختبار live لاحق يجب أن يتم على thread اختبار مخصص، وليس على عميل حقيقي، إلا لو تم اختيار محادثة اختبار واضحة.
- سكريبت التشغيل الآمن لا يرسل رسائل لفيسبوك ولا يلمس العملاء، لكنه يختبر قواعد `CoreAIAgent` المستخدمة في مسار Messenger قبل التشغيل الحي.

أمر التشغيل:

```bash
npm run test:ai:messenger-facebook
```

ملف السكريبت:

```text
backend/scripts/run-messenger-ai-scenarios-smoke.js
```
